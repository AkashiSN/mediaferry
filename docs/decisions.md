# 確定した設計判断とその理由

## はじめに

この文書は、mediaferry の**現在の設計がなぜこうなっているか**を話題ごとにまとめたもの。
各行は「判断」と「理由」の対で、理由の多くは実際に動かして、あるいはレビューで覆されて
初めて分かったことである。**理由を読まずに判断だけを元へ戻さないこと。**

- **いまの仕様**は [`design.md`](design.md) にある。この文書は仕様書ではなく、仕様が
  そうなっている根拠の置き場である。行の中の `§N` は `design.md` の節番号を指す。
- **開発の記録**（フェーズごとの計画・調査の経過）は [`history/`](history/) にある。
- 根拠が実測であるものは、話題に関わらず最初の節にまとめてある。

## 実測で覆った判断

机上の設計を実際に動かして覆った判断。**理屈で元へ戻すと同じ穴に落ちる。**
話題ごとの節にも関連する行があるが、覆した根拠が実測であるものはここに置く。

| 判断 | 理由 |
| --- | --- |
| **マウントは detached にする**（`mount` → `open_tree(OPEN_TREE_CLONE)` → `MNT_DETACH`） | 通常マウントの dirfd は `openat(dirfd, "..")` で親へ抜け、**親ディレクトリのファイルを実際に読めた**。規約では RCE を脅威モデルに含む §14 の境界を満たせない |
| **結合の検証にファイルサイズの単純比較を使わない** | `-c copy` は DJI の `dbgi`（ジャイロ、10.3 Mbps）等を落とすので、正常な結合でも **11.4% 縮む**。旧条件（Σ パートと ±1%）では全ての結合が不合格になっていた |
| **`remote_user_id` は同一性ではなく向き先変化の guard** | Immich v3.1.0 はサーバインスタンス ID を公開していない。`/api/server/about` は version/build のみで同版の全サーバで一致する |
| **`origin` は `status: created` を commit できた場合だけ `created_by_us`** | `deviceAssetId` が資産応答に無い。初回 `checking` が `accept` でも自作の証明にならない（間に別クライアントが割り込みうる） |
| **`isTrashed` を無視しない** | Immich のゴミ箱にある資産も重複として再アップロードを弾く |
| **接続先 URL と表示用 URL を分ける** | 公開 URL（Cloudflare 経由）では 622 MiB で 502。内部経路なら 28.36 GiB が 84.5 秒で完走 |
| **USB の `serial` を一意な識別子にしない** | Linux ガジェットの既定値 `123456789ABCDEF` だった。機体固有の文字列は `product` 側 |
| **空の `DCIM` でも正当なボリューム** | Osmo の内蔵ストレージは `DCIM` を持つが空だった |
| **checksum は base64 に統一** | `bulk-upload-check` は hex/base64 両方を受理するが `x-immich-checksum` は base64 |
| **mtime は真の瞬間。TZ を付けた aware な値をそのまま使う** | 「カードの時刻欄に UTC オフセットは書かれていない」を前提に mtime の UTC 表現を壁時計として使っていたが、**DJI は exFAT の `OffsetFromUtc` を書いていた**（2026-08-21 の実測。mtime を +09:00 で描画すると録画終端と +2 秒、UTC だと 9 時間ずれる）。UTC 表現を壁時計にすると `captured_at` がオフセットぶんずれる。**`_wall_clock` の mtime fallback・`publisher._collision_stamp`・`merger._recording_end_ns` を同時に直した** —— 片方だけだと `library/` と `derived/` で接尾辞の壁時計がずれる。`timezone_policy: none` は描画に使う TZ を持たないので UTC 表現のまま（介入しない方針そのもの）。**naive の壁時計へ落として付け直さない** —— 落とすと DST の戻りでどちらの 1 時間かを失い、`_attach_offset` が「先に来る方」を選んで 1 時間ずれる。曖昧さの解決は**壁時計から始めた値**（ファイル名・EXIF）だけの話。測った値は [`history/hardware-verification.md`](history/hardware-verification.md) |
| **Canon の `creation_time` は現地の壁時計であって UTC ではない。`Z` を信じない** | `canon-eos` は「EXIF にローカル時刻を書くので補正が不要」として `timezone_policy: none` にしていたが、**動画には EXIF が無い**。器（QuickTime の `format.tags.creation_time`）は `2026-08-26T12:35:08.000000Z` のように書かれるのに中身は現地の壁時計で、真に受けると **Immich で 9 時間ずれる**（2026-08-26 の実測。写真は 12 時 JST で正しく、動画だけ 12 時 UTC になった）。`force_offset` + `fix_datetime_after_upload: true` へ倒した。**`fix_datetime_after_upload` だけでは効かない** —— `none` のままだと書き戻す値そのものが UTC 扱いのままになる |
| **器が指すのは録画の開始、mtime は録画の終了** | 実測: 分割された 2 片は `creation_time` が別々（+0.572 秒の継ぎ目）なのに mtime は 2 つとも同じだった。**mtime に落ちると、分割の片が全部同じ時刻になって並びも継ぎ目も読めない** |
| **Canon は exFAT の `OffsetFromUtc` を書かない** | DJI で `instant` が正しかったからといって、他の機種に持ち込めない。Canon のカードでは UTC 表現の桁が現地の壁時計だった（`canon-eos` は既定の `wall_clock` のまま） |
| **`timestamp.source` は連鎖にする。`fallback` は廃止** | 写真は EXIF、動画は器、どちらも無ければ mtime —— 出所が 1 つと「当たらなかったとき」の 1 つでは足りない。**末尾は `mtime` でなければならない**（`mtime` だけが必ず値を返すので、算出が全域関数であり続ける根拠）。リリース前なので互換シムは作らず、他のプロファイルの版も進めた |
| **mtime の意味はプロファイルが宣言する**（`timestamp.mtime_semantics`、既定 `wall_clock`） | 「真の瞬間」が成り立つのは `OffsetFromUtc` を書く媒体だけ。FAT32 と valid bit の立たない exFAT では、Linux がマウントの `time_offset`（既定 0）で合成した**疑似 epoch**になる。**媒体の性質なので値の形からは見分けられない**（この案件で繰り返し出た「形から素性を推定する」誤り）。API は任意のユーザ定義プロファイルに `force_offset` を許すので、実データが出てから足すと**確定済みの公開名と派生物の mtime が直せないまま残る**（再計算は日時の 5 列しか触らない）。**既定は `wall_clock`** —— 宣言の無い定義（この欄より前に作られたもの）に「瞬間」を仮定すると黙ってずれる。実測した `dji-osmo` だけが `instant` を明示する。codex のレビューでの指摘を容れた |

## マウントとデバイスの同定

カードの検出・同定・自動取り込みの「門」に関する判断。**安い変化検出（列挙）と高い判定
（マウントを伴う `refresh()`）を分ける**ことが全体を貫く原則で、門の内側で判定すると
利用者の操作が反映されなくなる。

| 判断 | 理由 |
| --- | --- |
| **検出の起動源は `list_volumes` の generation ポーリング。`subscribe`（netlink uevent）は入れない** | `enumerate_volumes` は `_is_usb` で絞ってから `blkid` を掛けるので、USB ブロックデバイスが無い間はサブプロセスが起きない。高いのは列挙ではなく `refresh()`（判定のたびに実際にマウントする）で、**それは uevent 駆動でも同じ罠**。分けるべきはトリガの種類ではなく、安い変化検出と高い判定（根拠は §9.2） |
| **`refresh()`（マウントを伴う判定）は観測トークンの変化でしか走らせない。enqueue の判定は毎 tick DB の現在値から組み直す** | `trust()` は `trusted_at` を `UPDATE` するだけで mountd の指紋を動かさない。門の内側で判定すると、**カードを挿したまま承認しても自動取り込みが始まらない**。同じことが `AUTO_IMPORT` の変更とプロファイルの編集でも起きる。**利用者が DB を変えたことは観測トークンには現れない**（レビューで見つかった） |
| **判定材料はすべて DB に置く**（`0010` の `volume_instance.provisional`） | 1 つでも `VolumeView` にしか無いと、毎 tick の組み直しが成立しない |
| **`volume_instance.profile_id` / `profile_revision_id` は「前回の判定の写し」。現在の真実ではない** | 候補の抽出で `device_profile` を JOIN し、**archive されていないこと**と**その版が今も現行であること**を確かめる。確かめないと、判定の後・積む前に別接続で archive / `PUT` が commit でき、archive 済みのプロファイルや編集前の版で取り込みを積む（レビューで見つかった） |
| **観測トークンは空集合を専用の番兵として扱い、「未観測」と必ず区別する** | `generation` と `broker_epoch` は `VolumeInfo` の中にしかない（`_do_list` は volumes を返すだけ）ので、最後の 1 枚を抜くと読む場所が無くなる。同一視すると、前回の停止時に live のまま残った presence がある状態で空で起動したとき、**最初の tick が `detach_absent` を飛ばして抜けたカードに積む**（レビューで見つかった） |
| **門の入力には「プロファイルの現行版の指紋」も含める** | `require` を変えても mountd の観測は動かない。編集・複製・archive のどれでもこの値が動くので、明示的な wake を別に作らずに済む |
| **`VolumeWatcher` は 1 つのスコープを丸ごと持つ**（専用の DB 接続・`ProfileRegistry`・`VolumeService`・`BrokerClient`） | `refresh()` は自分の `BrokerClient` を使うので、API 側の `VolumeService` を借りると、停止のために専用ソケットを閉じても黙り込んだ `refresh` が止まらない。接続だけ共有すると 1 本の接続を 2 つの `RLock` で同時に使うことになる（レビューで見つかった） |
| **`lifespan` の停止順は watcher が先、runner が後** | 逆にすると、runner が降りた後に自動取り込みが積まれる |
| **`VolumeService.refresh()` の pass 1〜2 は `BEGIN IMMEDIATE` で囲む** | インスタンスが 1 つしか無かったから autocommit で成立していただけ。watcher が 2 つ目を持つと、pass の合間に相手の書き込みが挟まる。**判定（pass 3）はマウントを伴って長いので外に出す** |
| **`BrokerClient` の再接続は `list_volumes` だけ。閉じている最中は再接続しない** | `open_volume` は fd を伴うので再送すると 2 度目のマウントが起きる。`close_volume` の handle は発行した接続に束縛されている。停止は接続を閉じて `recv` を解くので、その `OSError` を再接続が拾うと停止が効かない（レビューで見つかった） |
| **`VolumeObservation` は接続の同一性であって媒体の同一性ではない** | mountd の `generation` は観測した集合の指紋が変わったときだけ進む。polling の合間に同じ UUID・容量のカードが同じノードで差し替わると据え置きになる。**開いた dirfd を使い回す根拠にできない**（判定は毎回開き直し、ジョブの handle は release で閉じる） |
| **プロファイルの一致度とボリュームの同定確度を混ぜない** | 中身が DJI のファイルであることは「前回と同じカードだ」の証明にならない。混ぜると同じ UUID の別カードが `trusted_at` を引き継ぐ |
| **ジョブは選択した瞬間の presence を params に持つ** | `volume_instance_id` だけを渡して実行時に最新の presence を選ぶと、抜き差しでカードが入れ替わっていても現在値から正しい `expect` を組み立て、ブローカーの TOCTOU 検証をすり抜ける |
| **自動取り込みが効くのは 2 度目以降の「観測」から。挿し直しは要らない** | `_identity_confidence` は憶えた指紋が無ければ必ず `low` を返す（「初めて見るカードは §12.1 のとおり必ず承認を待つ」）。ただし指紋を憶えるのは最初の `refresh()` なので、**同じ挿入のまま次の tick で `high` になる**。承認すると、**いま挿してあるカードの中身が数秒後に取り込まれる** —— 画面の文言も確認ダイアログもそう書く（「次に挿したときから」と書くと、同意の対象を取り違えさせる） |
| **「積んでよいか」の入力は全部、enqueue と同じ `BEGIN IMMEDIATE` の中で読む**（`AUTO_IMPORT` を含む） | 外で読むと、読んだ後・積む前に `PUT /settings` が `off` を commit でき、**off になった後で積める** |

## デバイスプロファイル

プロファイルは「取り込みの規則」であり、版（リビジョン）で固定して使う。ビルトインは
アプリ更新で同期されるので、編集を許すと黙って上書きされる。

| 判断 | 理由 |
| --- | --- |
| **ジョブは固定したプロファイルリビジョンを読む** | 現行を読み直すと、キューで待っている間の編集で、確認画面と違う規則で処理される |
| **プロファイルの正規表現は `regex` + `timeout` で当てる。`re` は使わない** | 長さの上限では catastrophic backtracking を防げず、保存時に敵対的な標本を試すのも `(z+)+$` が `a` の標本を素通りするので保証にならない。**実測**: `re` は `(a+)+$` に 10 秒でも終わらないが `regex` は 0.000 秒、`regex` でも破綻する `(a\|a)+$` には `timeout=` が 0.500 秒で発火する |
| **`PatternTimeout` は「一致しなかった」ではなく失敗として扱う** | 黙って不一致にすると原因が画面から分からない。判定では対象外に落として理由を出し、取り込みでは `fallback` へ落とす |
| **ビルトインへの mutation は `duplicate` を除いて全部拒む。ガードは 1 箇所に集約する** | `_upsert_revision` は `builtin` を見ないので、編集を許すと次のアプリ更新で `sync_builtins` が黙って上書きする。**`archive` も同じ** —— `sync_builtins` は `archived_at` を戻さないので、一度 archive すると再起動しても復活しない（レビューで見つかった） |
| **プロファイルの読み取りは `all()`（archive 済みを含む）と `active()`（含まない）に分ける** | 同じ一覧を両方の用途に使うと、どちらかが必ず間違う。一覧 API は `all()` —— archive は削除ではないので、一覧から消すと「外した」のか「消えた」のか区別が付かない |
| **`canon-eos` は `hints.usb_ids` を空にし、`merge` を有効にする（`min_part_size_gib: 3`）** | カードリーダー経由が前提なので、見える USB ID はリーダーのもの。分割の判別根拠は実カードで測って得た —— 片は 3.9675 GiB で切れ、継ぎ目は +0.572 秒、別録画は +55.063 秒。**誤結合は公開済みの `media_file` を取り残す**ので高くつくままで、閾値は実測より下（3 GiB）に置いて片側だけを厳しくする |
| **`generic-dcim` はメーカー固有の RAW と `MTS` を拾わない** | 汎用が拾うと機種プロファイルを作る動機が消えて `library/generic-dcim/` に何でも溜まる。`MTS`（AVCHD）は `BDMV` の構造とセットで意味を持つので、単体で拾うと分割された動画が個別に取り込まれる |

## 取り込みと公開（ArtifactPublisher と crash consistency）

取り込みと結合は同じ公開手順を共有する。**手順 6 までと 7 以降で回収の性質が変わる**
という境界が、両方の crash consistency の土台になっている。

| 判断 | 理由 |
| --- | --- |
| **§7 の 5 つのディレクトリは起動時にアプリが作る**（`ensure_layout`） | 手順書の `mkdir -p <dataset>/{library,...}` は、起動時の `assert_same_filesystem` が `stat` するためだけに存在していた（実際の書き込み先はどれも `parents=True` で作られる）。無いと `FileNotFoundError` で落ち、**原因も読めない**。**`chown` はアプリにはできない** —— 自分に権限を与えることになるので、作れないときは `chown <uid>:<gid> <dataset>` を示して止まる。**別々のデータセットに分ける事故も減る**（アプリが作るのはディレクトリなので、`link(2)` が通らない構成になりにくい） |
| **公開は `ArtifactPublisher` の 11 手順を通す。import と merge で同じ** | 手順 6 までで落ちれば作業がなかったことになり、7 以降なら永続情報だけで完遂する。この境界を共有しないと片方だけ回収不能になる |
| **公開は `os.link`。`os.replace` を使わない** | EEXIST で失敗する no-clobber 性が要る。既存を黙って上書きすると、再フォーマットで連番が再利用されたカードが過去の取り込みを消す |
| **`staged` の手前で落ちたら、書きかけの staging をその場で捨てる**（`_discard_writing`） | 起動時の reconciliation も同じものを捨てるが、**それは次の起動まで走らない**。動かし続ける限り、分割 1 本ぶん（DJI なら 16 GiB）が残る。しかも `GET /orphans` は「行の無い実体」しか出さないので、`artifact_staging` の行を持つ書きかけは**利用者から見えない**。実機で確かめて分かった（カードを抜いた後、3.56 GiB が残っていた）。**捨ててよい根拠は所有権**で、対象は自分のジョブが `writing` で持っている行だけ。「一時ファイルを無条件に消さない」（§9.6）が守っているのは「別ジョブが使用中かもしれない」場合で、ここは当たらない |
| **起動時の回収の結果をログに 1 行残す**（`_log_reconcile`） | 破棄も再開もディスク上の実体を動かす。記録が無いと**消えた容量の説明が付かない**。実機では 3.56 GiB が黙って消えた（`ReconcileReport` は `AppState` に入るだけで、`GET /orphans` に出るのは孤立の件数のみ、`discarded` はどこにも出なかった） |
| **`staged` 以降の失敗を「取り込み失敗」として扱わない**（`PublishInterrupted`） | ファイルは検証済みで公開に必要な情報は永続化済み。`source_entry` を failed に戻すと、次のスキャンで新規と判定されて二重に取り込む |
| **結合物の公開は `ArtifactPublisher.publish_prepared`（`work` → `staging` を `os.link`）** | `write` コールバックで staging へ書き直すと 30 GiB をもう一度書く。`work/` と `staging/` は同一ファイルシステム（§7）なので link で移せる。11 手順と回収の性質は `publish` と同じ |
| **EXIF はステージ済みのファイルから読む**（§9.3 手順 4 の後・手順 5 の中） | ソースを 2 度読むと、コピー中に書き換えられた場合に「取り込んだ中身と読んだ EXIF が違う」状態を作れる。前で読むと未完成のファイル、後で読むと `metadata_json` に載らない（レビューで見つかった）。`ArtifactRequest` の `captured` と `resolve_captured` は `__post_init__` でどちらか一方に強制する |
| **画像以外では EXIF を読みに行かない** | `exifread` は認識できない入力に例外ではなく WARNING を出す（実測）。Canon は MOV も `source: exif` のプロファイルを通るので、呼べば動画 1 本ごとに警告が並ぶ。振り分けは `MediaProbe` と同じ `PHOTO_EXTENSIONS` で行う |
| **カードから消えたファイルの `source_entry` は、スキャンが外す**（`_sweep_vanished`） | 外さないと `pending_count` が実体より多いまま残る。画面は「N 件取り込む」と言うのに、取り込みは開けない ENOENT で失敗し、落ちた行は `state='failed'` で取り込み対象に居座るので**以後の取り込みが毎回失敗する。画面から消す手段が無い**。実機で 70D のカードを抜いて PC で古い写真を消し、挿し直して踏んだ（1488 件のうち実体は 68 件だった） |
| **消す前に 1 件ずつ開いて「無い」を確かめる** | 列挙に現れないことと、カードから消えたことは別。`scan.extensions` を狭めれば実在するファイルの行も列挙から外れるので、そこで消すと広げ直すまで取り込めたはずのものが黙って消える。**「無い」には観測を要求する**（§9.11 の削除規則と同じ原則） |
| **外すのは取り込み対象の行だけ。`published` と、`artifact_staging` が指している行は残す** | `published` は「このカードから取り込んだ」という記録で、スタッキングの「同じカード」判定（§9.11）と `_known_files_survive` の標本が引く。staging が指す行は `ON DELETE RESTRICT` なので、消しに行くとスキャンごと `IntegrityError` で落ちる |
| **`observed_at < スキャン開始` は候補の絞りであって守りではない** | 今回触れた行はカードに実在するので、絞りが無くても `probe_beneath` が残す。開き直す回数が減るだけ。**ただし検出はできる** —— 絞りを外すと候補が増え、掃除中の心拍の回数を厳密に見ている 2 本（`test_the_lease_is_kept_alive_while_scanning` / `..._while_sweeping`）が落ちる |
| **削除の判断は「無い」と「確かめられなかった」を分ける**（`probe_beneath`） | `exists_beneath` は全 `OSError` を False にする。加えて `iter_media_files` の `_walk` は**開けないディレクトリを黙って飛ばす**ので、一時的な `EACCES` / `EIO` で部分木ぶんが列挙から落ち、そのまま掃除の候補になる。区別しないと**「存在を確かめてから消す」が成立していない**（codex のレビューで発見） |
| **確かめられなかった件数は警告としてジョブに残す** | 黙って残すと、次の取り込みがその行で失敗したときに理由がどこにも無い。起動時の回収が無言だった不具合（実機の 2 番）と同じ形 |
| **キャンセルは掃除の直前でも見る** | `ctx.cancelled()` を列挙の中だけで見ると、一致するファイルが 0 件のカードでは 1 度も評価されず、降りたスキャンがそのまま掃除する。**掃除は破壊的なので、`mark_scanned` より厳しく見る**（codex のレビューで発見） |
| **派生物の mtime は `captured_at` の瞬間そのまま**（`_recording_end_ns`） | 取り込みの mtime も真の瞬間なので（下の「mtime は真の瞬間」）、ここで UTC と読み替えると `library/` と `derived/` で epoch が 9 時間ずれる。接尾辞の壁時計は、両方を同じ TZ で描画することでそろえる。オフセットの無い値はシステムの TZ で読まれてしまうので UTC と見なす |

## 撮影日時（`captured_at`）の算出と再計算

`captured_at` はプロファイルの版に紐づく算出値で、後から設定を直したときに再計算できる。
**「取り込みに使った版」と「値を算出した版」を分ける**ことが、この機能の全ての前提になる。

| 判断 | 理由 |
| --- | --- |
| **`captured_at` を算出した版を、取り込みに使った版から分ける**（`media_file.captured_at_revision_id`、`0011`） | `profile_revision_id` は「そのレコードが使用した不変の版」という既存の契約。再計算で値だけ新しくすると旧版を指しながら中身は新版由来という嘘の行ができ、版ごと進めると timestamp 以外の新定義（`scan` / `merge` / `immich`）も適用したと偽る（レビューで見つかった） |
| **その 2 列の関係は trigger 2 本で守る**（NOT NULL と「同じプロファイルの版」） | `ALTER TABLE` では複合 FK も NOT NULL も後から足せない。`media_file` は `upload_record` / `artifact_staging` / `merge_member` から参照されているので、**移行の失敗が最も高くつく表**で rebuild する利は無い。`profile_revision` の `UNIQUE (profile_id, id)` に突き合わせれば同じ強さが作れる |
| **再計算の入力は role ごとに違う。`original` を全部直してから `derived` を直す** | `media_file` だけでは再計算できない。`filename` はカード上の原名（`source_entry.rel_path`）に当てる —— `media_file.rel_path` は衝突接尾辞つきの公開名。`derived` は算出ではなく先頭 active member からの継承（`Merger._captured_of`）なので、順序が要る（レビューで見つかった） |
| **`source_entry` が残っていない `original` は再計算せず、件数と理由を出す** | カードを再フォーマットすれば原名は消える。**勝手に mtime へ落とすと、正しかった値を壊す** |
| **supersede した結合の出力は再導出しない。継承元は排他区間の中で解決する** | active な member が無い出力に新しい値を書くと、退役したものを更新することになる。読み出した後・書き込む前に API 側の別接続で結合をやり直せるので、読んだときの member を持ち回ってはいけない |
| **継承元がこの版で再計算できていなければ、派生物も飛ばす** | 先頭 member が `source_entry` 欠落で飛ばされていると、値は旧版由来なのに新版で算出したと記録することになる |
| **`recompute` は Immich に触らない。値が変わった送信済みは `needs_recheck` へ戻す** | `awaiting_datetime_approval` は `tagging` からしか入れず（`Uploader` の CAS）、承認画面が出す「現在値」は承認待ちにするその瞬間の観測。ローカルのジョブには埋められないし、クライアントを持たせると送信側が固めた契約を丸ごと持ち込むことになる。`needs_recheck` なら既存のパイプラインがリースと preflight の下で再実行する |
| **戻すのは `immich.fix_datetime_after_upload` が真のプロファイルだけ。CAS は `state = 'complete'`** | 偽なら、こちらがリモートの日時を書いたことが無いので差は生じない。戻すと何も変わらない再送を全件に強いる。CAS を外すと進行中のレコードを横から動かす |
| **差し戻しは `media_file` の更新と同じトランザクション** | 割ると「値は新しいのに `complete` のまま」が残る |
| **再計算の対象は `batch_size` ごとに keyset で読む（鍵は `rel_path`）。読み出しもリースとキャンセルの内側** | 全件を先に materialize すると、`media_file` 1 行ごとの相関副問い合わせが**最初の `assert_lease` より前に**リース窓を超えうる。`rel_path` は UNIQUE で、再計算はその列を動かさないので巡回中に行が前後しない。索引は `0012` と `0013` |
| **器が申告した時刻は解釈せず、生の文字列のまま `media_file.container_wall` に持つ** | 意味（`container_semantics`）はプロファイルが宣言するので、**読み違えていても再計算で直せる**。取り込み時に解釈して捨てると、直すには元ファイルを probe し直すしかなくなる（カードはもう無いかもしれない）。`recompute` が ffprobe を呼ばずに済むのもこのため |
| **器の意味も、mtime と同じく「媒体の性質であって値の形からは見分けられない」** | `Z` が付いていることは UTC である証拠にならない（Canon が実例）。**形から素性を推定する誤りは、この案件で繰り返し出ている** |
| **QuickTime の epoch（`1904-01-01T00:00:00`）は「書かれていない」と同義に扱う** | 器の時刻欄が未設定のときにこの値が出る。真に受けると 1904 年の写真が一覧の末尾に溜まる |
| **`recompute` はビルトインでも受ける** | 編集はできないが、`DEFAULT_TIMEZONE` を後から設定した場合に既存レコードを直す手段がこれしかない（§12.2） |

## 分割動画の結合

カメラが 4GB で切った断片を `-c copy` で継ぐ。**ffmpeg の挙動は入力ごとに違う**ので、
map の作り方・経路の選択・検証の条件はすべて実物のストリーム構成から決める。

| 判断 | 理由 |
| --- | --- |
| **検出は「アクティブな member」を境界として扱う** | 列から取り除くだけだと、その前後がつながって別の録画を 1 つのグループにする。写真も候補の列に入れない（duration を持たないので境界として働き、前後の分割録画が検出されなくなる） |
| **map はパートごとに、そのパート自身の ffprobe 結果から作る** | 保持 signature が同じでも、保持しない data track の挿入位置が違えば絶対 index は変わる。先頭の index を使い回すと、**同じ codec の別トラックを失敗せずに黙って拾う** |
| **concat demuxer は preflight してから使う** | demuxer は最初のファイルの構成を全体に適用する。全ストリームの構成と保持対象の index の並びが一致しないときは、試さずに TS へ送る |
| **TS 経路は mpegts が運べないストリームを外して記録する** | `mpegts` は QuickTime の data track（`tmcd` / `djmd`）を運べない。map に残すと mux が拒否して**検証できる出力そのものができない**（既定の DJI プロファイルは `timecode: true` なので fallback が常に使えなくなる） |
| **TS 経路の音声は「実測で運べたものだけ」の許可リストで見る**（いまは `aac` のみ） | `mpegts` は運べない音声を**運べないのに拒まない** —— private data として詰め、警告だけ出して **exit 0** で終わる。読み直すと `bin_data` になっていて音声が消えている。「運べないストリームを外す」（既存の規則）は data track のための軸で、音声には効かない。**拒否リストにすると codec を 1 つずつ潰す形になり、次の codec でまた同じ穴が開く** —— 実測: `pcm_s16le` / `pcm_s24le` / `alac` / `vorbis` / `flac` / `amr_nb` が化け、`aac` / `mp3` / `ac3` / `eac3` / `opus` は残る。TS 経路は**あくまで fallback** なので、許可リストで断る方が「音を黙って捨てる」より正しい。**判定は `codec_type == 'audio'` に限る** —— data は `UNSUPPORTED_BY_TS` が別の軸で見ているので、二重に効かせると data track を持つ機種の経路が壊れる |
| **concat demuxer も「読めたところまでで正常終了する」** | 欠けたパートがあっても **exit 0** で、読めた分だけに切り詰めた出力を作る（ログには `Impossible to open` と `Error during demuxing` が出るのに終了コードは 0）。**この案件は「終了ステータスで判定する」と決めているが、その終了ステータス自体が嘘をつく場合がある** |
| **`canon-eos` の出力の器は `.MOV`（QuickTime）のまま** | 音声が `pcm_s16le` なので、MP4 では ffmpeg の版によって弾かれる（`ipcm` を持つのは新しい版だけ。配るイメージの bookworm は 5.1） |
| **TS 片のストリームの並びは種別順に揃える**（実装で判明） | `concat:` は mpegts の生バイトを継ぐので、パートごとに並びが違うと後続のパートを読めない（`No start code is found`）。map に使う index はそのパート自身のものにしたまま、並べる順だけを揃える |
| **空き容量は TS 経路のピーク（入力合計の 2 倍）で見積もる** | `.ts` の中間物と出力が同時に `work/` に置かれる。入力合計だけだと、始めた後の出力生成で ENOSPC になる |
| **期待サイズは `bit_rate` が取れた保持ストリームだけで組み立てる** | `tmcd` は `bit_rate` を持たない。それを理由に全体を `inconclusive` にすると、**既定のプロファイルでサイズ検査が常に無効**になる。ばらつきも合計ではなく対応するストリームごとに見る |
| **サイズ検査の許容誤差 2% は実機の大きさが前提**（実装で判明） | コンテナのオーバーヘッドは 16 GiB では 0.002% だが、数百 KB の合成クリップでは 7〜8% になる。lavfi のクリップで組んだ e2e は必ずサイズ検査に落ちるので、採用（`adopt`）まで通す形にしてある |
| **検証器の版は `verification_json.pipeline_version`。`input_digest` には入れない** | `input_digest` は §8 で入力の同一性の判定と定義されている。混ぜると、閾値を 1 つ変えただけで既存の結合物がそろって選択肢から消え、再結合するまで戻らない。**codex の指摘を退けた 1 件**（先方も受け入れた） |
| **検証結果は公開の前に commit する** | 公開の途中で落ちても検証をやり直さない。`merging` のまま残ったグループは起動時に決着させる |
| **`merging` のまま残ったグループは、出力の有無で merged / detected へ倒す** | 倒さないと再試行もできない。`_recover_staging` の後に走らせる（そこで公開が完遂して `output_media_file_id` が入る）。**回収できない `artifact_staging` を抱えたグループは動かさない**（再試行させると、古い staged 行と新しい公開が同じグループを指す） |
| **`record_verification` と `mark_merged` は成立条件を DB 側で確かめる** | 呼び出し順のバグ 1 つで「merged なのに出力が無い」行ができ、選択肢の側が隠すので静かに残る |
| **選択肢は `input_digest` を現行の構成から計算し直して照合する** | 見ないと、グループを編集した後に旧派生物が選択肢へ戻る（旧グループは `status = merged` のまま残るため）。member は 1 回の query でまとめて引く |
| **公開済みの結合の破棄と再結合は、手動編集の画面と一緒に入れる** | どちらも公開済みの `media_file` を取り残す。旧グループを `superseded_by_id` で向け直す仕組みが要り、それは手動編集と共通 |
| **結合の編集を拒むのは「これから送られる根拠」になっているときだけ** | `complete` まで拒むと、一度送ったグループが永久に直せず、破棄と再結合の目的が果たせない |
| **supersede は 1 トランザクション。無効化 → 向け直し → 新しい member の順** | 割れると `input_digest` の部分索引が一時的に 2 行を許す。1 つのファイルが active な member でいられるのは 1 グループだけなので、順序も決まる。trigger が旧 member を `active = 0` にするので、**無効化を後にすると 1 件も当たらない** |
| **つなぐ組は 2 件以上。組み直しにも同じ条件を課す** | 1 件だけの組にはつなぎ目が無く、画面は「なぜ同じ 1 本と判断したか」を書けない（`gapSeconds`）。作成（`POST /merge-groups`）は 2 件以上を要求していたが**組み直し（`?action=regroup`）は非空しか見ていなかった**ので、構成を変えるダイアログでチェックを 1 つまで外すと、つなぎようのない組が一覧に残せた |
| **検証に落ちた結合物は、それ自体が「やること」** | 送る候補には出ず（`SENDABLE_CLAUSE`）、構成ファイルも active な member なので出ない。どの数にも入らないと、**ホームが「やることはありません」と書く一方で、つなぐ画面には「中身を見て、これを使う」が出ている**状態になる。数える条件は画面の `adoptable` と揃える（merged / 未 supersede / 未採用 / 出力あり / 検証が合格でない） |
| **件数の集計も、グループのプロファイルリビジョンが現行かを見る** | `input_digest` はリビジョンを含むので、カメラの種類を保存して版が上がると `POST /uploads` はその派生物を必ず断る（`group_is_current`）。`SENDABLE_CLAUSE` は digest を計算できないが**リビジョンなら SQL で見える** —— 見ないと、ホームの「N 件をまだ送っていません」が押しても全件 rejected で、数が永久に減らない |

## Immich への送信 —— 宛先の版と、送る手前の確認

宛先は編集できるので、**キューに積んだときの宛先と、いま送ろうとしている宛先は違いうる**。
版（`destination_revision` / `target_epoch`）で固定し、外部へ触る直前にもう一度確かめる。

| 判断 | 理由 |
| --- | --- |
| **宛先の版（`destination_revision` / `target_epoch`）を固定する** | 可変の宛先行に履歴を直結すると、キュー投入後に API キーを編集したとき**確認画面で示した宛先と違う先へ送られる** |
| **リビジョンを変えると `target_epoch` が上がり、旧 epoch の未完了レコードは*同じトランザクションで*無効化する** | 別トランザクションにすると、その隙間で claim された記録が旧 epoch のまま送られる。無効化した件数は `RevisionOutcome` で返して API がそのまま利用者へ見せる |
| **claim は宛先の現行リビジョンを同じトランザクションで解決する** | 先に読むと、claim までの間に編集されたリビジョンで送ることになる。ジョブは claim したリビジョンで送り切る |
| **`create_pairs` は宛先の現行リビジョンを INSERT と同じトランザクションで読む** | 外で読むと、読んだ後・書く前に他の書き手が epoch を進めて旧 epoch の無効化まで済ませられる。すり抜けた行は `claim_next` が拾わないので、次の起動の掃除まで理由の無い `pending` で残る |
| **送信前に `/api/users/me` で向き先を再確認する** | 宛先を編集しなくても DNS・プロキシ・Immich 本体の差し替えで同じ URL の先が変わる |
| **preflight は成功を 15 分だけ憶え、失敗はリビジョンが変わるまで憶える** | 向き先が違うまま試し続けると、**間違った Immich に少しずつ資産が積み上がる**。直し方は「宛先を編集する」＝リビジョンを変えることなので、そこまで憶える |
| **URL の検証は接続の検証より先** | 逆にすると `javascript:` のような値でもまず接続を試し、400 ではなく 502 を返す |
| **リースの確認は preflight より先** | preflight の `GET /api/users/me` も鍵を付けた要求で、キャンセル済みのジョブから出してよいものではない。再確認は「別のライブラリへ書かない」ための guard なので、送信の直前である限り順序を入れ替えても意味は変わらない |
| **リモートに触る手前は `prepare_side_effect`（`assert_lease` + 厳密な CAS）を 1 トランザクションで通す** | `assert_lease` は `cancelling` を拒むが `extend_lease` は拒まない。心拍だけを頼りにすると、**キャンセル要求の後にアップロードを始めうる** |
| **guard は prepare → preflight → prepare の 2 段** | 向き先の再確認は相手待ちで、リース（60 秒）より長くなりうる。前だけに置くと「直前に確かめた」保証が消え、確認している間に commit されたキャンセルを見落とす |
| **2 段 guard は後段も同じ強さで確かめる** | 後段だけ根拠（§10）の見直しを落とすと、相手を待っている間に結合をやり直されたとき、いま結合中のグループの構成ファイルを送る。**「直前に確かめた」保証が消えるのはキャンセルだけではない** |
| **最初の 1 バイトを送る直前に、§10 の根拠をリース・claim と同じトランザクションで見直す**（`verify_eligibility`） | claim 直後の判定はその時点の状態でしかない。判定から送信までの間に利用者が結合をやり直すと、**いま結合中のグループの構成ファイルを送ってしまう**。資産が既にリモートにある後（タグ・日時）は、見送っても取り消せないので見直さない |
| **既存資産へのタグ付けの前にも §10 を見直す** | 「もうリモートにあるので見送っても取り消せない」は、**こちらが作った資産にしか当てはまらない**。他人が上げた資産へのタグ付けは、こちらが起こす最初の変更 |
| **同じリモートを指す 2 つ目の宛先は、送信せずに既存資産を引き受ける** | チェックサムが一致するので送る意味が無い。ただし自作と証明できないので、日時の補正は承認待ちになる |
| **未送信は『押せば送れるもの』にする。`pending` を含めない** | `pending` まで未送信に数えると、送信中の宛先で「進行中」と「未送信」が同時に大きな数を示し、画面の 2 つのバッジが矛盾する。加えて `pending` は既にキューに入っているので、押しても §10 の claim が競合として拒否する |

## Immich への送信 —— 状態機械・origin・タグ・日時

`origin` は「この資産を作ったのが我々か」の記録で、タグと日時の扱いを分ける。**リモートの
成否が不明なまま `failed` にしない**、**観測した値そのものを条件に書く**が状態遷移の芯。

| 判断 | 理由 |
| --- | --- |
| **送信は宛先ごとに 1 本のジョブで、1 件ずつ直列に処理する** | 律速はネットワークと Immich 側の取り込みで、同時本数を増やしても増えるのは失敗の同時多発だけ。接続をスコープごとに 1 本に保つ約束も崩れる。直列ならキャンセルの観測点も「次の 1 件に入る前」で足りる |
| **`selection_rule` は不変。再試行で上書きしない** | 上書きすると選択の根拠が失われ、claim が安全条件しか見なくなって古い派生物を送る |
| **キャンセルで送信が途切れたら `needs_recheck` に落とす。`failed` にしない** | サーバ側の成否が不明なまま失敗にすると、次に「未送信」として上げ直して重複する |
| **`refuse` は所有を落とすと同時に `state` を `pending` に戻す** | 進行中の状態のまま所有だけ外すと、`upload_record` の CHECK（進行中の状態は所有者を持つ）に触れる |
| **一度確定した `created_by_us` は降格させない** | 後処理の一時障害（503）で再開したとき、自分が上げた資産は当然 `reject` で返る。付け直すと `unknown` になり、タグと日時の扱いが「他人が上げたもの」に変わる（タグが付かず、日時が承認待ちになる） |
| **`duplicate` で返った資産は他人のものかもしれない** | 初回が `accept` でも応答が `duplicate` なら自作の証明は無い（`origin` は `unknown`）。こちらはまだ何も変えていないので、タグ付けが最初の変更になる。その前に §10 を見直す |
| **`origin` が `created_by_us` でなければ日時の補正は承認待ち** | 別経路で上がっていて、ユーザが手で直しているかもしれない |
| **承認はジョブとして実行し、却下は同期で済ませる** | 承認はリモートの日時を書き換える。リースとキャンセルの下で行い、途中で落ちても決着させる。却下はリモートに触らないので待たせる必要が無い。同じレコードの承認が実行待ちなら 409 で断る（積めると 1 本目の後の残りが軒並み失敗として並ぶ） |
| **既に無効化された行の理由と時刻は上書きしない** | claim を持っている間に別の経路で無効化されることがある。上書きすると、監査で見えるのが二次的な文言に変わる |
| **照合の結果は、照合したときの行にしか書かない** | `complete` は終端ではない。消滅と判定された行は requeue でき、送り直しが済めばまた `complete` に戻る。id と現在の状態だけを条件にすると、新しい `remote_asset_id` を古い観測（消滅＝NULL）で消す。観測した値そのものを条件に入れ、動いた行は書かずに飛ばして**「確認した」とも数えない** |
| **再確認は batch ごとにキャンセルとリースの両方を見る** | 最初の batch も飛ばさない（preflight は相手待ちで、その間にキャンセルが commit されうる）。`cancelled()` はジョブの状態しか見ないので、`running` のままリースだけ失効した worker が残りの batch を送り続ける |
| **再確認もリモートへ触る前にリースを見て、待っている間は心拍を打つ** | 最初のリモート要求は preflight の `GET /api/users/me` で、`cancelled()` はジョブの状態しか見ないから、`running` のままリースだけ失効した worker を止められない。さらに `assert_lease` は見るだけで延ばさないので、**心拍が無いと 60 秒を超える正常な再確認が必ずリース切れになり、`JobRunner` が failed として記録する** |
| **再確認の結果は 1 つのトランザクションで書き、分割も `Rechecker` 側で行う** | 1 行ずつ commit すると、途中でキャンセルやリースの失効が起きたときに中途半端な状態が残る。`cancelled()` はジョブの状態しか見ないので `assert_lease()` が要る。adapter に全件を渡すと、内部ループの合間にキャンセルを見られない |

## RAW/JPEG のスタッキング

送信済みの資産どうしを Immich 側で束ねる第 2 パス。`complete` のレコードは claim を持たない
ので、**送信本体の guard をそのまま流用できない**ことがこの機能の制約を決めている。

| 判断 | 理由 |
| --- | --- |
| **スタックは `upload_record` の 3 列で持つ**（`stack_state` / `remote_stack_id` / `stack_reason`） | スタックの成否は「その宛先へその資産を送った結果」そのもので、`remote_asset_id` と同じ層。別表にすると無効化・再送・`target_epoch` との整合を二重に守ることになる |
| **抽出は現行 `target_epoch` の、`complete` かつ未評価の行だけ。組めない場合も見送りとして決着させる** | 未評価のまま残すと、送信のたびにライブラリ全体を舐める。決着は「今は組めない」の記録であって永久の拒否ではなく、後から相方が完了したときに相方の側から `stacked` へ更新される。**epoch で絞らないと、別ライブラリへ送った資産 ID を現行の資格情報で送る**（旧 epoch の `complete` は監査履歴として無効化されずに残る） |
| **組の規則は「取り込んだ版」ではなく、プロファイルの現行リビジョンから読む。組の全員に同じ `profile_id` を要求する** | スタックは取り込みの記録ではなく、いま適用する操作。`immich.tags` が現行リビジョンを見ているのと同じ層にある。取り込み時の版に固定すると、**版ごとに規則が違う member でどちらが先に走るかによって結果が変わり**、`stack` を持たない旧版で取り込んだ既存ライブラリは永久に対象外になる |
| **外部へ触る手前は、スタック専用の guard（リース + 組全員の厳密な照合 + **宛先の現行 epoch** + **プロファイルの現行版**）を `POST` と `PUT` の直前ごとに通す。記録は全員一致でなければ 1 行も書かない** | `complete` のレコードは claim を持たないので `prepare_side_effect` を流用できない。GET を何度か挟む間にリースは切れ、キャンセルは commit されうる。**epoch を進める編集は `complete` を無効化しない**ので、第 2 パスだけが既存の停止境界から外れる（開始後に別ライブラリへ向き替えられても、固定した旧リビジョンの preflight は成功する）。プロファイルの編集も同期 API で行える。一部だけ `stacked` になると、残りが別の組として再評価される |
| **相手待ちはすべて `with_lease_pulse` で囲む。ローカルの見送りもリースの下で書き、行をまたいだ heartbeat を打つ** | `UPLOAD_TIMEOUT_SECONDS` は既定 86400 秒なので、1 回の読み取りが 60 秒のリースを跨ぐのは正常。囲まないと、送信が成功した直後の記録でリースを失って正常なジョブが失敗になる。相手に触らない見送りも、数が多ければ同じことが起きる |
| **プロファイルの新しいリビジョンを作るトランザクションで、そのプロファイルのメディアの見送りを未評価へ戻す。戻すのは `stack` 節が変わったときだけ** | 「現行版を使う」は初回の評価だけでは成立しない。規則を有効にしても、拡張子や許容差を変えても、一度見送った行は二度と評価されない。一方、名前やタグだけの編集で全件を戻すと、相手側の事情で見送った行まで問い合わせ直すことになる |
| **見送りの記録も、成功の記録と同じ条件（リース・宛先の現行 epoch・プロファイルの現行版・`remote_asset_id`）で CAS する** | 相手に触らない見送りは guard を通らない。条件を緩めると、規則を読んだ後・書く前に版が進んだとき、**旧規則の判断が新しい版の世界に残って二度と評価されない** |
| **宛先の障害（接続不能・5xx・認証失敗・redirect）では第 2 パスを打ち切る** | 組ごとの失敗ではないので次の組へ進んでも同じ結果になる。未評価が N 件あれば、失効した鍵や停止したサーバへ N 組ぶんの要求を投げ続ける（timeout は既定 86400 秒） |
| **「既存スタックには触らない」は保証ではなく、窓を最小にした最善である** | Immich に条件付きの作成が無く、`POST /stacks` は無条件に吸収する。読み直しと `POST` の間の競合は実装では閉じられない。残余として明記し、`created_by_us` の組だけに限って影響を抑える |
| **組の同一性はカード上の原名で取る**（§6 の 3 条件） | 公開名は衝突時に改名される。ライブラリ側の stem で組むと、連番が一周した別カードのファイルと束ねうる |
| **撮影時刻を組の条件にしない**（`captured_at` の一致と `captured_at_source` の一致を両方外し、`stack.tolerance_seconds` を読むのをやめた） | 時刻は同じ 1 枚であることを**弱めこそすれ強めない**。実機で、カメラの時計が電池切れでリセットされたまま撮り、後から一括で日時を入れ直した束が出た —— この操作は JPG だけ書き換えて CR2 を元のまま残しうる（RAW に書き込める道具の方が少ない）。逆に時刻が揃っていても同席の証拠より弱い。**誤って組を拒む理由にしかならない**ので外した。パーサは既存リビジョンを開くために鍵だけ許し、値は読まない |
| **代わりに「同じ時点でカードに在ったこと」を要求する**（`source_entry.copresent_key`。スキャンが `<job_id>:<stem prefix>` を書き、判定は**鍵ごとに**一致を見る） | 鍵（カード + ディレクトリ + stem）だけでは、**片方だけ撮り直したとき**に古い published な行が相方として残る。同席は「1 回のシャッターで 2 つできた」の直接の証拠で、時刻と違って後から書き換わらない。集合へ潰さず鍵ごとに突き合わせるのは、別々の観測でそれぞれが一致するだけの組を通さないため。`NULL` は「同席していない」ではなく「**まだ確かめられていない**」なので、確かめられない相手として組まない |
| **同席の印を消す引き金は `media_file_id` が `NULL` に戻ること。`quick_fingerprint` の不一致ではない** | `quick_fingerprint` は size + 16 窓の**確率的なキャッシュ鍵**であって完全性検査ではない。これを引き金にすると、撮り直したのに指紋が一致したファイルの古い印が残る。取り込み直しになる（＝`media_file_id` が外れる）という**構造的な事実**で判定する |
| **印を消すのは、`media_file_id` が**もともと在った**行だけ**（更新前の値で判断する） | 取り込み待ちの `seen` の行でも消していたので、**完走しないスキャン**（末尾の同席の印付けに届かない）が組の片方だけ印を落とし、その組が二度と成立しなくなっていた。スキャンの中止は画面から普通にできる操作である。代償として、取り込み待ちの行では撮り直しの守りが 1 段弱い —— 残る筋書きは「片方が取り込み待ち・もう片方が取り込み済みで、取り込み済みの側がカードから消えた」場合だけで（完走したスキャンは印を書き直し、取り込み待ちの相方は掃除が外す）、**中断が組を永久に壊す方が重い** |
| **同じ拡張子の相方が 2 つ以上あるときは組まず、理由を画面に出す。送信は止めない** | `UNIQUE (volume_instance_id, rel_path)` があるので同じ原名は 1 つだが、拡張子は `{ext.upper()}` に正規化して突き合わせるため、case-sensitive な FS では `IMG_0001.JPG` と `IMG_0001.jpg` が並びうる（codex のレビューで到達可能だと確定した）。**どちらかを機械に選ばせない** —— `POST /stacks` は既存スタックを無条件に吸収するので、誤った組は戻しにくい。送信まで止めると、組めないだけで写真が Immich へ行かなくなる |
| **身元の規則は 1 つ、実装は 2 つ（`identity_partners` と SQL）。ずれたら不具合として扱い、突き合わせるテストを置く** | 一覧は行ごとに Python の判定を呼べない（組がページの境目をまたぐ）ので、同じ規則を SQL で書き直すしかない。**実際にずれた** —— SQL は曖昧さを同席グループ単位で数え、`identity_partners` は主の全観測にまたがって数えていたので、画面が Immich の作らない 3 枚組を宣言し、実在する RAW が一覧から消えた。資格（`origin`・`state`・資産 ID・プロファイル）は宛先を見る話なので第 2 パスだけが持つ |
| **規則の「読み方」が変わったときは、定義 JSON の比較では見送りを戻せない** | `_publish_revision` が見るのは**パース後の `StackRule`**。`stack.tolerance_seconds` のように「JSON には残るが読まなくなった」鍵は、旧版と新版が同じ値にパースされて差が出ない。**設計書は「自動で発火する」と書いていたが発火しなかった。** 一度きりの移行（`0025`）で戻す。`recompute_timestamps` の `captured_at` 由来の戻しは、時刻を条件から外した後は結果を変えない（見送りの理由がどれも `captured_at` を見ない）ので、救済には数えない |
| **`origin` は両方が `created_by_us` のときだけ** | `POST /stacks` は既存スタックを吸収する。タグ（追加のみ）より影響が大きく、`tag_pre_existing` に相乗りさせられない |
| **中断からの回収に新しい状態を作らない。回収の経路でも primary を検査する** | 未評価のまま残った行を、次の送信で「既存スタックのメンバー集合が我々の組と一致する」経路が拾う。§9.10 の `checking` が既存を照合するのと同じ形。`POST` の直後・`PUT` の前に落ちた場合、集合は一致するが primary は相手が選んだままなので、検査しないと望みの primary へ二度と直らない |
| **カード上の観測は順序で 1 つ選ばない。`(volume_instance_id, stem_prefix)` の鍵の集合が交わることを見て、member は `media_file_id` で一意化する** | `observed_at` は再スキャンのたびに更新されるので、「最初の観測」で選ぶと同じ組が実行のたびに変わりうる。**ボリュームと stem を別々の集合に平坦化すると**、別々の観測でそれぞれが一致するだけの組が通る。同じ資産が複数の観測で候補に入ると、2 回送って 2 回記録する |
| **`POST /stacks` は redirect を追わない（`allow_redirect=False`）。`PUT` は既定のまま** | `_request` は 303 でも method を変えずに同じ本文で再送する。`POST /stacks` は**非冪等で、既存スタックを吸収する** —— 自動の replay が安全でないのは、ストリームが EOF に達するからだけではない。`PUT /stacks/{id}` は冪等なので既存の JSON 本文の呼び出しと同じ扱いでよい |

| **グループ検出の差の下限は 0 ではなく `captured_at` の分解能** | 実機の DJI で、16 GiB × 5 パートの連続録画の継ぎ目が `+0.963 / +0.091 / **−0.909** / +0.877` になり、**1 か所の符号だけで 5 パートが 2 つに割れた**。`captured_at` はファイル名由来で秒までしか無いのに `duration` は小数なので、終端の推定は構造的に 1 秒ぶれる。**符号は丸めの結果でしかない。** 閾値（`tolerance_seconds`）を緩めるのではなく、誤差の下限を正しく置く。境界（ちょうど 1 分解能ぶんの重なり）は別グループのまま —— 秒に丸めた差は真の差から開区間 `(-1, +1)` ぶんしかずれないので、ちょうど 1 秒の重なりは丸めでは作れない。**粗い方の分解能**を採る（誤差は粗い方が支配する） |
| **取り込みの完了行に `skipped` と `failed` も出す** | 公開の件数だけだと、2 度目の取り込みが「何もしなかった」ように読める。件数は `ImportOutcome` にあるのに捨てていた。スキャンの完了行は「新規 N 件 / 取込済 M 件」と両方出しており、そちらに揃える。**出さなければ、スキップが効いていることを画面からもログからも確かめられない** |

| **`supersede` も「別グループが持っているファイル」を 409 で断る**（`create_manual` と対称） | 部分索引 `merge_member_one_active_group` に当たった `IntegrityError` を握っていなかったので、**2 つのグループを 1 つにまとめようとすると 500「内部エラー」**になっていた。§13 が「構成変更は新しいグループを作って旧を supersede」と決めている以上、**まとめる操作は必ずこの経路を通る**。実機で結合判定を直した後、既に 2 つに割れて検出されていたものを組み直そうとして踏んだ |

| **`merge_member.active` の写し元は「生きているグループ」**（`superseded_by_id IS NULL AND status <> 'skipped'`。`0017`） | `0003` では `superseded_by_id` だけの写しだったので、**破棄したグループがファイルを握ったまま**になり、再検出も `supersede` も `create_manual` も塞がっていた。**2 つのグループを 1 つにまとめる経路が実質存在しない。** 実機で、16 GiB 分割の 5 パートが 2 つに割れて検出され、組み直せずに詰まって分かった。**解放しても同じ構成が作り直されることはない** —— `save_detected` は同じ `input_digest` で `superseded_by_id IS NULL` の行があれば作らないので、破棄したグループ自身が番人になる。破棄は supersede と同じく不可逆にする（戻せると active と親の状態が乖離する） |
| **破棄したグループの member は、opt-in 無しで普通の選択肢に戻る** | 破棄は「このまとまりは無し」であって、ファイルを隠すことではない。`_MEMBERS_OF_UNMERGED`（`INCLUDE_FAILED_GROUP_MEMBERS`）が拾うのは `failed` だけになる —— そちらは再試行できるのでグループが生きている |
| **`discard` の無効化は `skipped` にする前に行う**（`supersede` と同じ） | `status` を立てた trigger が member を `active = 0` にするので、後だと「active な member」を条件にした無効化が 1 件も当たらない。**破棄したのに、その構成を根拠にした送信待ちが生き残る。** `0017` を入れた時点でこの順序が意味を持つようになった（テストが捕まえた） |

| **グループ一覧の既定は「いま操作できるもの」だけ。履歴は畳んで出す** | `list_groups` は全行を返しており、画面は `skipped` でもボタンを隠すだけで同じ形に描いていた。**破棄と組み直しのたびに操作できない行が増え、同じファイル名が繰り返し並ぶ。** 実機で 2 回破棄しただけで 3 つ並び、どれが生きているのか読めなくなった。`superseded` は定義上「置き換えられた構成」なので `status` を指定しても出さない。`skipped` は「なぜこの組み合わせを作らないか」の根拠として見たい場面があるので、消さずに `?status=skipped` と画面の折りたたみで残す |

| **concat demuxer には data ストリームを渡さない** | 実機の DJI は `tmcd` を持つので、`keep_streams.timecode` に従って `-map 0:4` を渡すと `Cannot map stream #0:4 - unsupported type` で**必ず**失敗し、毎回 TS 経路へ落ちていた（74.87 GiB で 14 分）。TS 経路も `tmcd` を落とすので、最初から選ばなければ失うものは無い。**TS 経路は `hvc1` を `hev1` に変える**（HEVC のパラメータセットの置き場所が変わる。Apple 系で再生できないことがある）ので、通らずに済むこと自体に価値がある |
| **経路が運べなかったストリームは「消えた」に数えない**（`_streams_check` が `route_dropped` を差し引く） | `size` 検査は差し引いていた（`excluded_streams`）のに `streams` 検査だけが差し引かず、**TS 経路を通ると必ず不合格**になっていた。ただし理由を言えるものだけ —— `route_dropped` に無いストリームが消えたら失敗のまま |
| **経路の判断は `job_event` に残す**（`on_note`） | どちらの経路を通ったかは「その出力がなぜその形なのか」の説明なので、ジョブの記録に属する。`logger.warning` だけだと `docker logs` を読むまで分からない（実機で実際にそうなった）。ログにも残すのは、ジョブの外から追う場合のため |
| **進捗は `job.progress_json` に上書きし、心拍と同じ 1 回の UPDATE に乗せる** | `job_event` に入れると監査の記録が心拍のたびに増える（16 GiB のコピー 1 本で数十行、1 時間の結合ならもっと）。進捗は「いまの値」だけあればよい。`extend_lease` は元から `lease_expires_at` を書いているので、**書き込みは増えない**。列は `0001` の時点から在って未使用だった |
| **速度と残り時間は画面で出す**（`started_at` からの平均） | サーバに持たせると、心拍の間隔に依存した値を永続化することになる。2 点の差分は state か ref が要り、React では**効果の中の setState（連鎖レンダー）も描画中の ref 参照も禁じ手**。開始からの平均なら状態を持たずに出せて、長い処理では値も落ち着く。`Date.now()` も描画中には呼べないので、取り直しと同じ拍で `now` を state に入れる |

| **`stream_signature` は欠けた値と `None` を同じに扱う** | ffprobe は持たない欄を落とし、`stream_summary` は `None` で埋める。`str(s.get(k, ""))` だと片方が `""`、もう片方が `"None"` になり、**経路が落としたものの差し引きが黙って効かなくなる**（実機の検証結果に `tmcd` が残っていて気づいた。**同じ辞書を両側に渡す試験では一致してしまう**） |
| **`streams` 検査は「足りない」と「増えた」で見る**（一致ではなく） | concat 経路は `tmcd` を `-map` しないが、**mp4 muxer がコンテナのメタデータから作り直す**（実機で確認）。運べなかったと記録したものが出力に在っても失敗ではない。逆に、期待に無いものが増えているのは選択が効いていない証拠なので失敗にする |
| **進捗は `finish_claimed` でも落とす** | 正常終了は `finish` ではなくこちらを通る（`runner.py`）。片方だけ落としても、**完了したジョブに「結合中 …」が残り続ける**（実機で気づいた） |

| **破棄の記録は消せる**（`DELETE /merge-groups/{id}`。`skipped` かつ結合結果を持たないものだけ） | 残す理由は `input_digest` の番人（同じ組み合わせを検出し直さない）だけで、**検出は利用者が押したときにしか走らない**。**忘れてよいと言われたものを、隠れて憶えておかない** —— digest だけ別テーブルに残す案は採らない。消したあと同じ組み合わせが再び出るのは消したのだから当然で、確認ダイアログにそう書く。結合結果を持つ記録は消せない（その派生物の出所が分からなくなる） |
| **`supersede` は旧グループを先に向け直してから新しい行を入れる**（`PRAGMA defer_foreign_keys`） | `UNIQUE(input_digest) WHERE superseded_by_id IS NULL` があるので、**構成を変えない組み直しは、新しい行を先に入れると必ず衝突する**。そしてそれが**やり直しの経路** —— 結合の実装を直しても `input_digest` は動かず（検証器の版を digest に入れる案は Phase 2 で退けた）、`merged` は再結合できず、破棄すると番人が再検出を止める。実機で結合を直した後、作り直せずに詰まった。まだ存在しない id を指すので、外部キーの検査を commit まで遅らせる |
| **やり直しは「同じ構成で新しい候補を作る」**（`merged` への再結合を許すのではなく） | 古い出力は古いグループに残るので**取り残されない**（§3 の「消さずに向け直す」と同じ形）。新しい状態遷移を足さずに済む |

## 並行性・リース・キャンセル

SQLite の上で、複数のスコープ（API・ジョブ・watcher）が同じ DB を触る。**行ロックが無い**
ことと、**リースは 60 秒しかない**ことが、あらゆる長い処理の書き方を決めている。

| 判断 | 理由 |
| --- | --- |
| **DB 接続はスコープごとに 1 本。同時共有しない** | トランザクションは接続に属していてスレッドには属さない。API の書き込みが publisher の `BEGIN IMMEDIATE` に混ざる。`check_same_thread=False` は必要（作るスレッドと使うスレッドが違う）だが、共有してよいという意味ではない |
| **SQLite に行ロックは無い。`BEGIN IMMEDIATE` + 条件付き UPDATE（CAS）で claim する** | `SELECT ... FOR UPDATE` は存在しない。`UNIQUE` は行の重複作成しか防げない |
| **claim 時に評価するのは「選べる場面」ではなく「その根拠が今も成立しているか」** | 「まだ採用していない derived」を条件にすると、採用して enqueue した瞬間に自分自身が条件を満たさず**必ず拒否される** |
| **リースの確認と `staged` への遷移を 1 つの `BEGIN IMMEDIATE` に入れる** | 分けると隙間にキャンセルが commit でき、「キャンセル済みと表示した後に公開される」経路が残る |
| **`publish_prepared` の SHA-1 走査中も heartbeat とキャンセル確認を続ける** | 30 GiB の走査はリース（60 秒）より長い。打たないと、読み切った後の手順 7 の `assert_lease` で失効し、**正しく生成・検証済みの結合物が捨てられる** |
| **staged より前の「中断できない長い処理」は `_with_lease_pulse` で囲む** | `os.fsync`（30 GiB の直後は数十秒）と ffprobe（timeout がリースと同値）は途中で止められず、chunk の合間の heartbeat では守れない。処理を別スレッドへ出し、待つ側が打つ（DB へ触るのは待つ側だけなので接続は 1 本のまま）。**取り込み側にも同じ穴があり（§7）、共通の `_publish` を直すことで両方に効く** |
| **`with_lease_pulse` は publisher から `core/lease_pulse.py` へ出した** | 中断できない長い処理はアップロードにもある（大きなファイルの送信）。公開と同じ仕掛けを両方から使う |
| **送信の進捗は、心拍の UPDATE に相乗りさせる**（`with_lease_pulse` の待つ側が `progress` 付きで打つ。`jobs/uploader.py` の `_Reported`） | 71.2 GB を 6 分、35 件を 2 分半かけている間、送信のジョブは進捗を一度も書いていなかった。動いているのか止まっているのかが画面に出ない。**書き込みを増やさずに出せる** —— 心拍は既に同じ `job` の行を定期的に UPDATE しているので、そこに `progress_json` を載せるだけで済む（進捗のために別の UPDATE を足すと、リースの延長を throttle した意味が薄れる）。送る本文のストリームは薄いラッパで包んで読んだ量を共有カウンタへ足すだけにし、**そのスレッドから DB には触らない**（接続はスコープごとに 1 本）。**形は取り込みと同じにする** —— 画面の `progressLine` もバーも既存のものがそのまま動き、速度と残り時間まで出る。合計は開始時のスナップショットなので走っている間に増減しうる。実測が追い越したら**合計のほうを実測に合わせて伸ばす**（`12 / 10 件` という嘘を画面に出さない） |
| **リースの延長は throttle し、キャンセル確認だけを細かく回す** | poll のたびに延ばすと 30 分の結合で数千回 WAL へ書き、API とキャンセルの書き込みロックに競合する |
| **リースを守る仕掛けは 2 つ要る**（1 件ごとの pulse と、行をまたいだ経過時間） | `with_lease_pulse` は処理が間隔より短く終わると 1 度も打たない。1 枚ずつが短くても 100 枚で積もる。**どちらも `assert_lease` を先に呼ぶ** —— `extend_lease` は `cancelling` でも延ばすので、heartbeat だけだとキャンセルを取りこぼす |
| **相手待ちはどこでも心拍で囲む。囲むのは待ちだけ** | `users/me` はクライアントの timeout（既定 86400 秒）まで待ちうるので、preflight もリースを跨ぐ。`PreflightCache.assert_target` の `wait` に `with_lease_pulse` を渡す（`Rechecker` / `Uploader` / `ApprovalService` の 3 つとも）。**クライアントの構築（資格情報の復号）は呼び出し側のスレッドに残す** —— DB へ触るのは待つ側だけ、という約束を崩さない |
| **キャンセルは例外で `JobRunner` まで上げない** | `_run_one` は例外をすべて `failed` にするので、利用者が押したキャンセルがジョブの失敗として記録される。ハンドラが受け止めて正常 return し、`finish_claimed` の `cancelling -> cancelled` に決着させる（取り込みも結合も同じ形で降りている） |
| **`LeaseLost` をジョブの外へ出さない** | `_run_one` が例外をすべて `failed` にするので、利用者が押したキャンセルがジョブの失敗として記録される |
| **停止は走っているジョブの完了を待つ** | `to_thread` のハンドラは task の cancel では止まらない。待たずに接続と dirfd を閉じると、コピー中のスレッドから見て資源が突然消える。timeout を付けて worker を cancel しても同じ |
| **`JobRunner.stop()` の cancel は自前の接続で書く**（`_request_cancel`） | `stop()` は cancel を `to_thread` へ逃がすので、待っている間にイベントループは `run_forever` を先へ進める。ジョブが同じ瞬間に終われば `run_forever` は降りて poller を閉じ、cancel の続きは閉じた接続の上に落ちる。**文の実行中に閉じられるとプロセスごと落ちる** —— CI #39 の pytest が `Fatal Python error: Segmentation fault`（exit 139）で死んだのはこれ。`close()` が文と文の間に入れば `ProgrammingError` で済むが、どちらになるかは競争で決まる |

## データモデルとマイグレーション

移行は前の版で作った DB を開けなくする力を持つので、**適用済みの版は不変**が最初の契約。
相手由来の値を後から締める移行は、値を見て選り分けず**版（cohort）で切る**。

| 判断 | 理由 |
| --- | --- |
| **適用済みの版のファイルは書き換えない。作り替えは新しい版を足す** | 書き換えると、前の版で作った DB は `MigrationError` で開けなくなる —— **移行が走る前に落ちるので、データを直す機会も無い**。`migrate.py` の checksum 照合はそのための契約であって、破ってよい警告ではない。`test_a_database_from_the_previous_release_still_opens` が版の checksum を凍結している（版を足したら、その一覧にも足す） |
| **既存 DB の観測値も移行で指紋へ変換する**（`0005`） | 変換しないと旧平文が残り、preflight が全宛先を「向き先が変わった」と誤判定する。`destination_revision` は不変なので、trigger を外して変換し作り直す。**SQLite に SHA-256 が無い**ので、runner が `mediaferry_fingerprint` を接続へ登録する |
| **変換済みかどうかは、形の推定ではなく値の接頭辞で見分ける**（`0005` / `sha256:`） | 指紋化を入れたアプリは新しい行を指紋で保存するが、移行が無ければ `schema_migration` は前の版のまま。**生値と指紋が混ざった DB が正規に作れる**ので、二重ハッシュを避ける必要がある。ただし「64 文字の 16 進なら指紋」と推定すると、**同じ形の API キーを相手が `users/me` の `id` に返していた DB で「もう指紋だ」と誤認し、鍵の平文がこの列と API 応答に残る**（この移行が塞ごうとしている脅威そのもの）。指紋であることを値自身に持たせ、接頭辞の無い値は中身が何であれ観測値として変換する |
| **保存済みの相手由来の識別子・観測は、値を見て選り分けずに cohort ごと落とす**（`0006` / `0007`） | 受け取る側の検査は新しく受け取る値にしか効かない。**形で選り分けると `test-api-key` のように unreserved だけでできた鍵が残る**し、SQLite の `length` と `GLOB` は埋め込み NUL で打ち切られるので NUL を挟んだ値もすり抜ける。SQL からは鍵を復号できないが、**版そのものが「検査を入れる前に書かれた行」という cohort を指せる**ので、値に関係なく一度外して再確認で戻す。`remote_asset_id` / `remote_checked_at` / `remote_is_trashed` は**まとめて**捨てる（片方だけ残すと「どの資産の、いつの観測か分からないゴミ箱状態」が一覧に出る。`complete` に `remote_checked_at` を残すと「リモートに存在しない」と同じ形になり、実際には在る資産を requeue で送り直せる）。`complete` は再確認で戻り、`awaiting_datetime_approval` は指す資産が無いので無効化する |
| **表を作り直す移行のために、runner に「FK を外す経路」を足す**（先頭行の目印 `-- mediaferry:foreign-keys-off`） | SQLite の `PRAGMA foreign_keys` は**トランザクションの中では黙って無視される**。runner は移行を 1 トランザクションで包むので、そのままでは `media_file` のように子 4 表から参照される表を作り直せない（`RENAME` が子の参照先を書き換えてしまう）。4 通り測って「トランザクションの外で立てる」しか無いと分かった —— **`defer_foreign_keys` も `legacy_alter_table` も代わりにならない**。**この穴は移行をスカッシュしても消えない**ので、runner の側に持つ |
| **`PRAGMA foreign_key_check` は COMMIT の前に走らせ、壊れていれば ROLLBACK する** | 後に置くと、壊れた DB でも版が `schema_migration` に記録される。次に起動したとき runner は「もう適用済み」と見て**黙って何もしない** —— 壊れたまま動き続ける。レビューが計画の欠陥として掘り当てた |
| **一覧の索引の tie-break は `rel_path`。`id` では並びに意味が出ない**（`0026`） | `id` は 32 桁の乱数 hex なので、同じ撮影日時の行の並びが実行ごとに変わりうる（実機で `MVI_0007` が `MVI_0008` より左上に来たのは id の出方がそうだっただけ）。`rel_path` は `TEXT NOT NULL UNIQUE` なので**単独で tie-break になる**。**索引と `ORDER BY` は同時に直す** —— 索引だけ張り替えると、タイの中の並びだけが一時 B-tree に落ちる（`role=derived` の経路で実測） |
| **「まだ送っていない」の集計は、2 列とも等値で当たる索引を置いて速くする**（`0019`。統計は取らない） | ダッシュボードは media 1 件ごとに「この宛先の有効な記録があるか」を尋ねる。条件は `media_file_id` と `destination_id` の 2 つの等値だが、既存の索引はそれぞれ 1 列ずつしか持たない —— **統計（`sqlite_stat1`）が無いと SQLite は `destination_id` の側を選び、media 1 件ごとにその宛先の全レコードを走査する**（実測: media 4,000 件で 1.3 秒、8,000 件で 5.6 秒。行数が倍になるたびに 4 倍）。2 列の部分索引を置くと統計の有無によらずこちらが選ばれる（同じ DB で 2.5 ms）。**`ANALYZE` では解決しない** —— 取り直せるのは起動時だけで、空の DB で取った統計（「どの表も 0 行」）が残ると、取り込みで行が増えたあとの選択が統計が無いときより悪くなる（結合の構成ファイルを引く問い合わせが走査に落ちるのを確認した） |

## Web UI と API

画面は「利用者が同意できる形」を作る側で、**同意の内容が作れないなら操作させない**。
API 側は、相手由来の値と内部の文言を利用者へ流さないための封筒を持つ。

| 判断 | 理由 |
| --- | --- |
| **API の失敗は `{code, detail, meta}` の封筒に統一する** | 画面は `code` を見て日本語を決める。`detail` をそのまま出す作りにすると、内部の文言や相手由来の値が利用者へ流れる |
| **SSE の再開 cursor は `job_event.id`（`seq` ではない）。初回は履歴を流さない** | `seq` はジョブ内の連番なのでジョブをまたげない。長く運用した後に新しいタブを開くだけで全件流れると、画面も回線も詰まる |
| **`BaseHTTPMiddleware` を使わない** | 応答を一旦受け止めてから流すので、終わらない応答（SSE）が相手に届かない |
| **SSE の資源は「終わり方を選ばずに」返す** | 相手が切れると Starlette は `aclose()` を呼ばずにタスクを取り消す。`StopAsyncIteration` だけ見ていると、8 回切れば `/events` が恒久的に 503 |
| **サムネイルは DB に入れず、位置と容量に上限を置く。キャッシュはアプリに 1 つ** | 再生成できるキャッシュであって派生物ではない。`at` を自由に受けると、1 本の長い動画で何千枚も作れてデータ領域を埋められる。要求ごとに作ると single-flight が効かない |
| **一覧の並びは `captured_at DESC, rel_path DESC`** | 同じ撮影日時の行があるので、tie-break が無いと実行計画が変わった日にページの境目で重複・欠落する。**tie-break は `rel_path`** —— `UNIQUE` なので単独で足り、`id` は乱数なので同じ撮影日時の並びに意味が出ない。`db/selection.py` の 3 つの断片も同じ並びで揃える（`limit` で切るので、順序が決まらないとどれが候補に入るかが実行ごとに変わる） |

| **リモートの日時と提案は、文字列ではなく瞬間で比べる** | Immich は日時を **UTC へ正規化して返す** —— `2026-08-26T12:33:05+09:00` で書いた値は `2026-08-26T03:33:05+00:00` で戻る。文字列の一致で見ると**同じ瞬間が常に「違う」**になるので、`identical`（＝「変更なし」）が **JST のカードでは一度も真にならない**。実機では、リセット後に送り直した資産が全部「日時を直しますか」の確認に並んだ（2026-08-28）。押しても同じ瞬間を書き直すだけなので壊れないが、**変わらないものを承認させていた**。**観測値は提案と同じオフセットへ直してから画面に返す** —— 画面は文字列から壁時計を切り出すだけなので（`formatDateTime`）、片方が UTC のままだと「変更なし」の横に 9 時間ずれた 2 つの時刻が並ぶ。**オフセットの無い値は比べも直しもしない** —— どの地の 14:30 か決まらないものに現地時刻を補うと、承認を黙って飛ばす方へ倒れる |
| **回収待ちの送信（`upload_record` の claim）があるときも、消さずに断る** | `upload_record.claim_job_id` も `job` を `ON DELETE RESTRICT` で掴む —— **`job` を消す手順 1 はどの段でも走るので、放置された claim が 1 行でもあれば 4 段すべてが内部エラーで落ちる。**中断した送信の claim は起動時の `release_interrupted` が外すまで残るので、これは実際に起こる。**`code` は 3 つ目を立てる**（`upload_claim_pending`）—— 待つものが「作業」でも「取り込み」でもなく「再起動」なので、既存の 2 つに混ぜると文面が嘘になる |
| **「取り込んだファイル」の段は、数えた印（`scanned_at` / `auto_scan_at`）も落とす** | ホームは `pending_count == 0` を「取り込むものは無い」と読むので、**数えた元（`source_entry`）を捨てたのに印を残すと、カードに元があるのに取り込む入口が消える**。根は「数えた結果が 0」と「数えた記録ごと捨てた」を区別できていないこと（Phase 7 の「候補が 0 件だと候補を作る画面へ入れない」と同じ型）。**両方落とす** —— `scanned_at` だけでは監視が数え直さず、`auto_scan_at` だけではホームが「取り込むものは無い」のまま。**抜けた接続の `auto_scan_at` は触らない**（履歴で、監視も拾わない）。**`auto_import_at` は落とさない** —— 数えるのは読むだけだが、取り込みは書く。捨てたばかりのファイルを断りなく書き戻さず、ホームの「取り込む」で利用者に選ばせる |

## セキュリティと秘密の扱い

脅威モデルは §14。**相手（Immich）は「こちらが読む値」を選べる**、**入口の防御は書き忘れ
うる場所に置かない**、**秘密はログにも例外にも応答にも出さない**が芯になる。

| 判断 | 理由 |
| --- | --- |
| **入口の防御は既定で全経路に掛ける**（ルータ単位の `dependencies`） | 状態を変える API は 20 本以上ある。ルータごとに書くと**次に足すルータで書き忘れる**。例外は `/health` と `/auth/*` だけ |
| **`Host` を信頼できる集合と突き合わせる**（IP と `localhost` は既定で通し、名前は許可制） | Origin と Host の一致は **DNS rebinding を防がない**（どちらも攻撃者のホスト名になる）。IP を直に打つのは利用者の正当な操作なので通し、名前だけを明示の許可制にする |
| **CSRF は二重送信 Cookie。セッションに紐付けない** | 認証を切っていても、罠サイトを開いたブラウザから `127.0.0.1` を叩ける。紐付けないので、認証の有無に関わらず同じ経路で効く |
| **`/auth/login` は CSRF だけ免除。Origin と Host の検証は掛ける** | 丸ごと例外にすると、罠サイトからログインを試行させられる |
| **セッションは指紋で保存し、パスワードが変わったら全部失効させる** | DB のバックアップが漏れても有効な Cookie を作れない。パスワードを変える理由はたいてい「漏れたから」 |
| **パスワードの世代は保存済みハッシュへの `verify` で判定する** | 起動のたびにハッシュし直すと salt が毎回変わり、同じ平文でも一致しないので**再起動のたびに全員ログアウトになる** |
| **認証は既定 off、`BIND_HOST` の既定も loopback のまま** | 利用者の判断（LAN 内で無設定で使えることを優先）。認証の追加が変えたのは「認証を入れれば公開してよい状態になる」ことだけ |
| **API キーは AEAD で暗号化。「封筒暗号化」とは呼ばない** | マスター鍵を `DATA_ROOT` の外（環境変数）に置けば DB/backup 単体の流出には効く。ただし credential ごとの DEK は挟まないので envelope ではない |
| **`ImmichClient` は redirect を追わない。本文を伴う要求では `allow_redirect=False`** | `x-api-key` はカスタムヘッダなので cross-origin の redirect でも剥がれず、**外部へ 301 を返す誤設定で鍵がそのまま渡る**。本文を伴う要求では、ファイルが 1 回目で EOF に達しているので追うと空の本文を送る |
| **例外にも応答にも API キーと相手の応答本文を入れない。本文由来の scalar も入れない** | 本文は相手が決める値で、送った鍵をそのまま返す実装がありうる。転送先の一覧はマスク値すら返さない。**相手は「こちらが読む値」を選べる** —— 侵害された Immich は受け取った `x-api-key` を `users/me` の `id` や `POST /api/assets` の `status` として返せる。それを引用した例外文は `job.error` とログへ入る |
| **`remote_user_id` は観測値ではなく指紋（SHA-256）を保存する** | 用途は「同じ向き先を指し続けているか」の等値比較だけ。生の値を保存すると、相手が鍵を echo したときに、`SecretBox` で暗号化したはずの鍵の平文の複製が DB の列・API 応答・例外文（`job.error` とログ）に現れる |
| **識別子は「許す形」を並べて検める（allowlist）。境界の両方向で通し、dot-segment は別に拒む** | `assetId` は `remote_asset_id` として保存され API 応答にも出る。タグの id は次の要求の URL に入る。**「正常な形」で鍵を返されると、例外文を綺麗にしただけでは平文が通る。** 拒む文字を並べる検査は fail-open で、`%74%65%73%74` のように符号化した鍵は「使えない文字」を 1 つも含まないのに httpx はそのまま path に載せ、可逆なので経路の先で平文へ戻る。RFC 3986 の unreserved だけを長さの上限付きで通す。**送る値も同じ検査を通す**（検査の無かった版が保存した行が DB に残っている）。**`.` と `..` は unreserved だが dot-segment** なので別に拒む（`/api/tags/../assets` は要求の組み立てで `/api/assets` へ畳まれる） |
| **出所は値自身の中身で決めない（接頭辞も形も）。信用できるのは版（cohort）だけ** | 相手が値を選べる場所では、`sha256:` のような印も攻撃者が発行できる（API キーを作るのは相手）。SQLite の `LIKE` は ASCII の大小文字を区別しないので `SHA256:` も同じ。区別が付かないなら、相手由来の列は捨てて再取得させる（`0007`。preflight は記録が無ければ閉じるので、宛先を保存し直せば新しいリビジョンに今の観測が入る） |

## テストの土台

テストの作り方そのものが設計判断になっているもの。

| 判断 | 理由 |
| --- | --- |
| **fake Immich はループバックで listen する実 HTTP サーバにする** | httpx 0.28 の `ASGITransport` は async 専用（`handle_request` を持たない）ので、同期の `httpx.Client` からは使えない。実物の httpx を通すことでプロトコルの取り違えも見逃さない |
| **E2E の土台は 2 枚差し。`DEFAULT_TIMEZONE` を env から外せる** | 1 枚だと「複数デバイスを独立に扱える」を受け入れの経路に載せられない。env に `DEFAULT_TIMEZONE` があると `locked` になり画面から変えられないので、再計算の筋書き（設定を変えてから直す）が通らない |
| **Python は 3.14 だけを名乗る（`requires-python = ">=3.14"` と `.python-version`）** | もとの `>=3.12` では版が決まらず、uv がその場に居る適合版を掴む。CI の ubuntu-latest では系の 3.12.3 が選ばれていて、配るイメージ（`python:3.14-slim`）**とは違う版でテストが通っていた**。配るものは 1 つのイメージなので、試していない版を名乗る意味が無い |

| **古くなった派生物だけは消せる**（`DELETE /media/{id}`） | 「孤立ファイルは削除しない」という方針の例外に見えるが、**対象が「もう誰も参照していない、我々が作った派生物」に限られる**ので、出所の分からない孤立ファイルとは性質が違う。やり直しの経路を足したことで、古い出力が残る場面が現実になった（実機で 74 GiB）。条件は 3 つとも満たすこと（`role = derived`／持ち主のグループがもう現行でない／送信の記録が指していない）。**DB を先に消し、実体は後で消す** —— 逆にすると途中で落ちたとき「レコードはあるのに実体が無い」になる。この順なら実体だけが残っても孤立として画面に出る |
| **消せる派生物は「構成」ではなく「ファイル」として画面に出す**（`GET /media/stale-derived`） | `list_groups` は `superseded_by_id` を持つ行を**どの場合も返さない**（置き換えられた構成を一覧に並べる意味が無い）。そのため削除ボタンをグループ行に置くと、**まさに片付けたい出力にだけ到達できない** —— 実機で 66 GiB がそこに残っていた（2026-08-21 に判明）。**一覧の条件は `delete_stale_derived` の前提と同じにする**（押しても 409 で断られるボタンを並べない。片方を変えたらもう片方も変える）。`list_groups` の除外はそのまま —— 出すのは構成ではなく、残っているファイル |
| **結合画面に「できたファイル」を出す** | `status = merged` だけでは何ができたのか分からず、ライブラリまで行くことになる。API は `output_media_file_id` を最初から返しており、**画面が落としていただけ**だった（「受け入れの経路に入っていない機能は、無いのと同じ」の別の形） |

## 意図的にやらないこと

「できるがやらない」と決めたもの。**得るもの無しに契約へ触る改造は入れない**、
**自動でデータを失う経路は作らない**という判断が根拠になっている。

| 判断 | 理由 |
| --- | --- |
| **ワーカーの多重化はやらない。`UPLOAD_CONCURRENCY` を撤去する** | §9.10 は当初から「送信は宛先ごとに 1 本、1 件ずつ直列」と決めており、多重化で増やせるのは失敗の同時多発だけ。設定だけが「効かないまま画面に並ぶ」状態だった。claim の契約（type も宛先も見ない単一 worker）と停止の契約に触る改造を、得るもの無しに入れない |
| **孤立ファイルは報告するだけ。削除しない** | 自動削除はデータを失う経路になる |
| **送信中に Immich の背景ジョブを止めない**（immich-go はやる） | immich-go は大量取り込みの間 `/api/jobs` でサムネイル生成・メタデータ抽出・機械学習を止め、終わったら再開する。**速度のためにやっていることだが、こちらでは速度が問題になっていない** —— 実機で 71.2 GB を **186 MB/秒・再試行 0 回**で送れた（2026-08-23）。一方で**壊れ方が重い**: (1) **相手のサーバの状態を、こちらの都合で変える**（この設計は「既存の資産に触らない」を通してきた）。(2) **失敗したときに戻せない** —— 送信の途中でこちらが落ちると**ジョブが止まったまま残り**、家族の写真のサムネイルが作られないまま誰も気づかない。**「送信の途中で落ちる」は同じ日に実際に踏んだ**（リースの不具合）。(3) **他の人も使っているサーバかもしれない**（スマホの自動バックアップまで止める）。必要になるのは「大量に送ると Immich が目に見えて重い」と実際に困ったときで、そのときは**設定で明示的に有効にする**（既定は off）形と、**ジョブの終わり方に関わらず必ず再開する仕組み**をセットで入れる |
| **自動経路の at-most-once だけを保証する** | 手動の `POST /volumes/{id}/import` は `auto_import_at` を見ないので、同じ presence に手動 1 本と自動 1 本が積まれることはある。import は冪等なので受け入れる。ジョブ全体の重複排除は `JobStore` の契約を変える話として切り離す |
