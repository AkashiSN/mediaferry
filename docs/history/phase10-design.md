# Phase 10 の設計 —— 送る前に「どれとどれが 1 枚か」を見せる（2026-08-25）

**実機で Canon EOS 70D の RAW+JPEG を取り込んだ利用者が見つけた症状から始まる。**
現在の仕様は [`../design.md`](../design.md)、そう決めた理由は
[`../decisions.md`](../decisions.md) にある。ここにあるのは**なぜこの形にしたか**で、
実装の手順は `phase10-plan.md`（これから書く）にある。

## 何を直すのか

利用者の言葉では 2 つ、実際には 3 つの症状がある。

| | 症状 | いま起きていること |
| --- | --- | --- |
| A | **写真タブで RAW がプレビューできない** | サムネイルは**真っ黒な絵を 200 で返している**。ffmpeg は CR2 を TIFF として開けてしまうので失敗せず、現像していないセンサ値をそのまま絵にする。`ThumbnailFailed` が飛ばないので、アプリから見ると成功。**暗い写真と区別が付かない** |
| B | **同じ 1 枚が 2 タイルに割れて並ぶ** | `GET /media` は `media_file` を平らに返すので、`IMG_8364.JPG` と `IMG_8364.CR2` が別々のタイルになる |
| C | **どれとどれが組になるかを、送る前に確かめられない** | スタックの判定は**送信後の第 2 パス**にしかない（`upload_record` の `stack_state`）。組めたか・なぜ組めなかったかは、送った後にしか分からない |

**A はこの設計に含めない。** B を直せば一覧からは見えなくなるが、**JPG を撮らずに
RAW だけで撮った場合は残る**し、`/photos/:id` でも黙って黒が出る。別の不具合として
直す（[範囲の外](#範囲の外)）。

## この設計が前提にすること

**利用者の言葉:**

> ローカルで確認できた事実を元に immich に送信してスタックするので、基本的に
> ここがズレることはありません。

**予測と事実を別物にしない。** 画面に出す組と、Immich で実際に作る組は、
**同じ関数が決める**。規約ではなく構造でそろえる。

## 1. 規則を「身元」と「資格」に割る

いまの `resolve_group`（`core/uploads/stacking.py`）は 2 種類の判断を混ぜている。

| | 問い | 何を見るか |
| --- | --- | --- |
| **身元** | この 2 つは同じ 1 枚か | カード上の事実だけ |
| **資格** | いまこの宛先へ組を作ってよいか | `upload_record`・宛先の epoch・プロファイルの版 |

混ざっているので、**送る前には何も言えない**（`Candidate` が `upload_record` を
要求する）。身元を独立した関数へ切り出し、**一覧と第 2 パスの両方がそれを呼ぶ**。

資格の条件（`origin = created_by_us`／`remote_asset_id` が揃って重複しない／
`state = complete`／`profile_id` が一致）は第 2 パスに残す。**画面はここを見ない** ——
送る前には決まらない値だからで、「送ったら必ずこう組まれる」ではなく
「**この 2 つは同じ 1 枚だ**」を見せる。

## 2. 身元から時刻を外す

いまの身元は 4 条件で、うち 2 つが時刻だった。

```
同じカード + 同じディレクトリ・同じ stem
  + captured_at が秒まで一致        ← 外す
  + captured_at_source が同じ       ← 外す
```

**外す理由は、偽陰性しか生んでいないから。**

- **`captured_at_source` の一致** —— `exifread` が JPG は読めて CR2 は読めないと、
  `exif` と `mtime` で食い違って組まない
- **`tolerance_seconds` 以内** —— **一括で日時を入れ直したとき、JPG だけ書き換わって
  CR2 が元のままだと組まない。** RAW に書ける道具の方が少ないので、これは起こりうる

実機の 70D のカードがちょうどこの隣にいた。**カメラの時計が電池切れでリセットされて
いるのに気づかず撮り、後から一括で日時を入れた**カードで、68 件すべての
`captured_at` が同じ秒（`2026-08-08T13:00:00`）になっていた。今回はたまたま CR2 側にも
同じ値が入ったので `exif` で揃ったが、**道具が JPG しか書き換えなければ 34 組すべてが
黙って組まれずに終わっていた**。

**偽陽性の側は、ファイル名の鍵が構造的に防ぐ。**

```sql
-- 0003_artifacts_and_merges.sql
UNIQUE (volume_instance_id, rel_path)
```

`source_entry` は「カード × カード上の原名」で一意なので、**1 つの鍵
（カード＋ディレクトリ＋stem）の下では各拡張子はたかだか 1 つ**。同じ拡張子が
2 つ並ぶことは起きない。「相方が 2 つ見つかったらどうするか」という分岐は
**到達しない**ので作らない（`development.md` の「検出できない変異は、検出できない
ことを記録に残す」と同じ扱い）。

## 3. 同席の証拠を、スキャンが書き残す

**2 だけでは足りない。** 2 が保証するのは**相方の数**（各拡張子はたかだか 1 つ）で
あって、**その相方が正しいこと**ではない。鍵が同じでも「同じ時点でカードに在った」
とは限らない。

```
スキャン 1  IMG_8364.JPG → media_file A
           IMG_8364.CR2 → media_file B      どちらも published

（カードを再フォーマット。今度は JPG だけで撮る）

スキャン 2  IMG_8364.JPG  中身が違う → 同じ行を UPDATE（media_file_id = NULL）
                          → 取り込んで media_file C
           IMG_8364.CR2  カードに無い → 行は published なので掃除も残す ← B のまま
```

鍵は同じなので、**C（新しい JPG）と B（無関係な古い RAW）が組む**。いまはここを
時刻が止めている。**時刻を外すだけだと、この不具合を新しく作ることになる。**

**組の両方が撮り直された場合は起きない**（どちらの行も UPDATE されて縁が切れる）。
**片方だけ**のときに残る。

### 決めたこと

**`source_entry` に「同席の印」を 1 列足す**（NULL 可の TEXT。列名は実装計画で
決める）。完走したスキャンが、1 つの鍵の下で
`stack.extensions` の拡張子を 2 つ以上見たときだけ、その行たちに同じ印
（そのスキャンの `job_id`）を書く。

```
身元 = 同じカード
     + 同じディレクトリ・同じ stem
     + 拡張子が stack.extensions にある
     + 同席の印が等しく、かつ空でない        ← 追加
```

**印は消えずに残る。** 一度同席が証明されれば、後でカードから消しても組は成立し
続ける。**送信は取り込みよりずっと後になりうる**ので、これが要る。

**行の中身が変わったときは印を消す。** 場所は既に `media_file_id = NULL` を書いて
いるところ（`_reconcile_entry` の UPDATE 経路）と同じ。無いと、上の例の新しい JPG が
**古い同席の印を持ち越す**。

**途中で降りたスキャンは印を書かない**（`mark_scanned` と `_sweep_vanished` と同じ
`counted` の条件）。見ていないだけの相方を「居なかった」と読むため。

### 採らなかった案

**「同じ取り込みジョブで運ばれたこと」を証拠にする。** 取り込みを途中で止めて
再開すると別のジョブになるので、**同じ組が運び方によって成立したりしなかったり
する**。同席はカード上の事実なので、そちらを採る。

**印を「最後に見たスキャン」にする**（等しさで比較）。カードから片方を消して
再スキャンすると、**同じ組なのに印がずれて組めなくなる**。「一度でも同席した」を
記録する必要がある。

## 4. 一覧は「畳む」のではなく「従を隠す」

組をサーバで束ねて返すと、`captured_at DESC, id DESC` で切っているページの境目を
**組がまたぐ**。そこで束ねず、**従（`stack.extensions` で後ろの拡張子）の行を一覧から
外す**。

```
GET /media?collapse=stack
  → IMG_8364.CR2 の行は返さない
  → IMG_8364.JPG の行に stack を付ける
```

```json
{
  "id": "...",
  "rel_path": "library/canon-eos/DCIM/100CANON/IMG_8364.JPG",
  "stack": {
    "members": [
      {"id": "...", "rel_path": "...IMG_8364.JPG", "size_bytes": 3622127},
      {"id": "...", "rel_path": "...IMG_8364.CR2", "size_bytes": 22847966}
    ]
  }
}
```

**1 行 = 1 タイルのままなので、ページングの意味が変わらない。** 組が境目をまたぐ
こともない（見えるのは常に主だけ）。**既定は `collapse` 無し**なので、他の呼び出し元
（ホームの「さっき取り込んだもの」、選んで送る画面）の契約はそのまま。

**主は `stack.extensions` の先頭側**（`canon-eos` なら JPG）。これは第 2 パスの
`members` の並び（`rule.extensions.index(...)` で整列）と同じ規則で、
**primary の選び方を 2 か所に書かない**。

## 5. タイルは `つないだ` の隣に `RAW`

```
┌──────────┐
│ IMG_8364  │   ← JPG の絵
│ [RAW]     │   ← madeof と同じ位置・同じ作り
└──────────┘
```

`MediaTile.tsx` の `media.role === "derived" && <span className="madeof">つないだ</span>`
と同じ形で、`media.stack` があれば `RAW` を出す。

**どのファイルと組んでいるかは、名前がそのまま答え** —— 同じ stem なので
`IMG_8364` と読めれば相方は `IMG_8364.CR2` である。押した先は今までどおり
**JPG 1 枚の `/photos/:id`**（選んで送る画面と詳細画面は畳まない。利用者の判断）。

## 6. 難所 —— 従かどうかを SQL で判定する

**`stack.extensions` の順序はプロファイルの現行版から読む**（`decisions.md`
「組の規則は取り込んだ版ではなく、プロファイルの現行リビジョンから読む」）。一覧は
複数のプロファイルをまたぐので、**順序は行ごとに違う**。

素直には書けない。手順はこうする。

1. 一覧に出うるプロファイルの**現行版の `stack` 規則を Python 側で読む**
2. `(profile_id, 拡張子, 順位)` の対応を **`VALUES` の並びとして SQL へ渡す**
3. 「同じ鍵に、自分より順位が小さい拡張子の兄弟が居る」行を `EXISTS` で外す

**`stack.enabled` が false のプロファイル（`dji-osmo`）は何も外さない。**

ここは実装計画で 1 タスクを充てる。**測ってから決める** —— Phase 9 で索引を入れ違えて
他経路が退行した前例がある（`phase9-record.md`）。

## 移行

**`StackRule` から `tolerance_seconds` を落とすと、定義 JSON が変わる。** ビルトインは
次の起動の `sync_builtins` が新しいリビジョンを作り、`_publish_revision` の

```python
if _stack_rule_of(previous_json) != _stack_rule_of(definition_json):
    # stack_state = 'skipped' の行を未評価へ戻す
```

が**自動で発火する**。実機にいまある `stack_skipped: 36` 件は、入れ替えた時点で
未評価へ戻り、次の送信で新しい規則で評価し直される。**`stacked` は戻らない**
（相手側に既にあるものを作り直さない）。

**同席の印は、既存の行には入らない。** 移行で埋めることはできない —— 過去に
同席したかどうかは記録に無いからで、**無いものを在ったことにしない**。既存の
ライブラリは**次にそのカードをスキャンしたときに印が付く**。カードがもう無い
ライブラリは組まれない。**これは意図した振る舞い**で、証拠の無い組を作るより良い。

## 範囲の外

**A（CR2 のサムネイルが真っ黒）はここに含めない。** 原因は分かっている
（ffmpeg が CR2 を開けてしまい、失敗しないので `ThumbnailFailed` が飛ばない）。
直し方は別に決める —— 少なくとも「黒い絵を返す」のをやめ、**プレビューを作れない
ことが分かる形**にする。

## 試験の方針

- **身元の関数は純粋関数**（DB も相手も触らない）。条件を 1 つずつ壊す変異試験を
  そのまま書ける。いまの `stacking.py` の作りを引き継ぐ
- **同席の印は、スキャンの試験で見る** —— 2 つ同時に見えたら印が付く／1 つしか
  見えなければ付かない／中身が変わったら消える／途中で降りたら書かない
- **一覧の従外しは、複数プロファイルが混ざった一覧で見る**（`dji-osmo` の行が
  外れないこと）
- **E2E を受け入れコマンドに入れる**（`phase8-record.md` の教訓。入れないと腐る）
