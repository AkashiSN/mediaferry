## 何を直した回か

**実機（Canon EOS 70D）でのテストが 4 つの欠陥を出した。** 4 つは別々に見えて、
根が 1 つある —— **動画の撮影時刻の出所が無かった**こと。

| # | 実機で見えたこと | 根 |
| --- | --- | --- |
| 1 | 動画の時刻が録画の**終了**時刻になる | EXIF が無いので `mtime` へ落ちていた。器（QuickTime の `format.tags.creation_time`）を読む出所が無い |
| 2 | 4GB 分割が結合されない | `canon-eos` の `merge` が無効。**加えて `min_part_size_gib: 4` が実測の片（3.9675 GiB）を 33.2 MiB 差で弾く** |
| 3 | Immich で**動画だけ 9 時間ずれる** | Canon は現地の壁時計に `Z` を付けて書き、Immich が素直に UTC と読む |
| 4 | 同じ撮影日時の並びが**乱数** | tie-break が `id DESC` で、`id` は 32 桁の乱数 hex |

1 を直すと 2 の分割検出も同時に成立する（器の時刻が録画の**開始**なので、片の
継ぎ目が読める）。3 は 1 の値をどう解釈するかの問題で、4 だけが独立している。

## 「終了コードが嘘をつく」 —— ffmpeg の 2 例

この案件は**外部コマンドを終了ステータスで判定する**と決めている。Phase 13 で、
**その終了ステータス自体が嘘をつく**例が 2 つ実測で見つかった。

1. **mpegts は PCM を運べないのに拒まない。** private data として詰め、警告だけ出して
   **exit 0** で終わる。読み直すと `bin_data` になっていて音声が消えている。
   既存の規則「TS 経路は mpegts が運べないストリームを外して記録する」は data track
   のための軸で、音声には効かない。**codec を軸にした別の門**（`pcm_*` があるときは
   TS へ落とさない）を足した（Task 9）
2. **concat demuxer は欠けたパートがあっても exit 0 を返す。** 読めたところまで
   （2 パート分）に切り詰めた出力を作る。ログには `Impossible to open` と
   `Error during demuxing` が出るのに終了コードは 0。**Task 9 のブリーフが
   「存在しないパートを混ぜて concat を失敗させる」筋書きを指定していたので実装者が踏み、
   レビュアーが独立に再現した** —— つまり**このタスクが塞ごうとしている「成功したふりを
   して黙って中身を落とす」形と、同じものが concat 側にも実在した**

## Task 12 —— 同じ罠に 3 回かかった

**「タイの中の並びは rowid の向きに引きずられる」**。この 1 つの事実に、1 つのタスクの中で
**3 回、別々の理由で**かかった。

1. **実装者が、偶然通るテストを書いた。** `/uploads/selectable` の並びのテストが、
   修正前のコードでも通った。`_ORIGINALS` に tie-break が無く、SQLite が rowid 降順
   （＝挿入の逆順）に近い順で返していたため、挿入順がたまたま期待値と一致していた。
   実装者は挿入順を逆にして落ちるようにし、その経緯をコメントに残した
2. **レビュアーが、その理由を取り違えた。** 上のコメントは「期待値と逆の順で入れる」と
   言っているのに、**コードは期待値と同じ順で挿入していた**。実際に変異を殺していたのは
   挿入順ではなく、`media_file_captured_at` が **ASC の索引で、`captured_at DESC` の
   ときに後ろ向きに走る**ことだった。レビュアーの実測: コメントを信じて挿入順を
   「逆に直す」と、tie-break を丸ごと消しても **5/5 で通る**
3. **統括が、ブリーフで対策を外した。** 「行数を 8 行に増やして全順序を断言すれば
   偶然一致は 1/40320 に落ちる」と書いたが、実装者がそのとおり作ると
   **変異が 20/20 で素通りした**。挿入順を名前の昇順にしていたので、後方索引スキャンの
   逆順が**偶然 `rel_path` 降順とぴったり一致し続けた** —— 行数をいくら増やしても
   この一致は崩れない。挿入順を `rel_path` とも `id` とも無関係な順列に変えて、
   初めて 20/20 の検出になった（再レビュアーが独立に再現）

**結論**: タイの中の並びを試すテストは、**行数でも id の固定でもなく、
「並びを決める可能性のあるすべての軸（rel_path / id / 挿入順）を互いに無関係にする」**
ことでしか確実にならない。

## 「変異を検出した」は 1 回当てただけでは言えない

Task 12 のレビュアーが、変異を**回数で**当てた（この案件で初）。結果、実装者が
「検出した」と申告した変異のうち **2 件が確率的**だった。

| 変異 | 実測 |
| --- | --- |
| `ORDER BY` を `id DESC` に戻す | **8 回中 7 回**しか落ちない（1/6 で素通り。全件走行でも素通りを再現） |
| `_DERIVED` の tie-break を消す | **12 回中 9 回**しか落ちない |

`_DERIVED` の並びは `input_digest` 順で、digest は member の乱数 `id` と**乱数の
`profile_revision_id`** から出る。**`digest` を固定すると `_matching_digests` が
一致しなくなって候補が 0 件になり、member の `id` を固定しても digest は揺れる**
（レビュアーが両方実測して否定）。

**「たまに落ちる」を flaky と誤診して quarantine すると、網がそのまま消える。**

## 計画の誤り 17 件 —— 4 つの型

12 タスク中 11 タスクで計画に誤りが見つかった（誤りが無かったのは Task 10 だけ）。
型は 4 つに分かれる。

| 型 | 例 |
| --- | --- |
| **(a) 存在しないヘルパ名・戻り値の型の誤り** | `_part` / `_rule`（実物は `a_part` / `a_rule`）、`recompute()`（実物は `run()`）、`captured()` は 2-tuple ではなく 7 列の `Row` を返す |
| **(b) 変異を殺せないテストデータ** | `["exif","container"]` は両端とも `mtime` でないので `source[-1]` → `source[0]` の変異を殺せない。実測の正の差（+0.572 秒）だけでは分解能の変異を殺せない（負の重なりにしか効かない）。`IMG_0007.JPG` は `^` の有無に関係なく `MVI_` に当たらないので錨を検証できない |
| **(c) 何も検証せずに通るテスト（vacuous）** | 素の `a_media_file` は `source_entry` を持たないので `_recomputed_original` が行ごと飛ばす —— **1 本目は正しい実装でも落ち、2 本目は何も検証せずに通る** |
| **(d) 手順どうしの食い違い** | Step 1 の payload に `fallback` があると `_reject_unknown` が先に弾いて、狙った検査に届かない |

**(b) と (c) は「テストが通ること」からは見えない。** 変異試験だけが見つけられる。

## 索引の数を 2 度数え違えた

設計の段階で「`id DESC` で終わる索引は 4 本」と書き、3 本に直し、最終的に **2 本**だった
（`media_file_listing` と `media_file_derived_listing`）。

- `0013` の `media_file_by_profile` は `(profile_id, role, rel_path)` なので対象外
- `0022` の `media_file_by_role` は **`0023` が既に DROP している**

**`sqlite_master` を実際に読んだのが正**で、移行ファイルを読み合わせた推測は 2 回とも
外れた。おかげで索引張り替え専用の移行（`0027`）が不要になり、`0026` 1 本で済んだ。

## 移行 runner に穴があった

`media_file` を作り直すには外部キーを外す必要があるが、**`PRAGMA foreign_keys` は
トランザクションの中では黙って無視される**。runner は移行を 1 トランザクションで包む。

4 通り測って、**「トランザクションの外で `PRAGMA foreign_keys = OFF` を立てる」しか
無い**と分かった —— `defer_foreign_keys` も `legacy_alter_table` も代わりにならない。
**この穴は移行をスカッシュしても消えない**ので、runner の側に持たせた
（先頭行の目印 `-- mediaferry:foreign-keys-off`）。

そして SQLite の 12 手順の `ALTER` は `foreign_key_check` を **COMMIT の前に**要求する。
計画は後に置いていて、**壊れた DB でも版が記録され、次回は「もう適用済み」として黙って
素通りする**形だった。レビューが 1 巡目で掘り当てた。

| 経路 | 出荷形（`rel_path DESC`） | 実験用（`id DESC`） |
| --- | --- | --- |
| `GET /media?page_size=50` | 1.887 ms | 1.969 ms |
| `GET /media?collapse=stack` | 20.638 ms | 20.570 ms |
| `GET /media?stack=members` | 2.396 ms | 2.426 ms |

## ブランチ全体の最終レビューが、タスクの境目で Critical を 1 件掘り当てた

12 のタスクは 12 人の別々の実装者が、それぞれ自分のタスクだけを見て書いた。個別のレビューは
どれもクリーンだったが、**全体を 1 本のレビューに通したら、タスクの境目に穴があった。**

**C1: 既存 DB のまま新版を起動すると、クラッシュループになる。**

旧形の `definition_json`（`"source": "exif"` + `"fallback": "mtime"`）を
`db/profiles.py` の `_stack_rule_of` が `parse_definition` に掛けるので、
`sync_builtins()` が `ProfileInvalid` を上げる。それが lifespan の中で上がるので**起動しない**。
ビルトイン 3 つとも旧形なので必ず踏み、トランザクションが巻き戻るので毎回同じ所で落ちる ——
**手で DB を触るまで復旧しない。**

決め手は `_stack_rule_of` **自身の docstring** だった:

> **生の dict で比べてはいけない。** Phase 6 より前のリビジョンの JSON には
> `stack` キーが無く（省略時は `STACK_DISABLED` として読む）、新しい JSON は
> 正規形で `{"enabled": false, ...}` を持つ。

**この関数は契約上「旧リビジョンを読む」側**で、Phase 13 がその契約を壊していた。
直しは「読めない旧形＝規則が変わった」に倒すだけ（旧規則が分からない以上、
再評価に戻すのが保守的で正しい）。**旧形を「読める」ようにする互換シムは作っていない。**

同じ根で 2 件が続いた:

- **旧版が書いた `artifact_staging` を回収すると `KeyError: 'container_wall'`** —— やはり起動が止まる。
  ただしレビュアーの案（`.get()` に緩める）**だけ**では、Task 5 で締めた「キー名を間違えても
  永久に NULL のまま気づけない」という守りが消える。**読む側を緩めて、書く側をテストで締めた**
- **TZ 未設定だと Canon の取り込みが 1 件も通らない** —— `canon-eos` が `force_offset` になったため。
  実装は `design.md` §12.2 のとおりで、**間違っていたのは §6 の「起動時エラーとし」という記述の方**
  （§12.2 と食い違っていた）。`dji-osmo` は前から `force_offset` なので、これは Phase 13 の退行ではない

利用者は「データをリセットするので、古いデータでアプリが起動しないのは大丈夫」と判断した。
**それでも直しは入れた** —— プロファイル定義の形はこの先も変わるので、そのたびに
「起動しないので DB を消す」を繰り返したくない。

### 最終レビューが確かめて、問題が無かったもの

指摘と同じくらい、**確かめて無事だったこと**が記録の値になる。

- 時刻の連鎖（ffprobe → publisher → resolve → DB → recompute）は型も `None` の扱いも通っている
- **`parse_definition` 以外に `TimestampRule` を作る経路が無い**ので、`source` の終端が `mtime` という
  不変条件は破れない
- `0026` の作り直しは索引 5・trigger 2・列・CHECK すべて意図した差分だけ
  （`sqlite_master` を `0025` と機械比較。列順だけ `created_at` と `captured_at_revision_id` が
  入れ替わるが、位置指定の INSERT も `SELECT *` の位置参照も無い）
- Canon 相当の合成クリップ（h264 + pcm_s16le + tmcd, .MOV）で **`route=concat`・`pcm_s16le` 残存・
  検証 4 つすべて pass**（mov muxer が tmcd を作り直すが `selected_streams` 越しに見るので
  `unexpected` にならない）
- 新しいテストに vacuous なものは無い／秘密の漏れる新経路なし

### ブリーフが、保てと書いた性質を自分で壊していた

M4（`_refuse_ts_if_lossy` が先頭パートしか見ない）を直すとき、統括のブリーフは
`any(ts_route_blockers(streams, keep) for streams in part_streams)` という形を示しつつ、
**「例外に codec 名が入るという既存の性質は保つこと」**と書いていた。

実装者はこの 2 つが両立しないことを見つけた —— `ts_route_blockers` は blocker の一覧を返すだけで、
例外の整形（`"・".join(...)` と `MergeFailed` の送出）は `_refuse_ts_if_lossy` の中にある。
ブリーフの形にすると、その整形を呼び出し側へ複製することになる。既存関数をループで
全パートに適用する形へ変えた（再レビュアーが追認）。

## 外部レビュー（codex）が、直したばかりの穴の隣を突いた

ブランチ全体の最終レビューが通った後、**別の視点**を入れるために codex へレビューを頼んだ
（依頼では「すでに済んでいること」を明示して、同じ穴を掘り直させない形にした）。
返ってきたのは **Critical 0 / Important 2 / Minor 0**。どちらも codex が自分で再現している。

### Important 1 —— 拒否リストは、1 つ潰しても隣に同じ穴がある

**TS 経路の事前拒否が `pcm_` だけなので、ALAC でも同じ「音声が黙って消える」が起きる。**

codex は h264+alac の MOV 2 本で再現した —— `ts_route_blockers` は空を返し、mpegts は
`codec alac, is muxed as a private data stream` と警告するだけで **exit 0**、
入力の `audio/alac` が出力では `data/bin_data` になった。
**Phase 13 が PCM を塞いだ理由と完全に同型**である。

**拒否リストから許可リスト（「TS を往復させて音声が残ると実測できた codec だけ」）へ反転した。**
実装者が 11 の codec を実測した結果:

| TS 往復後も `audio` のまま | `data`（`bin_data`）へ化ける |
| --- | --- |
| `aac` / `mp3` / `ac3` / `eac3` / `opus` | `pcm_s16le` / `pcm_s24le` / **`alac`** / **`vorbis`** / **`flac`** / **`amr_nb`** |

**codex が再現したのは `alac` だけだったが、実際には `vorbis` / `flac` / `amr_nb` も
同じ穴を持っていた。** 拒否リストのままなら 1 つずつ潰す羽目になっていたことが、数字で裏付いた。
（再レビュアーが 4 つを独立に往復させ、実装者の表と 4/4 一致することを確認した。）

**許可リストは `aac` のみ**にした。`mp3` / `ac3` / `eac3` / `opus` は往復で生き残るが、
実在するカメラが SD カードに書く音声 codec ではない。**狭すぎた場合の失敗は「明示的な結合失敗」**
（利用者に見えるので、報告されたら実測して足せばよい。1 行）で、広すぎた場合は
「再生できるが妙な出力」になりうる。この案件の「黙って劣化させない」方針では狭い方が正しい。

あわせて、実装者が**潜在的な誤りを 1 つ**見つけた —— 旧コードは `codec_name` の前方一致だけを見て
`codec_type == "audio"` を確かめていなかった。`pcm_` がたまたま音声にしか出ない codec だったので
事故が起きていない。新しい判定では `codec_type == "audio"` を明示した
（**data に二重に効かせると、data track を持つ機種の経路が壊れる**）。

### Important 2 —— 記録して、直さなかった

**同じ `DATA_ROOT` で起動インスタンスが重なると、生きているリースを起動時 reconciliation が
中断扱いにする。** codex は有効期限内の running な結合ジョブを作って再現し、
`running/lease あり → interrupted/lease NULL`、作業ディレクトリも消えることを確認した。
あわせて `db/migrate.py:57` が適用済み一覧を `BEGIN IMMEDIATE` の**前**に読むので、
2 接続で同時に migration を走らせると片方が `UNIQUE constraint failed`（DB と FK は無傷）。

**直さないと決めた。** 理由は 3 つ ——
(1) **Phase 13 の退行ではない**（前からこの形）
(2) **実運用では起きない**（単一コンテナを stop-first で restart する形。codex も同意）
(3) 正しい直し（起動の所有権を排他する fence）は**それ自体が設計の判断**で、
ロックをどこに置くか・握られていたらどう振る舞うか・特権分離とどう噛むかを決める必要がある。

**`migrate.py:57` だけ直す部分対応も採らなかった** —— fence が無いままだと reconciliation の
側が残るので、「直った」という誤った安心を作る。`docs/development.md` の持ち越しに記録した。

### codex が確かめて、問題が無かったもの

- `container_wall` は original の生値保存と recompute の読み出しが一致し、
  derived は member 継承なので **mux 時刻を撮影時刻に使わない**
- Canon 写真の `force_offset` は**新規作成資産だけ自動補正し、既存・所有不明は承認待ちになる**
  （最終レビューが挙げた「写真にも `dateTimeOriginal` が送られる」懸念が、ここで 1 つ減った）
- 新たな vacuous test も無し

codex の sandbox は Unix socket / loopback の制約で protocol・mountd・Immich・system 系が
冒頭から落ちるため**全 pytest は完走できない**（対象 420 tests passed）。
外部レビューに渡すときは、**その環境で何が測れないか**も一緒に読む必要がある。

## 覆ったこと

- **`canon-eos` の `timezone_policy: none` は「EXIF にローカル時刻を書くので補正が不要」
  という理由で決めていたが、動画には EXIF が無い。** 器の時刻を使う以上、Canon にも
  `force_offset` が要る。`decisions.md` の「`canon-eos` は `merge` を無効にする」も、
  実カードで判別根拠が取れたので反転した
- **DJI で `mtime_semantics: instant` が正しかったからといって、他の機種に持ち込めない。**
  Canon は exFAT の `OffsetFromUtc` を書かないので、既定の `wall_clock` のままが正しい。
  **「形から素性を推定する」誤りが、また出た**
