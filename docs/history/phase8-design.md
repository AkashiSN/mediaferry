# Phase 8 の設計 —— ホームが「いま何が起きているか」を言えるようにする

**決まったこと（2026-08-24）。** 実装計画は `phase8-plan.md`、決着した判断は
`../decisions.md`、現在の仕様は `../design.md` §13 が正本になる。

## なぜこれをやるのか

**2026-08-23 の実機検証で、利用者が画面を触って見つけた。** 自動テストは全部
緑だった。同じ日に見つかった 7 件のうち、**4 件は同じ 1 つの課題**だった。

> 家族が画面を開いたとき、**いま何が起きていて、次に何をすればよいか**が分かる。

そのうち **3 件（ホームの動線・送信の進捗・取り外す）をこの設計で閉じる**。
残る 1 件「写真タブで 1 件を知って消す」は**別の設計として次に回す** —— 触る画面も
API も重ならないので、分けても片側だけにはならない。

**土台がもう 1 つ欠けているのが、設計の途中で分かった。** ホームの「N 件を
取り込む」は `source_entry` の残数から導くのに、**watcher が `scan` を積んで
いない**（§4）。実機の記録に既にあった不具合で、これが無いとホームが実態と
合わないので、この設計に含める。

| 実機で見えたもの | 記録 |
| --- | --- |
| **カードの帯と「やること」が矛盾する。** 「`SD_Card` のカードが挿さっています」の下に「いま、やることはありません」 | `../development.md` の持ち越し |
| **自動で取り込みが始まっているのに「いま取り込む」が押せる。** 下に進捗バーが出ているのに、同じ画面のボタンが有効 | 同上 |
| **実行中の作業を集める場所が無い。** 進行中のジョブは 1 件しか出ない | 同上 |
| **送信のジョブが進捗を一度も書かない。** 71.2 GB を 6 分、35 件を 2 分半かけている間、動いているか止まっているかが出ない | 同上 |
| **「取り外す」が、成功したときに何も言わない。** 押しても画面に変化が一切ない | 同上 |
| **watcher が `scan` を積まない。** 承認直後の `import` が「0 件で成功」した | `hardware-verification.md` の「自動取り込み（§12.1）が動かないことを、実機で確かめた」 |

**部品を 1 つずつ直すと、また片側だけになる。** 写真タブの B-2 で一度踏んでいる。
だから動線の設計から入り、モックで方向を決めてから実装計画を書く（Phase 7 と
同じ進め方）。

## 決めたこと

モックを 3 案 → 3 案の 2 段で比べ、**A-2** に決めた
（`.superpowers/brainstorm/*/content/home-layout.html` と `home-a-breakdown.html`。
追跡していないので残っていないことがある）。

- **A**（2 つの箱に分ける）を選び、**B**（1 本の列にまとめる）と
  **C**（カードを主役にする）は採らなかった
- その中で **A-2**（カードは「状態」ではなく「仕事」。取り込みを *やること* に
  並べ、走り出したら上の箱へ移す）を選び、**A-1**（カードは状態。上の箱に置く）と
  **A-3**（上下の両方に出す）は採らなかった

**A-2 を選んだ理由は、矛盾が文言の直しではなく形の上で消えること。** A-1 は
「やることが 0 件のときは下の箱ごと消す」という*追加の規則*で同じ矛盾を避けて
おり、規則を 1 つ足したぶん別の場面で破れる。A-3 は同じカードが 2 か所に出て、
押せるボタンが上下に散る。

## 1. ホームの構造と、状態から導く規則

**画面は一覧を持たない。** `/devices` ＋ `/jobs` ＋ `/dashboard` から毎回導く。
その導出を **1 つの純粋関数**に閉じ込め、上から 3 つの並びに振り分ける。

| 並び | 中身 |
| --- | --- |
| **いま動いていること** | 走っている・待っているジョブ**すべて**。カード由来のジョブにはカードのラベルを添える |
| **やること** | カードの取り込み ＋ `dashboard` の 4 つ（つなぐ／確かめる／送る／確認） |
| **いまの様子** | 仕事も動きも無いカード。「いま抜いて大丈夫です」はここ |

**カード 1 枚の行き先は、この順で決まる。**

1. そのカードを掴んでいるジョブが動いている → **いま動いていること**
   （やることには出さない）
2. 取り込むものが残っている（`source_entry` の `seen` / `failed` が 1 件以上）
   → **やること**「`SD_Card` から 38 件を取り込む」。**未信頼なら同じ札に
   「このカードを信頼する」も置く**（信頼を別の札に立てると、承認と取り込みが
   別々の仕事に見える）
3. **まだ一度も数えていない**（`scanned_at` が空）→ **いまの様子**「中身を
   数えています」。**「取り込むものはありません」とは書かない** —— 挿した直後の
   数えていないカードを「空」と断定すると、§4 の自動スキャンが終わるまでの間、
   画面が嘘をつく
4. それ以外 → **いまの様子**（「取り込むものはありません。いま抜いて
   大丈夫です」／対象外の理由／中身がまだ無い）

**「やること」の順は、手を動かす順。** 取り込む → つなぐ → 確かめる → 送る →
確認。現行の `hooks/useTasks.ts` の `ORDER` の先頭にカードが入る形になる。

**「いま、やることはありません」を出す条件を狭める。** **3 つの並びがすべて
空のときだけ**。カードが挿さっていれば必ずどれかに出るので、**帯と空表示が
同時に出ることは構造上あり得なくなる**。

**「いま動いていること」は全部出す。** 現行は `pickLiveJob()` が 1 本だけ選んで
いる（`hooks/useJobPulse.ts:40`）。「いま取り込む」は scan → import →
detect_groups の 3 本を積むので、**1 本しか出さないと残りが画面から消える**。
選ぶのをやめ、`isLive` なジョブを**走っているものが先**の順で並べる。

### 「いま取り込む」が押せてしまう問題

**2 重に塞ぐ。**

1. **取り込み中はその札が「やること」から消える**（＝ボタンごと無い）
2. 別のタブから押された競合に備え、**live なジョブを持つカードのボタンは
   `disabled`**。現行の `disabled={busy}` は「この画面が出した要求の最中」しか
   見ていない（`screens/Home.tsx:338`）

### サーバに足りないもの

`/devices` が返す各ボリュームに 3 欄を足す（`api/routes_devices.py:20`）。

| 足す欄 | 何のため |
| --- | --- |
| `pending_count` | 取り込む残りの件数。上の 1 と 2 の分岐そのもの |
| `scanned_at` | 一度も数えていないカードを見分ける（上の 3）。§4 で自動化するので、ふつうは一瞬で埋まる |
| `busy` | このカードを掴んでいる作業があるか。**「抜いていいか」の答え**（§3） |

`/jobs` の各ジョブに `volume_instance_id`（`params_json` 由来）と、それに
対応する**カードのラベル**を載せる。「いま動いていること」がどのカードの作業
なのかを言うため。

**`pending_count` は `source_entry` を数えるだけ**（`state IN ('seen','failed')`）。
`jobs/importer.py:83` が取り込む対象と同じ条件で数える —— **同じ条件を 2 か所に
書かない**ため、条件は 1 つの定数に切り出す。

## 2. 送信の進捗

**書き込みは増やさない。** 既にある心拍の UPDATE に相乗りさせる。

`with_lease_pulse` は「送る側」を別スレッドで走らせ、**待つ側が DB に触る**
（`core/lease_pulse.py:29`）。この分業をそのまま使う。

1. **ジョブの開始時に 1 回だけ数える** —— この宛先で送る対象の件数と合計バイト
   （条件は `claim_next` と同じ `SENDABLE_CLAUSE`）
2. **送る本文のストリームを薄いラッパで包む**（`adapters/immich.py:189` の
   `path.open("rb")`）。`read()` のたびに読んだ量を共有カウンタへ足すだけ。
   **このスレッドから DB には触らない**（接続はスコープごとに 1 本）
3. **心拍がそのカウンタを読んで `ctx.heartbeat(progress)` に載せる**
   （`jobs/uploader.py:103` の引数なしの心拍と、`with_lease_pulse` の中の心拍の
   両方）

**形は取り込みと同じにする。** 画面側は `progressLine` もバーも既存のものが
そのまま動き、**速度と残り時間まで出る**（`components/JobProgress.tsx:38`）。
足すのは `PHASES` に `upload: "送信中"` の 1 行だけ。

```
{phase:"upload", rel_path, file_index, file_count,
 bytes_done, bytes_total,          ← いま送っている 1 件
 bytes_done_all, bytes_total_all}  ← ジョブ全体
```

**合計は開始時のスナップショットで、走っている間に増減しうる。** 実測が合計を
追い越したら、**合計のほうを実測に合わせて伸ばす** —— `12 / 10 件` のような嘘を
画面に出さない。

**`uploader.py` の `_Progress` は別物。** あれは「リモートに触った可能性が
あるか」を持つ**解放先を決めるための内部フラグ**で、画面に出す進捗ではない。
名前が紛らわしいので、新しい進捗には別の名前を与える。

## 3. 「抜いていいか」を、押さずに分かるようにする

**ボタンを消して、状態にする。**

いまの「取り外す」は、掴んでいるジョブが無ければ**本当に何もしない**（読み取り
専用マウントはジョブの終わりに外れているので、押した時点で既に安全）。値打ちは
返ってくる答えだけなのに、その答えが画面に出ていなかった。名前も嘘を含んでいる
（何かが起きるように読めるのに、何も起きない）。

- **カードの箱に常時出す** —— 「**いま抜いて大丈夫です**」／「**取り込み中です。
  抜かないでください**」。元は §1 で足す `/devices` の `busy`
- **ホームは既に 2 秒ごとに取り直している**（`hooks/useJobPulse.ts:66`）。
  取り込みが終われば、**押さなくても表示が切り替わる**
- **「取り外す」ボタンは画面から消す**（ホームと `work/CardDetail.tsx` の両方）
- **`POST /volumes/{id}/close` は API に残す。** 掴んでいるジョブがあるときに
  `VolumeBusy` を返す口は、外から確かめる手段として害がない。`../design.md` §13
  から「取り外す」の記述を落とし、**画面から外した理由を `../decisions.md` に
  残す**

**`busy` の判定はサーバが持つ。** 画面が `/jobs` を見て自分で判断すると、
`close` の内側の条件（ハンドルを掴んでいるか）と**別の答えを出す 2 つ目の実装**
になる。

## 4. 挿すだけで取り込まれる、を実際に成立させる

§1 の「38 件を取り込む」は `source_entry` の残数から導く。**その行を作るのは
`scan` だけ**なので、watcher が `scan` を積まない限り、挿したばかりのカードは
永遠に「0 件」に見える。

**watcher が積むものを 3 本にする**（画面の「いま取り込む」と同じ並び。
`jobs/watcher.py:127` の `_enqueue_ready`）。

| 積むもの | 条件 | 印 |
| --- | --- | --- |
| `scan` | 対象と判定できた接続すべて。**信頼の有無にも `AUTO_IMPORT` にもよらない** | `volume_presence.auto_scan_at`（新設） |
| `import` | いまと同じ（`AUTO_IMPORT=trusted` ＋ 信頼済み ＋ `identity_confidence = high`） | `auto_import_at`（既存） |
| `detect_groups` | `import` を積んだときに一緒に | 同上 |

**`AUTO_IMPORT=off` でも `scan` は積む。** 「取り込まない」は「数えない」では
ない。§12.1 の「スキャン結果を画面に出すところで止まり、ユーザの承認を待つ」は、
スキャンが済んでいることを前提に書かれている。

**順序はジョブが直列に走ることで保たれる。** 同じ排他区間で `scan` → `import`
→ `detect_groups` の順に積めば、その順に 1 本ずつ走る。**印を付けるのと積むのは
同じトランザクションの中**（既存の `auto_import_at` と同じ形。SQLite に行ロックは
無いので、更新できた側だけが実行者になる）。

**印は presence ごとなので、挿し直すと `scan` がもう一度走る** —— これが「前回の
スキャン以降に撮った動画」を拾う道になる。**いまは挿し直しても `import` しか
積まれず、`source_entry` に無い新しいファイルは永久に取り込まれない。**

マイグレーションは **`0016`**（`volume_presence.auto_scan_at` 1 列）。

## 5. どう確かめるか

**実装より先に、失敗するテストを書き、失敗を確認してから最小実装する。**

**導出規則は純粋関数に切り出す。** `hooks/useTasks.ts` の `tasksFrom()` を、
カード・ジョブ・集計の 3 つを受けて 3 つの並びを返す関数に作り直す。**画面を
描かずに、カードの状態の組み合わせを網羅できる**のがねらい（取り込み中／未取り込み／
取り込み済み／対象外／未信頼／中身が無い × ジョブの有無）。

| 層 | 見るもの |
| --- | --- |
| 単体（画面） | 導出規則。**「カードが挿さっているのに、3 つの並びが全部空」が作れないこと**を明示的に確かめる |
| 単体（サーバ） | ストリームのラッパが読んだ量を数えること。心拍が進捗を載せること。**合計を追い越したら合計が伸びること** |
| 単体（サーバ） | watcher —— `scan` の印、3 本の順序、`AUTO_IMPORT=off` でも `scan` は積むこと、挿し直しで再スキャンされること |
| 単体（サーバ） | `pending_count` が `importer` の対象と同じ条件で数えること（**条件を切り出した定数を両方が使う**） |
| E2E | 巡回に錠を 1 本足す。**カードが挿さっている場面で「いま、やることはありません」が出ない** |
| 実機 | 送信の進捗が実際に動くか（71 GB）、抜いていい表示が取り込みの終わりで切り替わるか、**挿すだけで取り込まれるか**（§12.1 の踏み直し） |

**変異試験を省かない。** `PYTHONDONTWRITEBYTECODE=1` を付け、実装の判断を 1 つ
ずつ壊して対応するテストが落ちることを確認する（バイト数が変わらない書き換えで
古い `.pyc` に騙されないため）。壊すときは `git checkout` を使わず、scratchpad に
控えを取る。**検出できない変異は、検出できないことを記録に残す。**

**E2E の spec ファイルを増やさない。** E2E はサーバを回収しないので（持ち越し）、
spec を 1 本増やすと孤児が 1 つ増える。錠は**既存の巡回 spec に足す**。

## この設計に含まれないもの

**同じ日に見つかったが、別に扱うもの。**

| 項目 | どうするか |
| --- | --- |
| **写真タブで、選んだ 1 件が何なのかが分からず、消せない**（4 つで 1 つの設計課題） | **次の設計**。触る画面（`Photos.tsx` と新しい詳細）も API（`DELETE`・詳細）も重ならない |
| つなぎ目の警告が実カードでは毎回出る | 単独で直せる。閾値を時刻の分解能に合わせる |
| Immich の説明欄に `default` が出る | 単独で直せる。プロファイルが「捨てる説明」を宣言する |
| `origin = unknown` を「先に誰かが上げた」と描いている | 単独で直せる。書き分けるだけ |

**`../design.md` §13 の更新は実装と同じ PR で行う。** 仕様の正本と画面が食い違う
時間を作らない。
