## 1 行でいうと

**スタックの規則から撮影時刻を外し、代わりに「同じ時点でカードに在った」という
証拠を要求するようにした。** そのうえで、送る前の写真タブでも組を 1 タイルに畳んで
`RAW` の札を出すようにした。

**規則は 1 つだが、実装は 2 つある。** 第 2 パスは `identity_partners`（Python）、
一覧は同じ規則を SQL で書き直したもの（一覧は行ごとに Python の判定を呼べない ——
組がページの境目をまたぐ）。**この二重実装は実際にずれた**（後述の I-3）。最後に、
一覧の各行で「`stack` が付く ⟺ `resolve_group` が組を返す」を突き合わせるテストを
置いて、ずれを構造的に捕まえるようにした。

### 検出できなかった 5 件（うち 4 件は等価・実質到達不能）

**当初この節は「構造的に検出できないのは 1 件だけ」と書いていた。誤りだった** ——
全体レビューが独立に変異を当て直して、未検出が 5 件あることが分かった。うち 1 件は
**本物のテストの穴**である。

| 変異 | 判定 |
| --- | --- |
| `_SECONDARY_EXISTS` の `sib.media_file_id <> m.id` | **等価**（下に証明） |
| `identity_partners` の `if candidate.source_key not in keys: continue` | **等価**。`proofs` の鍵集合は `keys` と同一に構築されるので、`source_key not in keys` ⟺ `proofs.get(...) is None` となり、次行の証拠の門が必ず落とす。**いま鍵の門は完全に冗長**だが、読み手への明示として残す |
| `_SECONDARY_EXISTS` の `me.copresent_key IS NOT NULL` | **等価**。SQL の `NULL = NULL` は真にならないので、`sib.copresent_key = me.copresent_key` の JOIN 条件が既に 0 行しか通さない |
| `_SECONDARY_EXISTS` の `sib.state = 'published'` | **実質到達不能**。`sib.media_file_id IS NOT NULL` がほぼ含意する保険 |
| `jobs/scan.py` の `stack.enabled` / `extensions` の絞り | **本物の穴**。`stack` 対象外の拡張子や `enabled: false` のプロファイルに印を書かないことを、誰も見ていなかった。テストを足した |

### 等価の証明（`sib.media_file_id <> m.id`）

**`_SECONDARY_EXISTS` の `sib.media_file_id <> m.id` を外しても、どのテストも落ちない。**

`adapters/publisher.py::_commit` が保存先の `rel_path` で既存の `media_file` を
引き当てる（`existing = media_file WHERE rel_path = final_rel`）ので、**同じ
`media_file_id` を指す `source_entry` の行は拡張子まで揃う**。`sib.media_file_id = m.id`
を許しても `sib.extension = me.extension` が保証され、`theirs.rank` は常に
`mine.rank` と等しくなるので、厳密な `<` は真にならない。**保険であって、
到達する経路が無い。** 全 11 本で確認済み。

### pytest では落ちず、e2e だけが落ちた変異

`_reconcile_entry` の INSERT 経路が `extension` を入れないようにすると、**pytest は
緑のまま e2e だけが 2 本落ちた**。`test_api_media.py` が conftest の手書き
`source_entry` に依存していて、**スキャン → 取り込み → 一覧が単体テストで繋がって
いない**ためである。E2E が唯一の砦になっている箇所として記録に残す。

### 実装者の「検出できない」という申告が誤りだった 1 件

Task 6 で実装者は `theirs.rank < mine.rank` → `<=` を「単射性があるので構造的に
検出不能」と報告した。レビュアーが疑って反例を作り、**検出できることが確定した**。

単射性が効くのは **1 つの `media_file` の中だけ**である。同じ同席グループに
**別プロファイルの `media_file`** が混ざると（`extensions` の順が違う）、拡張子が
違うのに順位が一致しうる。ボリュームのプロファイルは観測のたびに解決し直されるが、
**`media_file.profile_id` は取り込みの時点で固定される**ので、この状況は作れる。

→ `cross_profile_rank_collision` fixture と
`test_a_sibling_under_a_different_profile_is_not_wrongly_hidden` を追加した。

**教訓: 「構造的に検出できない」という申告を鵜呑みにしない。** Phase 9 でも同じ
食い違いが 2 件あった（`phase9-record.md`）。**レビュアーに自分で変異を当てさせる**と
毎回何かが出る —— この Phase では Task 2・4・6・7 の 4 回で出た。

## 計画の誤り

### 1. Task 1／2 の切り方が誤っていた（統括が裁定で直した）

計画は「Task 1 で `StackRule.tolerance_seconds` を落とし、Task 2 で時刻の条件を
落とす」と切っていたが、**`tolerance_seconds` の唯一の消費者が `stacking.py` の
`_within`** なので、フィールドだけ消すと `AttributeError` になる。

実装者は「定数 0 を置いて凌ぐ」を提案してきた。**採らなかった** —— Task 2 で必ず
消すコードを 1 タスクぶん生かすだけで、レビューでも死にコードとして挙がる。
代わりに**時刻 2 条件の削除を Task 1 へ移した**。

### 2. Task 6 の SQL が誤っていた（実装者が気づき、レビュアーが実測で確定）

計画にはこう書いてあった。

```sql
AND NOT (_SECONDARY_EXISTS) AND NOT (_AMBIGUOUS_EXISTS)
```

**`_AMBIGUOUS_EXISTS` は同席グループ全体にかかる述語**なので、独立した除外条件に
すると**曖昧な組の行が丸ごと消える** —— 意図の正反対である（曖昧なときこそ全員を
別々に見せたい）。正しくは次の形。

```sql
AND NOT (_SECONDARY_EXISTS AND NOT _AMBIGUOUS_EXISTS)
```

レビュアーが計画どおりの SQL を実際に流し、**3 行が消える**ことを実測で確かめた。

### 3. 計画に書いたテストは、実装の判断を守る量に届かない（4 タスク連続）

Task 2・4・5・6 のすべてで、**計画付属のテストでは変異の半分以上が検出できなかった**
（Task 4 は 6 件中 4 件が未検出、Task 5 は 4 件中 3 件）。実装者が毎回テストを足した。

**次の Phase で効く形にすると: 計画にテストを書くときは、そのテストで検出したい変異を
1 つずつ挙げ、書いた後に当てて確かめる。** 「テストを N 本書く」は量の指定であって
守るものの指定ではない。

### 4. その他

- Task 4 の `_mark_copresence` に `ctx.heartbeat()` が無かった（**計画の抜け**）。
  `synchronous=FULL` の autocommit で 1 行ごとに fsync するので、1488 件のカードでは
  60 秒のリースを失う。実機で 1420 件消えたカードを見た直後だったので実在の値
- 計画のテスト例に stem の不整合（Task 2）、`test_api.py:203` は `MergeRule` 側で
  変更不要（計画の記述が誤り）

## 統括の裁定が誤っていて、レビューで覆った 1 件

**Task 7 で「写真タブから CR2 を単独で選べなくなる副作用を受け入れる」と裁定した。
これは前提が誤っていた。**

裁定の根拠はこうだった ——「利用者は『写真タブの一覧だけ畳む／選んで送る画面は
1 ファイル 1 行のまま』を明示的に選んでいるので、選択の意味まで変えるのは決定に反する」。

**`/photos` が「選んで送る画面」を兼ねる唯一の実装だった。** 別画面ではない。
実害は「RAW を選べない」ではなく、**組を選んで送ってもスタックが組まれない** ——
主（JPG）の id しか渡らないので Immich には 1 枚しか行かず、第 2 パスは相方が
`complete` でないので見送る。設計書 4 節の「選んで送る画面の契約はそのまま」に
真っ向から反していた。

**さらに悪いことに、実装者はこの退行をテストで迂回していた。** `phase6.spec.ts` の
「選んで送るとスタックが組まれる」E2E を、`selection` プリセットから `unsent`
プリセット経由（`/send` へ直接 goto）へ書き換えていた。切り分け自体は正しかったが、
**守るものを緩める方へ倒した**。

→ 裁定を取り消し、「畳んだタイルを選ぶと `stack.members` を全員展開する（合計サイズも
全員ぶん）」で直した。E2E は `selection` プリセットへ戻し、実装者が足した表示の
assert は残した。

**教訓: E2E が落ちたとき「迂回させるか、退行を直すか」の判断を実装者に任せない。**
dispatch に「既存のテストを書き換えたら、守るものが緩んでいないかを必ず報告する」と
書いても足りなかった —— **書き換えたこと自体をレビューの明示的な対象にする**。

## 測った値

### `collapse` 無しの一覧（既存経路。遅くなっていないこと）

`collapse` が `None` のときは分岐に入らず、`list_media` の SQL 文字列は Task 6 適用前と
**バイト単位で同一**。したがって実行計画が変わりようがない。それでも実測した。

- 60,000 行・フィルタ無し: **中央値 0.50 ms**（30 回。count + 1 ページぶんの行取得）
- `EXPLAIN QUERY PLAN` は変更の前後で完全に同じ

### `collapse=stack`（新機能。参考値）

同じ 60,000 行（うち 2,500 組が対象）で 10 回計測。

- **中央値 37.6 ms**（min 37.1 / max 38.9）
- より極端な条件（2,500 組すべてが同じ `copresent_key` 空間に密集する 30,000 行、
  フィルタ無し）では**中央値 144 ms**まで悪化する

`_SECONDARY_EXISTS` / `_AMBIGUOUS_EXISTS` は相関副問い合わせとして現れ、行 1 つあたりは
`source_entry_copresent`（`0024` の部分索引）と `source_entry_by_media` を辿るので索引
経由になる。ただし **`ORDER BY … USE TEMP B-TREE` と `LIMIT` の組み合わせでは SQLite が
早期打ち切りをできない**（`collapse` 無しなら `LIMIT` 側で打ち切れていた）。

**索引は足していない。** 「送る前に確認する」散発的な操作には十分で、ブリーフに速さの
合格基準も無い。**Phase 9 の教訓（狙っていない経路への影響を確かめずに索引を足さない）**
に従った。将来 RAW+JPEG の組が数千件規模で常用されるなら、そこで測って検討する。

## 全体レビューが見つけたもの（8 タスクが全部緑になった後）

**受け入れ 5 コマンドが全部緑・タスクごとのレビューも全部通過した状態から、Critical 1・
Important 5 が出た。** 記録に残す価値があるのは、どれも「タスクの範囲の中だけを見て
いては見つからない」形だったことである。

### C-1: 既存の見送りが未評価へ戻らない（設計書の「移行」が誤りだった）

設計書は「`tolerance_seconds` を落とすと定義 JSON が変わるので、リビジョン公開が
**自動で発火**して既存の `stack_skipped` は未評価へ戻る」としていた。**発火しない。**

`_publish_revision` が比べているのは JSON ではなく**パース後の `StackRule`** どうしで、
`tolerance_seconds` を dataclass から落とした結果、**旧 JSON と新 JSON が同じ値に
パースされる**。他の戻し口（`retry` は `failed` のみ／`requeue` はリモートから消えた
`complete` のみ／`_reopen_stack` はその実行で `captured_at` が動いた行のみ）は、
両方が見送りの組には効かない。**実機に残っていた 36 件は永久に見送りのままになる**
ところだった。

→ 一度きりの移行 `0025` で `stack_state = 'skipped' AND remote_stack_id IS NULL` を
未評価へ戻す。**教訓: 「規則の読み方」が変わったときは、定義の比較では戻せない。**

### I-1: 絞り込みと畳みの相互作用で、行が画面から消える

従を隠す条件が「**主も同じ絞り込みを通るか**」を見ていなかった。写真タブは全部の
絞り込みに `collapse=stack` を付けるので、JPG が `complete`・CR2 が `failed` のとき
`?status=failed` が **0 件**になる —— 部分的な失敗は普通に起きるのに、**「送れなかった
もの」に何も出ず、再試行に辿り着けない**。`?q=IMG_0001.CR2` も 0 件になっていた。

→ `_filters` を別名（`m` / `sm`）を取る形へ変え、従外しの中で主にも同じ節を当てる。

**採らなかった案**: 「`status` や `q` が付いていたら畳まない」。畳むかどうかが絞り込みの
有無で変わるのは説明できず、`profile` や `kind` でも同じ穴が残る。

### I-2: 中断したスキャンが同席の印を片方だけ落とす

印を消す `UPDATE` が無条件だったので、`media_file_id` がもともと NULL の行
（取り込み待ちの `seen`）でも消していた。完走したスキャンは末尾で書き直すので
表に出ないが、**途中で降りたスキャンは印を非対称にしたまま**にする。その組は二度と
成立しない。スキャンの中止は画面から普通にできる操作である。

→ `CASE WHEN media_file_id IS NOT NULL THEN NULL ELSE copresent_key END`
（SQLite の SET 式は更新前の行を見る）。代償は `docs/decisions.md` に書いた。

### I-3: 二重実装のずれ（**docs がそれを隠していた**）

SQL の曖昧さ判定は**同席グループ単位**、`identity_partners` は**主の全観測にまたがる**
単位で数えていた。同じ JPG が 2 枚のカードに在り、各カードに別々の CR2 がある形では、
**画面が Immich の作らない 3 枚組を宣言し、実在する 2 つの RAW が一覧から消える**。

さらに、統括が docs に「一覧と第 2 パスは**同じ関数**（`identity_partners`）を通る」と
書いていた。**実装と違う**（一覧は SQL で書き直している）。**docs がずれの存在自体を
見えなくしていた。**

→ SQL の数える範囲を合わせ、docs を「同じ規則を 2 つの実装で保つ。ずれたら不具合」へ
直し、**一覧の各行で「`stack` が付く ⟺ `resolve_group` が組を返す」を突き合わせる
テスト**を置いた。

**直しは裁定より 1 か所広くなった。** 曖昧さの範囲を合わせるだけでは症状が消えない ——
曖昧さの節は**隠される行**に相関しているので、範囲を広げても「CR2 から見た自分」は
曖昧にならず、RAW 2 つは消えたままだった（作られない 3 枚組の宣言だけが消える）。
隠してよいのは「**その主が組を宣言するとき**」なので、従外しの中で主の曖昧さも見る。

### この 6 件から言えること

**タスクごとのレビューは、タスクの範囲しか見ない。** C-1 は「Task 1 が型から欄を
落とす」と「Phase 6 が作った移行の仕組み」の間に落ちた。I-1 は「Task 6 が SQL を
書く」と「Task 7 が画面に付ける」の間に落ちた。I-3 は「Task 2 の Python」と
「Task 6 の SQL」の間に落ちた。**全部が接ぎ目である。**

**全体レビューを省いてはいけない。** 受け入れが全部緑なのは、範囲の中が正しいことしか
言っていない。
