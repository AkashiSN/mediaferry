## リセットのバグ —— テストが「仕掛けを持っていなかった」

**`artifact_staging` の行は公開が成功した後も `published` のまま残る**（happy path で消す経路が無い）。
その行は `job_id NOT NULL REFERENCES job(id) ON DELETE RESTRICT` を持つ。

一方 `reset()` は**手順 1 で `DELETE FROM job`** を実行し、`artifact_staging` を消すのは**手順 3**。
**親を先に消すので外部キーが止める。手順 1 はどの段でも必ず走るので 4 段すべてが落ちる。**
つまり**一度でも取り込みか結合をした DB では、リセットは絶対に通らなかった。**

ローカルの一時 DB で再現した:

```
--- 公開した行なし（既存テストと同じ）---
  jobs / uploads / library / all  →  すべて ok
--- 公開した行あり（実機と同じ）---
  jobs / uploads / library / all  →  IntegrityError: FOREIGN KEY constraint failed
```

**既存のテストが通っていた理由**: `test_reset.py` の `a_job()` は `job` と `job_event` しか作らず、
**`job` を参照する行を 1 つも用意していない**。Phase 13 の「素の `a_media_file` は `source_entry` を
持たないので行ごと飛ばされる」と同じ型で、**仕掛けが無いので試験が素通りする**。

**直し方は段の意味で分けた。** `published` は完了した公開の履歴なので作業の記録の段で `job` より先に消し、
`writing` / `staged` は回収待ちなので**消さずに断る**。**公開の手順そのものは変えていない** ——
Phase 13 で通した crash consistency の検証をやり直すことになる。

## 検出できない変異を 2 件記録した

`docs/development.md` の作法（「検出できない変異は、検出できないことを記録に残す」）に従う。

| 変異 | なぜ殺せないか |
| --- | --- |
| `reset()` の `WHERE state = 'published'` を外す | `immediate()` の `BEGIN IMMEDIATE` が書き込みを直列化し、`artifact_staging.state` は `CHECK` で domain が閉じている。**回収待ちの検査を通過した時点で全行が `published` であることが同一トランザクション内で保証される**ので、`WHERE` の有無を区別する入力が作れない（`claim_next` の CAS と同種） |
| `useQueuedJobs` の `!isLive(job)` を外す | `LIVE_STATUSES = ["queued","running","cancelling"]` と `"succeeded"` は排他なので、`!isLive(job) && job.status === "succeeded"` の左辺は**右辺が真になるすべての入力で必ず真**。真の同値変異 |

**「構造的に検出不能」と「単にテストが足りない」は別物**で、毎回レビュアーに独立して検証させた。
3 件目（下記）は**検証の結果、後者だった**。

## 「検査が新要素を覆えていない」型が 3 度出た

同じ形が 1 つのブランチで 3 回出た。**3 回とも根が違う。**

1. **`location.state` が無いと枠ごと出ない**（Task 4）—— `journey.spec.ts` の 44px の検査は
   `page.goto()` で各パスへ直接遷移するので、router の state を前提にする「押した操作」枠が
   **一度もレンダリングされない**
2. **静的な配列に詳細画面が入っていない**（Task 6）—— 同じ検査が `SCREENS` を回るだけで
   `/photos/:id` を含まない。**動的な詳細画面を含める `screensWithDetail()` は既に在り、
   別の 2 テストで使われていた**のに、44px の検査だけが使っていなかった。
   結果として**くわしく画面の既存ボタンも誰も実測していなかった**
3. **検査自体が「画面を落としたこと」を検出できない**（Task 6 → 7）—— `screensWithDetail()` を
   `SCREENS` に戻す変異が **0/5**。`tooSmall` は実測値でしか push されず、
   **「訪れなかったこと」を検出する断言が無かった**

**3 番目はレビュアーが「構造的に不能ではなく、書けるのに書いていない」と切り分けた。**
Task 7 で巡回したパスを断言する形にして、**0/5 から 5/5** へ変わった。

## 統合したときだけ壊れる形

Task 3 の Critical。`useQueuedJobs` は「`note` はジョブと独立に返す」という仕様どおりに作られ、
**フック単体のテストは全部通っていた**。ところが `Home.tsx` の「やることはありません」の判定に
`note` が入っておらず、**1 本も始まらなかった送信では、知らせのすぐ下に「いま、やることは
ありません」が同時に描かれた**。

**設計判断を、描画の一歩手前で打ち消していた。** しかもそれは
「1 本も始まらなかった送信でこそ知らせが要る」という、計画が名指しした最重要のケースだった。

## 設計の棚卸しが不完全だった

Task 4 の Important。統括は「`/sending` を消してよい、ホームが同じものを持つから」と裁定したが、
あの画面は**2 つのものを持っていた**。

- **「この画面を閉じても送信は続きます。」** —— `design.md` §13 が**明文で要求していた文言**
- **「作業の履歴」への直行の導線** —— Phase 7 で 17px リンクから 44px ボタンに直した動線

**筋書き**: 一度ホームを離れて戻ると `location.state` が無いので枠ごと消え、ジョブが終わっていれば
「いま動いていること」にも出ない。**結果に辿り着く道が画面上に一本も無くなる。**

## 利用者向けの変化が黙って起きていた

同じ Task 4。`/sending` を消したことで `JobCard` の `cancelLabel` を渡す呼び出し元が **0 になり**、
**送信ジョブの中止ボタンの文言が「送るのをやめる」から「中止する」へ変わっていた**。
誰も意図していない。実装者に「文言を戻す」か「統一する」かを選ばせ、前者になった。

## レビュアーが e2e に変異を当てた（この案件で初）

globalSetup が毎回 build し直すので、e2e にも変異が効く。3 画面それぞれを無遷移にすると
対応する spec が 1 本ずつ落ちることを実測し、**書き換えた 3 件が「緩んでいない」ことを、
消えた被覆の受け皿まで名指しして判定した**（組が `/merge` から消える件は
`test_api_merges.py::test_pending_leaves_out_the_groups_that_are_already_merged`、
「ホームへ」リンクは `journey.spec.ts:280`・`:314`）。

## 実装者が計画に無い判断をして、どちらも妥当だった

- **Task 3 の dedup** —— 走っているジョブは新しい枠と「いま動いていること」の両方に入るので
  2 回描かれる。計画は触れていなかった。**しかも「実装前は dedup が無いので 1 回しか描かれず、
  テストが偶然通る」ことにも自分で気づいて報告した**
- **Task 4 の「再試行する」への拡張** —— 同じエンドポイントで同じ 465 ms の窓に当たる。
  しかも**失敗カードは押した後も `failed` のまま描き直される**ので、留まると「つなぐ」より悪い

## 計画の誤り —— 7 タスク中 7 タスク

| 型 | 例 |
| --- | --- |
| **ヘルパの呼び方が実物と違う** | `a_volume` を既定値で呼ぶと `client` fixture の既定 DJI ボリュームと `UNIQUE (fs_uuid, fs_type, size_bytes)` で衝突する。**FK エラーではなく別の原因で「失敗するテスト」になり、TDD の赤が嘘になる** |
| **実在しないヘルパ** | `requestSpy` / `renderPhotos` / `currentSearch` / `lastMediaQuery`。Task 7 は Step 1 の**4 つのテスト片すべて**が該当 |
| **flaky な断言** | `count(job) == 1` は監視がスキャンを積むので落ちる。**同じファイルの既存テストが同じ警告を書いていた** |
| **変異を殺せないテスト** | `QUEUED_FADE_MS = 0` を殺すテストが無かった |
| **確認すべき対象の有無を確かめずに「確認せよ」と書いた** | typegen の差分は実際には 0 件。`get_media` に戻り値の型注釈が無く OpenAPI 上 `unknown` なので、型がそもそも無い |
| **CHECK 制約を満たさないテストデータ** | `state="complete"` は `destination_revision_id` が要る |
| **言語の仕様の読み違い** | `dest.upload_id!` の非 null アサーションは**クロージャ内で絞り込みが効かない** |
| **存在しない CSS クラス・role** | `.sel` / `.vh` / `role="list"` |

## 運用で分かったこと

- **e2e を他の重い処理と並行で流すと、CPU 競合で偽陽性が出る。単独で流す**
- **e2e の harness が起こす実プロセス（`.venv/bin/python3 -m mediaferry`）が溜まる。**
  1 回の実行で十数本増え、放っておくと数十本・数 GB になる。**アプリは停止時に走っている
  ジョブの完了を待つ設計なので、`SIGTERM` を送っても終了に数十秒かかる**
