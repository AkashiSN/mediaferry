# Phase 12 の設計 —— 組を 3 画面で通し、まとめて選べるようにする（2026-08-26）

**Phase 10 と Phase 11 を入れた main を実機で触った利用者のレビューから始まる。**
現在の仕様は [`../design.md`](../design.md)、そう決めた理由は
[`../decisions.md`](../decisions.md) にある。ここにあるのは**なぜこの形にしたか**で、
実装の手順は `phase12-plan.md`（これから書く）にある。

## 何を直すのか

**利用者の言葉では 5 件。性質は 2 つに割れる**（章の番号がその割り方にあたる）。

| | 利用者の言葉 | 実際に起きていること |
| --- | --- | --- |
| R1 | 日付の隣にも選択丸があって、その日付全部を選択できるようにしたい | 選べるのはタイル 1 つずつだけ。1 日 68 枚のカードでは 34 回押すことになる |
| R2 | よくある選択＋シフト選択で範囲選択が欲しい | 同上。範囲を選ぶ手段が無い |
| R3 | RAW がある写真の詳細で RAW に触れられていない。ファイル名やサイズを出して、選ぶと 2 枚送信にしたい | `GET /media/{id}` は `stack` を**一切返さない**（`api/routes_media.py:365`）。詳細画面には組を知る手段が無い |
| R4 | 送る画面でも RAW ラベルを付けて 2 枚カウントにしたい | 送る画面は `collapse` を付けずに引くので、JPG と CR2 が**別々のタイルで 2 件**として並ぶ |
| R5 | `RAW` ではなく `JPG+RAW` の方が 2 枚あると分かりやすい | タイルのラベルは `RAW` の 1 語（`components/MediaTile.tsx`） |

**R1・R2 は「選ぶ手数」の話**、**R3・R4・R5 は「組が一覧までしか届いていない」話**。
後者は Phase 10 で明示的にそう決めたことの反転なので、まずそこから書く。

利用者はあわせて **「2 枚選択状態でちゃんと Immich 側でスタックされていた」** と
報告している。**Phase 10 が作った仕組みそのものは実機で動いている。** ここで直すのは
その仕組みの**見え方と届く範囲**であって、組の判定ではない。

## 1. Phase 10 の「一覧だけ」を反転する

[`phase10-design.md`](phase10-design.md) の 5 にこう書いてある。

> 押した先は今までどおり**JPG 1 枚の `/photos/:id`**（選んで送る画面と詳細画面は
> 畳まない。利用者の判断）。

**これを反転する。** 反転する理由は、実機で触ってみて症状が出た側だからで、
当時の判断が間違っていたからではない。当時は「一覧で組が見えれば、選んで送るのは
これまでどおりでよい」と読めた。実際に触ると、

- 詳細を開くと **RAW の存在がどこにも出ない**。一覧では `RAW` と出ていたものが、
  押した先で消える
- 送る画面では、一覧で 1 タイルだったものが **2 タイルに割れて戻る**

つまり **組は一覧でだけ存在し、押すたびに消えたり現れたりする**。これは
「どれとどれが 1 枚か」を見せるという Phase 10 の目的そのものを損なっている。

**この設計の一貫した約束はこう置く。**

> **組は、一覧・詳細・送るの 3 画面で同じ 1 枚として振る舞う。**
> 数え方（枚数・合計サイズ）は**ファイル単位**、見え方（タイル・ラベル）は**組単位**。

数え方だけファイル単位に残すのは、利用者が R4 で「2 枚カウントにしたい」と言って
いるからで、**実際に転送されるファイルの数と、画面が言う数を食い違わせない**ため
でもある。

## 2. 送る画面は、API で畳んではいけない

**この設計でいちばん危ないところ。** 「一覧と同じように `collapse=stack` を付ける」は
素直に見えて、**壊れる**。

### 壊れ方 A —— 畳むと RAW が送られない

```
GET /media?status=unsent&destination_id=…&collapse=stack
  JPG も CR2 も未送信
  → CR2 の行は「従」として隠される
  → 返るのは JPG の行だけ
  → 送る画面は返ってきた行を送るので、CR2 が送られない
  → Immich でスタックが組まれない
```

**一覧では正しい振る舞いが、送る画面では機能の喪失になる。** 一覧の `collapse` は
「見せる行を減らす」ためのもので、`GET /media` はもともと**送る対象を決める API では
ない**。

### 壊れ方 B —— members を全部送ると件数が嘘になる

「主の行の `stack.members` を全部送る」で A は塞げる。**が、別の穴が開く。**

```
JPG は前回すでに送った（complete）。CR2 だけが未送信
  status=unsent は CR2 の行を返す（JPG は条件に合わないので返らない）
  従外しは効かない（主の JPG が同じ絞り込みを通らないため。routes_media.py の
  _secondary_exists_sql は「主も同じ絞り込みを通るときだけ隠す」）
  → CR2 の行に stack.members = [JPG, CR2] が付いて返る
  → members を全部送ると、送信済みの JPG を「2 件」に数え直す
```

**取り消せない操作の直前に出す数が嘘になる**ので、これは採れない。

### 決めたこと —— 平らに引いて、手元で組む

**送る対象は、絞り込みが返した行そのもの。`stack` は表示にしか使わない。**

そのために、API に**「隠さずに組だけ教える」**を足す。

```
GET /media?stack=members     ← 追加。従を隠さず、組に属する行すべてに stack を付ける
GET /media?collapse=stack    ← いまのまま（隠す + 主に stack を付ける）
```

送る画面は `stack=members` を付けて引き、**返ってきた行の集合の中だけで**組を作る。

| 返ってきた行 | タイル | ラベル | 数える枚数 |
| --- | --- | --- | --- |
| JPG と CR2 の両方 | 1 つ | `JPG+RAW` | 2 |
| CR2 だけ（JPG は送信済み） | 1 つ | 無し | 1 |
| JPG だけ（RAW を撮っていない） | 1 つ | 無し | 1 |

### なぜ「CR2 だけ後から送る」で正しく組まれるのか

**これは見立てではなく、実装を読んで確かめた。** 壊れ方 B の場面で CR2 だけを送ると、
第 2 パスはこう動く。

1. `unstacked_batch`（`db/uploads.py:847`）が、今回 `complete` になった **CR2 の
   レコード**を拾う（`stack_state IS NULL`）
2. `Stacker._candidate_of`（`jobs/stacker.py`）が、相方の JPG について
   `record_for(destination_id, epoch, media_file_id)` を引く。**今回の送信で作った
   レコードである必要は無い** —— 過去の `complete` がそのまま相方になる
3. `resolve_group` の資格条件は `origin = created_by_us` ／ `remote_asset_id` が
   揃って重複しない ／ `state = complete` ／ 同じプロファイル。**どれも「同じ
   バッチで送ったか」を見ていない**
4. `mark_stacked`（`db/uploads.py:929`）の `WHERE` は
   `(stack_state IS NULL OR stack_state = 'skipped')`。**前回「相方が見つからない」で
   見送りになった JPG を明示的に引き上げる**（同関数の docstring:
   「見送り済みの相方は引き上げる。見送りは『今は組めない』の記録であって永久の
   拒否ではない」）

**つまり「送るのは未送信のぶんだけ」で正しく、かつそれが唯一正しい。** すでに送った
ものを送り直すのは、この動線では常に無駄である。

### 「選んだもの」プリセットも同じ規則で組む

写真タブから持ち帰った `ids` は `GET /media/{id}` を 1 件ずつ引いている
（`work/Send.tsx:240`）。**詳細 API が `stack` を返すようになる**（4 章）ので、
同じ「返ってきた集合の中だけで組む」が使える。

**選ばれている member だけで組む**ので、詳細画面で RAW のチェックを外して送れば、
送る画面のタイルは JPG 単独・1 件になる。**外したものが黙って戻ってくることはない。**

## 3. 一覧 —— 日付の全選択と Shift の範囲選択

### 日付の丸

日付の見出し（`.sechead`）の左に丸を置く。**`role="checkbox"` の 3 状態**にする。

| その日の選ばれ方 | `aria-checked` | 押したとき |
| --- | --- | --- |
| 全部 | `"true"` | その日を全解除 |
| 一部 | `"mixed"` | その日を全選択 |
| 無し | `"false"` | その日を全選択 |

**`aria-pressed` のボタンにしない。** 「一部選ばれている」は押下状態では表せず、
読み上げでは全選択と区別が付かなくなる。`mixed` はチェックボックスにしかない。

**単位はタイル（＝組）。** 日付の丸で選ぶと、その日のタイルの members が全部付いて
くる（いまの `toggle`（`screens/Photos.tsx:251`）と同じ判断）。

**数えるのは、いま画面に並んでいる行だけ。** 絞り込みで隠れているぶんや、次の
ページのぶんは触らない —— 見えていないものを選ぶ丸は、押した結果が確かめられない。

### Shift+クリックの範囲

**直前に押したタイルをアンカーに、いま画面に並んでいる順で範囲を選ぶ。**
日付のまとまりはまたぐ（利用者が見ている並びは 1 本の流れで、まとまりは見出しに
すぎない）。

**範囲は常に「選ぶ」側に倒す。** アンカーの選択状態に合わせて外す実装もあるが、
「シフトで選び、要らないものを個別に外す」の方が手数が少なく、押した結果が
予想しやすい。**外すのは個別のクリックに残す。**

**アンカーは捨てる場面を決めておく。**

- タイルの丸を押すたびに、そのタイルへ更新する
- **ページ送り・絞り込み・検索の言葉・宛先の変更で捨てる**

捨てないと、並びが変わったあとのアンカーが**利用者の見ていたものと違う範囲**を指す。
`selected` は Phase 7 の判断どおり隠れても覚えておくが（`screens/Photos.tsx:138`）、
**アンカーは「並び」に属する状態なので、並びが変われば無効**である。

### 部品への波及

`MediaTile` の `onToggle` は `(id: string) => void`（`components/MediaTile.tsx:61`）。
**修飾キーを渡せるようにする。** 型を `(id: string, modifiers: { shift: boolean }) => void`
にする —— イベントそのものを渡すと、呼ぶ側が `preventDefault` などを触れてしまう。

## 4. 詳細 —— 組を出して、送るものを選ぶ

### API

`GET /media/{id}` に `stack` を足す。**一覧と同じ `_members_of`（`routes_media.py:216`）を
通す** —— そうすれば「曖昧な組は組にしない」が詳細でも自動でそろう。Phase 10 の
「画面に出す組と Immich が作る組は、同じ関数が決める」をここでも守る。

### 画面

「この 1 枚を作っているファイル」を出す。members を順位順（主が先頭）に並べ、
行ごとに**チェック・ファイル名・大きさ**。

```
┌─────────────────────────────┐
│  IMG_8364.JPG                  │
│  2026-08-08 13:00 ・ 3.5 MB     │
├─ この 1 枚を作っているファイル ──┤
│  ☑ IMG_8364.JPG        3.5 MB  │
│  ☑ IMG_8364.CR2       21.8 MB  │
│     2 枚 ・ 25.3 MB を送ります    │
└─────────────────────────────┘
```

- **既定は全部オン。** 一覧の丸が組ごとに選ぶのと揃える。外したい人だけが操作する
- 「送る」はチェックの付いた id だけを渡す。**0 個なら押せない**
- 組でない写真では**セクションごと出さない**（いまと同じ 1 件送信）
- ファイル名はその member の `/photos/:id` へのリンクにする（「元になったファイル」の
  節と同じ形）。**従の詳細を直接開いても同じセクションが出る**（members の並びは
  どちらから見ても主が先頭）

**チェックの状態は URL に持たない。** 送るまでの一時的な選択で、戻る操作で
復元する意味が無い。

## 5. ラベル —— `RAW` を `JPG+RAW` にする

**`{主の拡張子}+RAW`。** `canon-eos` では見た目どおり `JPG+RAW`。

**「RAW」の語は固定で、主の拡張子だけをファイル名から取る。** `stack.extensions` は
利用者が編集できる（設定 › カメラの種類）ので、主を `HEIC` にした人には `HEIC+RAW` と
出す —— **画面が実在しないファイル名を名乗らないための保険**であって、利用者の
「JPG+RAW と出したい」を狭めるものではない。

**主以外が 2 つ以上ある組**（`extensions` に 3 つ以上入れた場合）は `JPG+RAW ×2` の
ように枚数を添える。ビルトインには無いが、**組の枚数を黙って隠さない**。

**タイルの幅に収まるかは実測する。** 送る画面のタイルは 58px（`work/Send.tsx:499`
のグリッド）で、`RAW` の 3 文字から `JPG+RAW` の 7 文字へ伸びる。`.madeof` の
文字サイズか `.madeofs` の折り返しで詰める。**読めなくなるくらいなら、送る画面の
タイルを少し大きくする方を選ぶ**（送る前に確かめる画面なので）。

## 6. 数え方を 1 か所に置く

「組にまとめる」「ラベルを作る」「枚数と合計サイズを出す」を
**`web/src/utils/stacks.ts` に集める**。一覧・詳細・送るの 3 画面が同じものを呼ぶ。

**書き写さない理由は Phase 10 と同じ。** 3 画面が同じ組を別々の規則で作ると、
どれか 1 つだけが古くなり、**画面によって枚数が違う**という最悪の形になる。
1 章で置いた約束（「組は 3 画面で同じ 1 枚として振る舞う」）は、規約ではなく
この関数で守る。

## 6.5. 状態の印と凡例を外す（作業中に利用者から出た指摘）

**この節は設計を書いたあとで足した。** 実装が Task 5 まで進んだ時点で、利用者が
「写真一覧の送信済み・確認が要る・送れなかったのアイコンの凡例は使われているのか」
と尋ね、調べたところ**使われていないに等しかった**。

### 実際に何が起きていたか

印は `screens/Photos.tsx` の 1 行で決まっていた。

```ts
const impliedStatus = !media.stale && DESTINATION_SCOPED.has(filter) ? filter : null;
// …
return (media.data?.media ?? []).map((row) => ({ ...row, status: impliedStatus }));
```

**行ごとに状態を引いていない。** 宛先ごとの絞り込み（まだ送っていない／確認が要る／
送信済み／送れなかった）が効いている間は、返ってきた行はすべてその状態なので、
**全行へ同じ印を被せている**。

| いまの絞り込み | 印 |
| --- | --- |
| すべて／動画／つないだ動画 | **1 つも出ない** |
| まだ送っていない | 全タイルが白い丸 |
| 確認が要る | 全タイルが `!` |
| 送信済み | 全タイルがチェック |
| 送れなかった | 全タイルが `×` |

**1 つの画面に 2 種類の印が並ぶことがない。** 印が出るときは必ず全部同じで、それは
直前に押した絞り込みのチップが言っていることの繰り返しである。そして凡例は
**絞り込みに関係なく常に出ている** —— 印が 1 つも無い「すべて」の画面でも、
4 種類の説明だけが並ぶ。

`MediaTile` へ状態を渡している場所は、リポジトリ全体でここ 1 か所だけだった
（`work/Send.tsx` と `work/Approve.tsx` は渡していない）。

### 決めたこと —— 印ごと外す

**凡例を「印が出るときだけ出す」ようにするのでは足りない。** それでも印は
チップの繰り返しのままで、画面に情報が増えない。

**「すべて」でも行ごとの状態を出す**（印を本物にする）道もあるが、`GET /media` は
行ごとの宛先ごとの状態を返していないので、backend の契約を変える別の設計になる。
Phase 12 の範囲ではない。

したがって**印と凡例をどちらも外す**。絞り込みのチップが同じことを言っているので、
画面から失われる情報は無い。

### 何が一緒に消えるか

`MediaStatus` 型、`Media.status`、`StatusMark`、`.tile .mark*` と `.legend` の CSS、
`Photos.tsx` の `impliedStatus`。

**`!media.stale` の門も一緒に消える。** これは「新しい絞り込みの結果が返るまでは
印を出さない」ための門で（被せると送信済みの 200 枚に赤い × が付いた）、印が無く
なれば守る対象そのものが無い。

### なぜ Phase 12 の枝でやるのか

触るファイル（`Photos.tsx`・`MediaTile.tsx`・`styles.css`）は Phase 12 が
書き換えている最中のもので、別の枝に分けると衝突の解消だけが仕事になる。
**Phase 12 の全タスクが終わったあと、最後に外す。**

## 7. 触らないもの

- **`resolve_group`・`identity_partners`・同席の印**。組の判定は何も変えない
- **Immich 側のスタックの作り方**（第 2 パス）。1 行も触らない
- **`collapse=stack` の意味**。写真タブの契約はそのまま
- **ホームの「さっき取り込んだもの」**。`stack` を付けずに引く（いまのまま）
- **DB スキーマと移行**。この設計に移行は無い（API は追加のみ）

## 8. 危険

**`stack=members` は行ごとに 1 クエリ増える。** `collapse=stack` と同じ費用
（`_members_of` を行ごとに 1 回）だが、**送る画面は最大 200 行 × 宛先数**を引く。
Phase 9 で索引を入れ違えて他経路が退行した前例があるので（`phase9-record.md`）、
**測ってから決める**。実測が受け入れられない値なら、members を 1 本の SQL で
まとめて引く形に落とす。

**`stack=members` と `collapse=stack` の両方が来たときの意味**を決めておく。
`collapse=stack` が勝つ（隠す）。**片方だけを新設の 400 にしない** —— 既存の
呼び出し元が壊れる。

## 9. 試験の方針

- **backend**: `/media/{id}` の `stack`（組・非組・曖昧な組で `None`）、
  `/media?stack=members`（**従を隠さないこと**・従の行にも `stack` が付くこと・
  `collapse` と併用したときは隠すこと）
- **一覧**: 日付の丸の 3 状態と押したときの向き、Shift の範囲（**アンカーが
  ページ送り・絞り込み・検索・宛先の変更で捨てられること**）
- **詳細**: 既定で全部オン、外したときに「送る」へ渡る id、0 個で押せないこと
- **送る**: 組み方の 3 パターン（両方来た／片方だけ来た／詳細で外した）と、
  そのときの件数・合計サイズ・ラベル
- **E2E**: 「JPG+RAW を選んで送る」を `journey.spec.ts` に足す
  （`phase8-record.md` の教訓 —— 受け入れコマンドに入れないと腐る）
- **変異試験**は各タスクで。検出できないものは、検出できない理由を記録に残す

## 10. 採らなかった案

**送る画面でも `collapse=stack` を使い、members を全部送る。** 2 章の壊れ方 B。
すでに送ったものを数え直すので、取り消せない操作の直前に出す数が嘘になる。

**`GET /media` が常に `stack` を返す**（旗を要らなくする）。契約が全呼び出し元で
変わり、ホームの「さっき取り込んだもの」にも費用が乗る。**旗にすれば、払う画面
だけが払う。**

**詳細画面で RAW を既定オフにする**（利用者の言葉「これを選択すると 2 枚送信」に
いちばん近い読み）。一覧の丸は組ごとに 2 枚選ぶので、**同じ写真が画面によって
違う既定を持つ**ことになる。1 章の約束と食い違うため、既定オンにして「外せる」
形にした（利用者に確認済み）。
