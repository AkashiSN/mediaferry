# Phase 14 設計 — リセットを通し、押したことを伝え、送り直せるようにする

**この文書が実装の正本。** 実装計画（`phase14-plan.md`）はここから導く。
現在の仕様は [`../design.md`](../design.md)、決着した判断は
[`../decisions.md`](../decisions.md)。

## この回が何か

**実機（2026-08-27）で 4 件が出た。** Phase 13 の確認中に、利用者が実際に触って見つけたもの。

| # | 中身 | 性質 |
| --- | --- | --- |
| 1 | **リセットが 4 段すべて内部エラーで落ちる** | **バグ。原因確定・再現済み** |
| 2 | ジョブを積むボタンが、押したことを画面で言わない | バグ + 動線 |
| 3 | Immich で消した資産を送り直す手段が画面に無い | 機能の穴 |
| 4 | 一覧に送り先の絞り込みが常設されていない | 機能追加 |

**1 を最優先にする。** いま実害が出ていて、しかも「作り直せない」という一番困る形。

## 決定の表

| # | 決めたこと | なぜ |
| --- | --- | --- |
| 1 | **`published` の staging 行は「作業の記録」の段で、`job` より先に消す** | 段の意味に沿う。公開が完了した行は履歴であって、回収の対象ではない |
| 2 | **`writing` / `staged` の行があるときはリセットを断る**（409） | 回収待ちを黙って消すと、中断した公開の復旧経路が消える |
| 3 | **公開の手順（`_commit`）は変えない** | Phase 13 で通した crash consistency の検証をやり直すことになる |
| 4 | **`artifact_staging.job_id` を nullable にしない** | 移行が要るうえ、「どのジョブが公開したか」の記録が消える |
| 5 | **時間のかかるジョブを積む操作は、積んだと言ってからホームへ送る** | 進捗はホームにある。押した人のいる場所に情報が無いのが問題 |
| 6 | **`/sending` はルートごと消す** | ホームが同じものを持つ。残すと誰も辿り着かない画面が 1 枚増える（利用者の判断） |
| 7 | **結果のフェードは「ホームに着いてから」クライアント側で計る** | `finished_at` との引き算はブラウザとサーバの時計のずれで狂う |
| 8 | **失敗は自動で消さない** | 時間で消える失敗は「何も起きなかった」と区別が付かない |

## §1 リセットが落ちる

### 原因（再現済み）

`artifact_staging` の行は**公開が成功した後も `published` のまま残る**。happy path で消す経路が無い
（`publisher.py` が `DELETE` するのは `writing` の行だけ）。その行は

```sql
job_id TEXT NOT NULL REFERENCES job(id) ON DELETE RESTRICT
```

を持つ。一方 `db/reset.py` の `reset()` は**手順 1 で `DELETE FROM job`** を実行し、
`artifact_staging` を消すのは**手順 3**（`library` の段）。**親を先に消すので外部キーが止める。**

**手順 1 はどの段でも必ず走るので、4 段すべてが落ちる。**
つまり**一度でも取り込みか結合をした DB では、リセットは絶対に通らない。**

実測（ローカルの一時 DB、`scratchpad/repro_reset.py`）:

```
--- 公開した行なし（既存テストと同じ）---
  jobs / uploads / library / all  →  すべて ok
--- 公開した行あり（実機と同じ）---
  jobs / uploads / library / all  →  IntegrityError: FOREIGN KEY constraint failed
```

### なぜ試験が通っていたか

`app/tests/test_reset.py` の `a_job()` は `job` と `job_event` しか作らず、
**`job` を参照する行を 1 つも用意していない**。この案件で繰り返し出ている
「仕掛けが無いので試験が素通りする」型。

### 直し方

**段の意味で分ける。**

- **`published`** = 完了した公開の履歴 → **「作業の記録」の段で、`job` より先に消す**
- **`writing` / `staged`** = 回収待ち → **消さずに 409 で断る**
  （「回収待ちの取り込みがあるので、いまはリセットできない」）

いまの「走っている作業があるか」の検査（`status IN ('running','cancelling')`）の隣に、
**回収待ちの staging があるかの検査**を足す。どちらも `ResetNotPossible` で、
画面は `code` で文面を選ぶ。

新しい手順（`jobs` の段）:

```
1. 回収待ちの staging があれば断る（新）
2. DELETE FROM artifact_staging WHERE state = 'published'   （新。job より先）
3. DELETE FROM job_event
4. DELETE FROM job
```

`library` の段の `DELETE FROM artifact_staging`（全件）はそのまま残す —— 回収待ちが
無いことは 1 で確かめてあるので、実際には 2 で消え切っているが、**段の定義としては
「取り込んだファイルの記録も消す」に属する**ので条文を残す。

### `published` を消して壊れないことの根拠（実装で確認済み）

`published` の行を読む箇所は 2 つ。**どちらも `media_file` 側で同じことが言える。**

| 読み手 | 何をしているか | なぜ安全か |
| --- | --- | --- |
| `jobs/scan.py:117` | 消してよい `source_entry` から、staging が指すものを除外 | `PENDING_CLAUSE = "state IN ('seen','failed')"`。公開が済んだ `source_entry` は `state = 'published'` なので**そもそも候補に入らない**。除外が効くのは `writing` / `staged` の行だけで、それらは消さない |
| `jobs/reconcile.py:210` | 孤立判定で `final_rel_path` を「既知」に入れる | `_commit` は `final_rel` をそのまま `media_file.rel_path` に入れる。**`published` の `final_rel_path` は必ず `media_file.rel_path` と一致する**ので、`known` 集合が同じものを覆う |

`reconcile.py:239`（`work` の掃除）は `state <> 'published'` で明示的に除いているので無関係。

### エラー文言

いまは 500 の定型で「内部エラーが起きました。設定 › 詳しい情報 › 作業の履歴を
確認してください。」と出る。**リセットはジョブを積まないので、履歴を見ても何も無い。**
409 の 2 つ（走っている作業がある / 回収待ちがある）は `code` で文面を分け、
**何を待てばよいかを書く**。

### 試験

- **公開済みの staging を持つ形**を `test_reset.py` の土台に入れる（4 段すべてで）
- 回収待ち（`staged`）があるときに 409 で断られ、**`job` も `media_file` も 1 行も消えていない**こと
- `published` の行が「作業の記録」の段で消えること
- 変異: `state = 'published'` の条件を外す（回収待ちまで消える）→ 断りの試験が落ちる。
  順序を元に戻す（`job` を先に消す）→ 4 段すべての試験が落ちる

## §2 押したことを伝え、ホームへ送る

### いまの不揃い（実測）

| 画面 | 押した後 | 進捗はどこに |
| --- | --- | --- |
| ホームの「取り込む」 | 留まる | **同じ画面**（バーが出る）OK |
| カードの中身の「取り込む」 | 留まる | ホーム（見えない）NG |
| つなぐの「つなぐ」 | 留まる | ホーム（見えない）NG |
| 送るの「送る」 | `/sending` へ遷移 | その画面（専用） |

**なぜ「押しても何も起きない」に見えるか**（実測）: `POST /merge-groups/{id}/merge` は
**ジョブを積むだけ**で、`detected → merging` の書き換えは**ワーカーがジョブを拾ってから**
（`db/merges.py` の `mark_merging`）。画面の `act()` は POST 直後に `groups.reload()` を
呼ぶので、その窓に入ると **`detected` のままのカードを描き直す**（押す前と同じ見た目）。

実機の実測: `created_at 23:24:27.006` → `started_at 23:24:27.471` = **465 ms の窓**。

### 規則

**時間のかかるジョブを積む操作は、積んだと言ってからホームへ送る。進捗はホームが持つ。**

| 操作 | どうする |
| --- | --- |
| カードの中身の「取り込む」 | 通知 → ホーム |
| つなぐの「つなぐ」 | 通知 → ホーム |
| 送るの「送る」 | 通知 → ホーム（`/sending` ではなく） |
| **「分かれた動画を探す」** | **留まる** —— 候補がその画面に出るので、連れ出したら本末転倒 |
| 採用・破棄・組み直し | 留まる —— その場の一覧が変わる |
| ホームの「取り込む」 | 留まる —— すでにホーム |

### すぐ終わるジョブ

検出ジョブは実測 **47 ms**（`23:06:30.463` → `23:06:30.510`）で終わる。遷移した時点で
もう `succeeded` になっているので、`isLive` で絞っているホームには**何も無い** ——
問題が移動するだけになる。

**押したジョブの id を router の state で持って行き、ホームが名指しで追う。**
走っていれば進捗、終わっていれば結果を出す。仕組みは `Send.tsx` がすでに持っている
（`navigate("/sending", { state: { jobIds, note } })`）ので、行き先を変えるだけ。

- **フェードは「ホームに着いてから」クライアント側で 30 秒計る。**
  `finished_at` との引き算にしない —— ブラウザとサーバの時計がずれていると、
  遅れていれば「未来に終わったジョブ」が居座り、進んでいれば一度も出ない
- **× でも消せる。** 自動だけだと読んでいる途中で文字が逃げる
- **失敗は自動で消さない。** 時間で消える失敗は「何も起きなかった」と区別が付かない

### `/sending` を消す

ルート・`Sending.tsx`・そのテスト・e2e の該当箇所を消す。ホームの「いま動いていること」が
同じものを持ち、cancel も `JobCard` にある。

**送るの `note` を落とさない。** 「断られた写真と、開始に失敗した宛先を隠さない」は
`design.md` §13 の設計価値で、いまは `/sending` が出している。ホームで出す。

### 試験

- 4 つの操作それぞれで、**通知が出てホームへ遷移すること**
- 「分かれた動画を探す」は**遷移しないこと**
- **すぐ終わるジョブ**（ホームに着いた時点で `succeeded`）でも結果が出ること
- 失敗した場合、30 秒経っても消えないこと
- `note` がホームに出ること
- e2e: 送る → ホーム → 進捗が見えること

## §3 送り直す

### いまの状態

**機能は揃っていて、ボタンだけが無い。**

- `POST /destinations/{id}/recheck` —— **設定 › 送り先**にボタンがある（`Destinations.tsx:563`）
- `POST /uploads/{id}/requeue` —— **画面からの呼び出し元が 1 つも無い**
  （`web/src/api/types.ts` の型と `errors.ts` の「この記録は送り直せません。」だけ）

条件は明確: **再確認でサーバに無いと分かった `complete`**
（`remote_asset_id IS NULL` かつ `remote_checked_at IS NOT NULL`）。通常の `complete` は 409。

### 直し方

**`/photos/:id`（くわしく）の宛先ごとの状況に「送り直す」を足す。** すでに宛先ごとの
状態を出している行があるので、条件に当たる宛先にだけ出す。**押せない状態のボタンを
並べない**（`deletable` / `delete_blocked_reason` と同じ形で、理由を出す）。

**再確認への動線も足す。** いまは設定 › 送り先の奥にしかなく、「Immich で消した →
反映されない」に気づいた人がそこへ辿り着けない。くわしくの宛先の行に、
**「サーバを確かめる」を置く**（対象はその宛先）。

### 試験

- 条件に当たる記録に「送り直す」が出て、押すと `pending` へ戻ること
- **通常の `complete` には出ないこと**（押せないボタンを並べない）
- 409 が返る筋書きで、`errors.ts` の文言が出ること

## §4 送り先の絞り込みを常設する

`Photos.tsx` は `destination_id` をすでに扱う（`selectDestination` もある）が、
**宛先が 2 つ以上あり、かつ宛先が要る絞り込み（`DESTINATION_SCOPED`）を選んだときだけ**出る。

**フィルタ行の右端に常設のプルダウンへ変える。** API 側は `destination_id` を受けるので変更不要。

- 宛先が 1 つのときは**選ばせない**（いまの「黙ってそれを使う」を保つ）
- 宛先を変えたら**1 ページ目へ戻す**（いまの `selectDestination` の性質を保つ）
- 宛先が要らない絞り込みでも選べるようにするが、**その場合 API には渡さない**
  （`status` を伴わない `destination_id` は 400 になる。`Photos.tsx:36` のコメントどおり）

### 試験

- 宛先が 2 つ以上あるとき、どの絞り込みでもプルダウンが出ること
- 宛先が 1 つのときは出ないこと
- 宛先を変えるとページが 1 に戻ること
- **宛先が要らない絞り込みでは `destination_id` をクエリに載せないこと**（400 を踏まない）
