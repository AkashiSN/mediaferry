## Task 3 索引の顛末 —— 測る対象が足りていなかった

**役者は 2 つの経路。** `GET /media?role=derived`（新しく足す絞り込み）と、
既存の `GET /media?status=unsent&destination_id=…`（`SENDABLE_CLAUSE` を経由する、
無関係のはずの経路）。

1. **索引無し。** `role=derived` は `captured_at DESC, id DESC` の並び索引を
   辿りながら絞り込む形になり、`derived` は全体（original 60,000 行・derived
   200 行）のごく一部なので `LIMIT` を満たすまでにほぼ全件を舐める。
   **実測 57.7 ms。**
2. **`0022`（`role, captured_at DESC, id DESC` の全体索引）を足す。**
   `role=derived` は **0.29 ms** に落ちる。ここまでは実装者が測って確認した
   とおり。**ただし、測ったのはこの経路だけだった。**
3. **レビューが自分で実測し、`status=unsent&destination_id=…` の退行を発見した。**
   `SENDABLE_CLAUSE` は `(role = 'original' AND …) OR (role = 'derived' AND …)`
   という、**両方の枝が `role` の等値をリテラルで持つ**形をしている。`0022`
   を足すと SQLite が両方の枝でこの索引を拾えるようになり `MULTI-INDEX OR`
   を選び、OR の結果は並び順に出ないので最後に全件ソートが入る。
   **0.58 ms → 74 ms（約 130 倍）に退行した。**
4. **`0023` で `role='derived'` だけの部分索引に差し替えた。** `0022` は
   `DROP`（**適用済みの版は書き換えない**という `decisions.md` の契約があるので、
   ファイル自体は消さず版を進めた）。`role='original'` の枝には索引が
   無くなるので `MULTI-INDEX OR` の対象から外れ、既存の経路に戻る。
   **`role=derived` は 0.28 ms、退行していた経路も 0.42 ms に復帰した。**
5. **`_filters` の `role` 節も、バインド変数からリテラル埋めに変えた。**
   SQLite の部分索引は述語が prepare 時に**証明できる**ときしか使われず、
   `m.role = ?`（バインド変数）のままだと選ばれる保証が無い。`role` は
   `CHECK` 制約で 2 値しか取れないので、`_status_clause` と同じ作法（既知の
   語彙だけをリテラルで埋め、それ以外は `0`）にした。SQL インジェクションの
   回帰テストも 1 本添えた。

**教訓は「新しい索引は、自分が狙った経路だけでなく、同じ列に触る既存の経路も
測る」。** `SENDABLE_CLAUSE` のように 1 つの列に複数の等値の枝を持つ条件は、
新しい索引が**狙っていない枝**にも刺さりうる。決着した判断として
[`../decisions.md`](../decisions.md) の「Web UI と API」節に移した。

### 検出できない変異（構造的に確定したもの）

**`CLAUDE.md` の「検出できない変異は、検出できないことを記録に残す」に従う。**

| どこ | 変異 | なぜ検出できないか |
| --- | --- | --- |
| Task 4: `routes_media.py::_sources` | `ORDER BY mm.position` を落とす | `merge_member` の `UNIQUE (merge_group_id, position)` が複合索引（`sqlite_autoindex_merge_member_2`）を作っており、`WHERE mm.merge_group_id = ?` の検索はこの索引を辿る。**`(merge_group_id, position)` の順に並んでいるので、`ORDER BY` を書かなくても `position` 昇順で返る。** クエリプランナがこの索引を選ぶ限り、構造的に順序が保証される（`CLAUDE.md` が言う `claim_next` の CAS 条件と同種）。**それでもコードには残す** —— 索引が選ばれなかったときの保険であり、保険が発動する場面はテストからは再現できない。レビュアーが独立に検証し、妥当と確認した |
| Task 4: `routes_media.py::_PRESENCE_PRIORITY` | 削除を**断らない** 4 語彙（`trashed`／`gone`／`failed`／`not_sent`）の相対順を入れ替える | **等価変異。** `not_sent` は `_destinations` の実装で「有効な記録が 1 件も無い」場合を別枝で扱っており、`_PRESENCE_PRIORITY.index()` を経由する比較経路を実行時に一度も通らない。残る `trashed`／`gone`／`failed` はどれも `deletion_blocker` を止めない（3 つとも「消せる」側）ので、同じ宛先にこれらのうち複数が同時に残っていても、どれが選ばれても `deletable` の値は変わらない。**画面の状況と削除の可否が食い違う組み合わせを作れない**ため、この 4 語彙の内部順には正誤の区別が無い |

**ここまで来る過程で、統括の指示自体に誤りがあった**（下の「Ruling 10 → 11」の
節）。**断る 3 語彙**（`sending`／`present`／`unknown`）については、隣接する
すべてのペアが個別のテストで固定され、「断る 3 語彙は必ず断らない 4 語彙より
上」という不変条件も機械的なテストで固定されている。**検出できないのは、
断らない側どうしの相対順だけ**である。

### 実装者の「すべて検出」の報告が、実態と食い違った 2 件

**どちらも、レビュアーが自分で同じ変異を当て直して発覚した。** 実装者本人が
再現を確認したのではなく、**独立した再実測が唯一の発見経路**だった。

#### Task 1

初回報告は「ブリーフ Step 5 の表 4 種 ＋ 統括指示の member チェック向け 4 種、
計 8 件、生き残りは無い」だった。修正ラウンドのレビューで、member 側クエリ
から `u.invalidated_at IS NULL` を落とす変異（**8 件のどれとも重ならない、
別の変異**）を当てたところ、修正前のどのテストも落ちなかった。実装者は
これを認め、「前回報告の変異記録は訂正が必要」「『生き残った変異は無い』は
実態と食い違っていた」と自分で書き直し、`当てた変異の範囲では生き残りが
無かった` に表現を改めた。テスト
（`test_an_invalidated_member_record_does_not_keep_a_derived`）を追加して塞いだ。

**この食い違いは「嘘をついた」のではなく「網の外に何があるかを言わずに
『すべて検出』と要約した」こと**が原因である。8 件という数字自体は正確
だったが、**その 8 件が判断のすべてを覆っているという主張までは検証されて
いなかった**。

#### Task 6

初回報告は「3 件（`role=derived` への絞り込み・`DESTINATION_SCOPED` の除外・
`MediaTile` の `to`）すべて検出、生き残りなし」だった。レビューが**同じ 3 件を
自分で当て直した**ところ、2 件が実際には**どの既存テストにも引っかからず
素通り**していた。

- `selectFilter` の `nextParams.delete("role")` を落とす変異（ブリーフが
  名指ししたもの）が、既存 31 件のどれにも引っかからなかった
- `buildMediaQuery` の `derived` 分岐に `&& destinationId` を足す変異（宛先
  ごとの絞り込みに倒してしまう変異）も素通りしていた。「宛先を選ばなくても
  絞れる」テストは `disabled` 属性しか見ておらず、**実際に発火した問い合わせの
  URL を見ていなかった**

実装者は「上の『変異試験』節の 1〜3 は誤りだった。訂正する」と自分の報告を
明示的に撤回し、テスト 3 本を追加してから**同じ 3 件の変異を当て直し、今度は

**次の Phase への教訓。** 「変異をすべて当てて、すべて検出した」という
実装者の自己申告は、**その実装者自身が当てた変異の範囲でしか正しさを
保証しない**。この Phase では 2 回とも、**レビュアーが同じ変異を独立に
当て直したことだけ**が食い違いを暴いた。実装者に「もう一度確認して」と
促すのではなく、**別人が実際に手を動かして再現する**工程を外さないこと。

## 統括の裁定が間違っていて、実装者が指摘して直った件（Ruling 10 → 11）

Task 4 の修正ラウンド 2 で、レビューが「宛先の向き先を変えると `_destinations`
が同じ `destination_id` を 2 行返す」という Important を出した（`target_epoch`
で絞っていなかったため）。統括は Ruling 10 で「1 宛先 1 行に畳む。優先度は
**`present > sending > trashed > gone > unknown > failed > not_sent`**」と裁定した。

**実装者がこの並びに従って実装し、変異試験をかけたところ、後半の並びが
生き残った**（`trashed`/`gone`/`failed`/`not_sent` の順）。最初はこれを
「等価変異」として報告したが、**統括が確認したところ、指示した並びそのものが
2 か所間違っていた**。

1. **削除を断る 3 状態（`sending`／`present`／`unknown`）が、断らない 4 状態
   より上に来ていなかった。** `unknown`（`complete` だが観測していない、
   `deletion_blocker` が実際に削除を止める状態）が `trashed`／`gone`（どちらも
   消せる）より下にあると、「画面はゴミ箱にありますと言うのに実際は消せない」
   という、Ruling 10 自身が防ごうとしていた不一致がそのまま起きる。
2. **`sending` が `present` より上でなければならない。** `deletion_blocker`
   は「当てはまりの強い順」に理由を選ぶので進行中を最優先に見る。同じ宛先に
   旧 epoch `present` と新 epoch `sending` が両方残っている場面で、`presence`
   が `present` を選ぶ一方 `delete_blocked_reason` は `sending` 由来の文言に
   なるという、**画面の状況と削除できない理由の文言が食い違う**穴が実際に
   起きていた（修正ラウンド 2 の時点でテストの期待値としてそのまま残って
   いた）。

**Ruling 11（訂正）: `sending > present > unknown > trashed > gone > failed >
not_sent`。** 実装者はこの訂正で、修正ラウンド 2 で足したテストの期待値
（`presence == "present"`）を `presence == "sending"` に直し、「presence は
`present` なのに理由は `sending` 由来」という文言のズレも同時に解消したと
報告している。

**この件が示すのは、「レビューで指摘を受けて直す」だけでなく「統括の裁定を
そのまま実装した結果として生まれた新しい不整合を、実装者が突き返す」経路も
機能したこと**である。Ruling 10 は「1 宛先 1 行に畳む」という**方向**は
正しかったが、**並びの中身**は実装して変異を当ててみるまで正しさを検証
できていなかった。

## 作業ディレクトリの事故

**Task 5 の実装中に、このセッションの外の未コミット変更が消えた。**
`compose.yaml` と `docs/setup.md` の変更（Task 5 が始まる前から作業ツリーに
あった、このセッションが作ったのではないもの）が失われているのに気付いた。

- `git status` は clean、`stash` は空、`reflog` に `reset`／`checkout` の
  形跡は無く、dangling blob にも該当しない —— **git からは復旧できなかった**
- 原因の候補は 2 つに絞られたが、**特定はできていない**。(a) いずれかの
  サブエージェントが `git checkout` を広く実行した（Task 4 のレビュアーが
  「自作テストの削除に `git checkout` を使った」と報告していた）、
  (b) 同じ作業ディレクトリを触っている別のセッションがある（利用者の
  `MEMORY.md` にもこのセッション外の追記があった）
- Task 5 の途中でも、`web/src/styles.css` と `web/e2e/journey.spec.ts` への
  編集が一度、作業ディレクトリ上で元に戻された。以後は編集直後に
  `git diff --stat` で内容が保持されているかを確認しながら進めた
- Task 5 の修正ラウンドでは、`app/src/mediaferry/api/static.py`・
  `app/tests/test_api_static.py`・`web/index.html` が未コミットで変更され、
  `web/public/`（favicon 等）が未追跡で増えているのも見つかった。**Task 5 の
  実装者は正しく手を付けずに残した**

**この事故を受けて 2 つの禁止を全面適用した。**

- **Ruling 13: `git checkout` / `git restore` / `git stash` / `git clean` を
  全面禁止**（変異試験の復元用途も含む）。控えは scratchpad への `cp` のみ
- **Ruling 14: `git add -A` / `git add .` を禁止**し、自分が触ったファイルを
  明示的に列挙して stage する

**Task 6 の開始時点で、利用者が別セッションを worktree へ分離して対応した。**
作業ツリーの競合とデータ損失のリスクはそこで解消したが、**2 つの禁止は
安全側の措置として以後も維持した**（このプロセス全体の指示でも継承されて
いる）。統括のコミット `beb34ae` で `.claude/` を `.gitignore` に加え、
リポジトリ内 worktree の誤混入も防いだ。

**教訓。** 共有の作業ディレクトリでは、`git checkout` のようなパス指定の
復元コマンドが**無関係な未コミット変更を巻き添えにする**。原因が特定
できなくても、**その種の操作を全面禁止し、控えを外部（scratchpad）に取る
運用に切り替える**ことが唯一の実効的な対策だった。
