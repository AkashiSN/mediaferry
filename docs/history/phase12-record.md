### 検出できなかった 1 件（等価変異）

**`_ranks` の `if not ranks: return "", ()` を消しても、何も落ちない。**

計画は「`_members_of` の SQL が壊れて全テストが落ちる」と予想していたが、実測では
壊れない。戻り値が削除の前後で**数学的に同一**だからである —— `ranks` が空のとき
`", ".join([...] * 0) == ""` かつ `tuple(... for row in [])== ()` なので、早期 return の
有無で出力が変わらない。加えて呼び出し側（`_stack_of` の `if not ranks_sql: return None`
と `list_media` の `if ranks_sql:`）が**両方とも独立に空文字列を弾いている**ので、
壊れた SQL が `_members_of` へ渡る経路が無い。

**ガードは残した。** `VALUES` は 0 行を書けないという設計意図はコードとして正しく、
いま呼び出し側の防御と重複しているだけである。将来どちらも空文字列を見ない呼び出し元が
増えたとき、初めて意味を持つ。

### 本物の網の穴だった 1 件（Task 7）

`included === null ? [data.id] : [...included]` を `[data.id]` に潰しても、名指しの
「外した 1 枚は送るへ渡らない」が落ちなかった。

理由は**フィクスチャ固有の偶然**である。`aPair()` の `members[0].id` と `detail()` の
既定 id がどちらも同じ値だったので、「従だけ外す」操作では残るのが常に主 = `data.id` に
なり、**正しい実装（選んだぶんを渡す）と壊れた実装（いつも `data.id` を渡す）が
同じ結果になる**。

> **当初この報告は「`data.id` は組の主と常に一致する」と書いていた。誤りである。**
> 従自身の詳細を開けば `data.id` は従になる —— `GET /media/{id}` は開いた id が主でも
> 従でも組を主が先頭の並びで返すだけで、`data.id` が主に固定される保証は無い。
> レビューの指摘で訂正した。

→ **主を外して従だけを残す**テストを足した。正しい実装は従の id を、変異は主の id を
渡すので確実に見分けが付く。

## レビューが実装者の結論を覆した 2 件

**この 2 件が、次にこの層を触る人にいちばん役に立つ。**

### 1. 「等価変異」と報告された変異は、目に見える崩れだった（Task 4）

実装者は `label !== null` → `media.stack != null` を「検出できない」と報告した。
テスト（`queryByText(/RAW/)`）が緑のままだったからである。

**等価変異ではない。** 1 枚しか表さないタイル（相方が送信済みで CR2 だけが対象、という
送る画面の実在のケース）で変異させると、

```html
<span class="madeofs"><span class="madeof raw"></span></span>
```

が残る。`.madeof.raw` は背景色と padding を持つので、これは**文字の無い色付きのピルと
して画面に見える**。テストが**文字しか見ていなかった**ので、空の要素を見落としていた。

→ `container.querySelector(".madeofs")` が `null` であることの**構造の表明**を足した。
変異を当て直して、今度は狙ったテストが落ちることを確認した。

**教訓: 「文字が出ない」は「何も出ない」ではない。** 消えるはずのものを守るテストは、
文字ではなく要素の不在で書く。

### 2. 「テストが覆っている」の根拠が、名前ほどには確かめていないテストだった（Task 7）

実装者は「効果の依存を潰す変異（`if (false)`）で 4 本落ちるので覆えている」と報告した。
レビューはこれを**「同期が走ること」の証明にしかなっていない**と指摘した ——
8 本のテストはすべて**1 枚の写真しか描かない**ので、再初期化が**何を鍵に**走るかを
誰も固定していない。React Router は param だけの遷移でマウントを作り直さないので、
このタスクで足した相方リンクで別の組へ渡ると、同じマウントのまま `memberKey` が変わる。
ここが「一度でも選ばれたか」のような誤った条件に壊れても、既存の 50 本は 1 本も
気づけない。

**指摘どおりの変異は、実際には緑にならなかった。** `if (included === null)` に書き換えると
描画中の `setState` が毎回条件を真のまま残し、React の再試行上限（25 回）に達して
"Too many re-renders" でスイート全体が落ちる。実装者はこれを隠さず報告し、**同じ欠陥の
型を、スイートを巻き込まずに実体化する変異**（「組を一度でも見たか」を鍵に 1 回だけ
種を撒く形）を別に組んだ。その変異では追加した「別の写真へ移ったときは、選択が
引き継がれない」だけが落ち、他 49 本は緑のままだった —— 指摘が説明した**静かな
壊れ方**そのものである。

再レビューは、この代替が「指摘した欠陥の型そのものの実体化」であって、新テストが
偶然捕まえる別物ではないと判定した。

### 付随して: Minor を修正ラウンドへ入れた 1 件（Task 10）

通常 Minor は台帳へ送るだけだが、Task 10 の 2 件は**「無いことを網で押さえる」という
このタスクの中核が弱い**という指摘だったので、修正ラウンドへ入れた。

- 印の網はクリック直後の `waitFor` が**クリック前から画面にあったタイル**で満たされて
  しまい、忠実な復元（門ごと戻る）ではステイルの窓で緑になりうった
- 凡例の網は凡例が最も出にくい状態（宛先 0・写真 0）でしか見ておらず、設計が退けた
  折衷案を捕まえられなかった

どちらも上の復元実験で、直した後は捕まえることを確かめた。

**この計画は 12 か所で実物と食い違った。** 内訳は、**計画を書いている最中に気づいて

### 計画を書いている最中に先に直した 1 件（元は設計の誤り）

**`formatBytes` の単位。** 設計のモックが送る枚数の行を `MB` で書いていたが、実装の
`formatBytes` は 2 進の単位（`B` / `KiB` / `MiB` / …）を出す。計画は Task 7 のブリーフを
書く時点でこれに気づき、テストの期待値を 2 進単位に直したうえで「**`MB` と書かない**」を
注記した。**この注記が無ければ、実装者は画面ではなく `formatBytes` の方を「直して」
いた可能性がある** —— `formatBytes` は送る・つなぐ・写真・進捗のすべてが共有している。

**これだけは、計画の本文が書かれる前に潰れている。** 実装者へ渡ったブリーフには
既に正しい期待値と注記が入っていた。

### 実装中に実装者が直した 5 件

1. **`react-hooks/set-state-in-effect`（Task 6・Task 7）。** 計画が書いた
   `useEffect(() => setAnchor(null), [mediaQuery])` の形は、このリポジトリの lint が
   エラーにする。React 公式が推す「**描画の途中で前の値と比べ、その場で調整する**」形
   （`const [anchorMediaQuery, setAnchorMediaQuery] = useState(mediaQuery);` と、
   食い違ったらその場で捨てる分岐）へ置き換えた。振る舞いは同じで、描画が 1 回減る。
   **Task 7 も同じ穴に落ち、Task 6 が確立した形に倣って解決した。**
2. **`react-hooks/preserve-manual-memoization`（Task 10）。** 計画どおり `rows` から
   `impliedStatus` を落とすと、依存配列が 3 → 2 に減った瞬間に React Compiler が
   「既存の手動メモ化を保てない」で落ちる（依存の順序を変えても、宣言位置を動かしても
   再現する）。`needsDestination` を `useMemo` で包んで解消した —— 値は従来と完全に
   同一で、純粋な派生値をキャッシュしただけである。
3. **`react-hooks/globals`（Task 7）。** 計画のテストが使っていたインライン `Spy`
   （コンポーネント外の変数をレンダー中に再代入する）が lint に落ちた。同じファイルに
   既にある `SendProbe` / `data-testid` の形へ寄せた。
4. **`userEvent` の修飾キーは押しっぱなしにならない（Task 6）。** 計画は
   `userEvent.keyboard("{Shift>}")` の後に**別呼びの** `userEvent.click(...)` を書いて
   いたが、直接 API は呼び出しごとに新しい session を作るので、**押している状態が

### `stack=members` は `collapse=stack` より速い（Task 2）

送る画面の実際の上限にあたる **200 行（100 組）の canon-eos カード**を、実プロセス・
実 DB・実ジョブ経路（スキャン → 取り込み）で用意し、3 パターンをウォームアップ後に
20 回ずつ叩いた中央値。3 回実行して再現性を確かめた。

| 形 | 1 回目 | 2 回目 | 3 回目 |
| --- | --- | --- | --- |
| `GET /media?page_size=200` | 2.18 ms | 2.17 ms | 2.09 ms |
| `GET /media?page_size=200&stack=members` | 4.45 ms | 4.50 ms | 4.50 ms |
| `GET /media?page_size=200&collapse=stack` | 5.67 ms | 5.61 ms | 5.84 ms |
| `stack=members` / `collapse=stack` | 0.78x | 0.80x | 0.77x |

**計画の安全弁（2 倍以上遅ければ止まる）は発動しなかった。** 計画は「行ごとに 1 クエリ
増える」ことを危険視していたが、`collapse=stack` は**同じ行ごとの `_members_of` に加えて**
主クエリ自体に高コストな除外節（相関 `EXISTS`）を持つので、`stack=members` の方が
総じて軽い。`_members_of` を 1 本の SQL にまとめる作業は**不要と判断した**。

同じ手順は、次に `_members_of` の中身が重くなる変更が入ったときの回帰検知にそのまま
使える。

> **計測が CSRF に阻まれた。** `system_app` は `web/dist` が無いと CSRF トークンを
> 発行する唯一の GET ルートをマウントしないので、素の HTTP クライアントでは
> 二重送信 Cookie を受け取れず、取り込み経路が軒並み 403 になる。テストの `client`
> フィクスチャと同じ「固定トークンをクッキーとヘッダの両方に見せかけで置く」やり方で
> 回避した。

### 札はタイルからはみ出していた（Task 4）

計画は「dev サーバで目で見る」と書いていたが、サブエージェントに目は無い。**統括の
裁定**: CSS の保険（`max-width` + ellipsis）は無条件に入れ、タイル幅は**実測がある
場合だけ**変える。実測が取れなければ触らず Task 9 へ送る —— **見ていないものを
「確かめた」と書かせない。**

実装者は E2E の harness で `/send` を実際に描かせ、`.madeof.raw` の
`clientWidth` / `scrollWidth` を読んだ。

**`minmax(58px, 1fr)`（変更前）:**

| viewport | タイル幅 | badge clientWidth | badge scrollWidth |
| --- | --- | --- | --- |
| 320px | 66.75px | 53px | 54px |
| 340px | 71.75px | 54px | 54px |
| 360px | 60px | **46px** | 54px |
| 375px | 63px | 49px | 54px |
| 390px | 66px | 52px | 54px |
| 412px | 70.4px | 54px | 54px |
| 430px | 60.5px | **47px** | 54px |

**`minmax(74px, 1fr)`（変更後）:** 同じ 7 つの viewport すべてで
`clientWidth === scrollWidth === 54px`。切れは全て解消した。

**`repeat(auto-fill, minmax(…))` はアイテム数に関係なく、コンテナ幅だけでトラック数と
トラック幅が決まる**（空きトラックも幅を持つ）。だから「58px 固定」ではなく 58〜75px を
行き来し、**一般的なスマホ幅でちょうど切れる**という直観に反する形になっていた。

この画面の `MediaTile` は `to` も `onToggle` も渡さない（`role="img"` の絵）ので、
幅を広げても E2E の「狭い画面のボタンは 44px 以上」には触れない。

## 状態の印と凡例を外した（Task 10）

### なぜ外したのか（実測）

- **印は行ごとに引いていない。** 宛先ごとの絞り込みが効いている間だけ、返ってきた行
  すべてへ同じ印を被せる（`Photos.tsx` の `impliedStatus`）。だから 1 つの画面に
  2 種類の印が並ぶことがなく、**印が出るときは必ず全部同じで、それは直前に押した
  絞り込みチップが言っていることの繰り返し**になる
- **凡例は絞り込みに関係なく常に出る。** 印が 1 つも出ない「すべて」の画面でも、
  4 種類の説明だけが並んでいた
- `MediaTile` へ `status` を渡している場所は**リポジトリ全体で 1 か所**だけ

**「凡例を印が出るときだけ出す」では足りない。** それでも印はチップの繰り返しのままで、
画面に情報は増えない。「すべて」でも行ごとの状態を出す道は、`GET /media` が行ごとの
宛先ごとの状態を返していないので**別の設計**になる。よって印ごと外した。

### 消したテスト 3 本の判定

削除タスクなので、**消す 1 本ずつについて「何を守っていたか」「それは今も在るか」**を
書かせた。**3 本とも主題ごと消えた**ので、観測の付け替えは 0 本だった。

| 消したテスト | 何を守っていたか | 判断 |
| --- | --- | --- |
| 「宛先ごとの絞り込みが効いているときだけ、状態の印を出す」 | `impliedStatus` の分岐そのもの | 分岐も観測対象も両方消える。**同じ場所を「印が出ないこと」の網に置き換えた** |
| 「絞り込みを変えて読んでいる間は、前の行に新しい印を付けない」 | `!media.stale` の門 | 門の唯一の出力（`impliedStatus`）が消え、`media.stale` の読み手が `Photos.tsx` に 1 つも無くなる。**「観測手段が消えた」より強い理由**でレビューが削除を追認した |
| 「送れなかったものには、その印を出す」 | `.mark.failed` が出ること | 観測対象そのものが無くなる |

計画に無かった削除が 1 つある: `.lg`（凡例の丸のスタイル）。`.legend` を消すと使う場所が
無くなるので、grep で確かめたうえで一緒に消した。
