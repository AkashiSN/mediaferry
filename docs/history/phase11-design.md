# Phase 11 の設計 —— 実機で触って出た 13 件を、直せる形に割る（2026-08-25）

**実機を一通り触った利用者のレビューから始まる。** 現在の仕様は
[`../design.md`](../design.md)、そう決めた理由は [`../decisions.md`](../decisions.md)
にある。ここにあるのは**なぜこの形にしたか**で、実装の手順は `phase11-plan.md`
（これから書く）にある。

**13 件すべてを実サーバで再現し、原因を実測で確かめてある。** 見立てで書いた項目は
無い。確かめ方は[この設計の土台](#この設計の土台--見立てではなく実測)にある。

## 何を直すのか

**利用者の言葉では 13 件。同じ画面の話が離れて出てくるので、性質ごとに並べ
直した**（章の番号がその割り方にあたる）。

| | 利用者の言葉 | 実際に起きていること |
| --- | --- | --- |

| R6 | 確認ダイアログのタイトルと内容の隙が狭い／情報量が少ない | リセットで `h1,h2,h3` も `p` も `margin: 0`、`.dialog` に `gap` も無いので**間隔が 0**。`upload` の本文は件数・合計・宛先の 3 行だけ |

| R10 | つなぐ画面で、結合済みのものを未結合のように出さないでほしい | 黄色（`.wn`）は結合状態と無関係に `gapSeconds` だけで付く。見出しも「N つに分かれています」のまま、本文も「確かめてから決めてください」と**決める前の文**が出る |
| R11 | 設定から飛べるのに、戻るがホームになっている | 「ホームへ」= `/card`・`/merge`・`/approve` の 3 つ。「設定へ」= `/settings/*` の 5 つ |
| R12 | 設定というラベルも要検討。設定なのは詳しい設定だけ | 「詳しい情報」の 7 項目に、作業画面 3・記録 3・設定 1 が混ざっている |
| R13 | リセット画面がほしい。消えた写真の枚数を保持しているから | 枚数の件と、段階的なリセットは**別の話**（[6 章](#6-リセット--まず-1-つ塞がっている)） |

**加えて、レビューには無かった壊れ方が 4 件見つかった。**

| | 症状 |
| --- | --- |
| N1 | **つなぐ画面で、ファイル名が画面の外へ 30px はみ出す**（390px 幅）。カードの幅 968px のうち `.acts` が 552px、`.parts` が 108px を取り、本文が 242px しか残らない |
| N2 | `ul` の既定の `padding-left: 40px` が残っている（リセットは `margin` だけ）。つなぐ画面の狭い本文欄と、確認ダイアログの箇条書きから取られている |
| N3 | `a` の下線がリセットされていない。ボタンの形をしたリンクにも下線が付き、写真詳細の「元になったファイル」は **`rgb(0,0,238)` ＝ ブラウザ既定の青** |
| N4 | 作業の履歴が、終わった作業の要約文を出さない。一覧は「スキャン／完了／終わった日時」だけで、`スキャン完了: …` は**画面を開いていた間に届いたぶんしか描かれない** |

## この設計の土台 —— 見立てではなく実測

**E2E と同じ実サーバを立て、ブラウザに描かせて測った。** mock では分からない
（jsdom は `styles.css` を解析しないので、**528 件の web テストのどれも CSS の色も
寸法も観測できない**。`../development.md` の持ち越しにある）。手順は
[`../development.md`](../development.md) に足す。

**見立てが 2 件外れた。** 読みだけで書いていたら、直しどころを間違えていた。

- R5 を「本文の 15px がそのまま出ている」と読んだが、実測は **22.5px**。原因は
  文字サイズの指定漏れではなく、**セクション見出しにクラスが付いていないこと**だった
- R4 を「狭い画面だけ」と読んだが、**1280px でも折り返していた**

## 1. 見た目の不具合 —— 判断が要らないもの

R1〜R6 と N2・N3 は、原因が 1 つに定まっていて、直し方に選択の余地が無い。

| | 直し方 |
| --- | --- |
| R1 | 「やめる」を `div.row` で包む（他の 3 画面と同じ形） |
| R2 | 縦並びの chip を作る。**`.chip` そのものを縦にしない** —— 写真タブの絞り込みが同じクラスを使っており、そちらは 1 行が正しい |
| R3 | プリセットの `padding` と最小幅を下げ、送るもののタイルとの落差を詰める |
| R4 | info の `<p>` に `.grow` を付ける |
| R5 | セクション見出しを `.sechead` で包む（他の画面と同じ）。行は名前と状況を 1 行に保つ形へ |
| R6 | `.dialog` に縦の `gap` を入れる（`h2` 直下だけの余白ではなく、ダイアログ全体の規則として） |
| N2 | `ul` の `padding-left` をリセットに足す |
| N3 | `a` の `text-decoration` をリセットし、リンクの色をトークンから取る |

**R4 の理由は、`.grow` を足すと直るという結果ではなく、なぜ縮まないかにある。**
flex は**行に詰めるかどうかを flex-basis で判定する**。ここでは `flex-basis: auto`
＝ max-content（320px）で、残り幅 288px に入らないので、**縮む前に改行される**。
`.grow` は `flex: 1`（basis 0）なので、まず行に入ってから縮む。同じ形の `.rowtop`
が他にもあるので、**`.rowtop` の中の本文には `.grow` を付ける**を規則として書く。

### R6 の後半 —— 確認に何を出すか

**「取り消せない」と書いてあるのに、確認に出るのは 3 行しかない。** 何を足すかは
`upload` に限った話ではないので、[採らなかった案](#採らなかった案)に整理してある。
この Phase では**送り先ごとの内訳と、対象の内訳（原本／つないだ動画）**を足す。
どちらも画面が既に持っている値で、新しい API は要らない。

## 2. つなぐ画面は「まだつないでいないもの」だけにする

**利用者の指摘（R10）は、色の話ではなく、画面が何のためにあるかの話だった。**

いまの `/merge` は `GET /merge-groups` を無条件で引くので、`detected`（未結合）・
`merged`（結合済み）・`failed`（失敗）が同じ形で並ぶ。結合済みのグループにも
`gapSeconds` の判定が走り、空白が測れれば黄色が付き、見出しは
「**2 つに分かれています**」、本文は「**別の撮影かもしれないので、確かめてから
決めてください**」——**もう決めた後のものに、決める前の文が出る。**

### 決めたこと

**`/merge` は「これからつなぐもの」だけを出す。** 残すのは `detected` と `failed`。
`merged` は「つないだ動画」なので、**写真タブの `/photos?role=derived` へ寄せ、
1 本ごとの操作はくわしく画面（`/photos/:id`）へ移す。** 記録を「つないだ後の
後片付け」へ寄せた Phase 9 の判断と同じ形で、`/merge` にはリンクだけを置く。

### 落とせない点が 2 つある

1. **「中身を見て、これを使う」は、検証に落ちた結合済みグループにしか出ない。**
   `SENDABLE_CLAUSE` は `passed` か `adopted_at` を見るので、**この入口を一緒に
   移さないと、検証不合格の動画を送る手段が消える。** `/merge` から `merged` を
   外すのと、くわしく画面に採用を置くのは、**同じ Task でなければならない。**
2. **`failed` は「まだつないでいない」側**なので `/merge` に残す。結合に失敗した
   組は §10 の既定の一覧から外れており、「個別に送る」もここにしか無い（裁定 12）。

`superseded_by_id` が入った組は既に操作できず表示だけなので、`/merge` からは外す
（辿り道は「使っていないファイル」にある）。

### N1 も同じ章で直す

**本文が 242px しか残らないのは、`.acts` の 4 つのボタンが 1 行に並んでいるから。**
`merged` を外すと `detected` の操作は「つなぐ」「構成を変える」「これは別々」の
3 つになり、圧迫は減る。**ただし減るだけでは直らない** —— ファイル名は `/` で
折り返さないので、`.ident`（`overflow-wrap: anywhere`。この用途のために既にある）
を当て、操作は本文の下へ落とす。

### なぜ試験が捕まえなかったのか

**網は 2 つあり、どちらも構造的に届いていなかった。**

| 網 | なぜ素通りしたか |
| --- | --- |
| `spilling`（文字が入れ物からはみ出さない） | `main *, nav *` を巡るので `/merge` も対象だが、見ているのは**末端の要素が自分の箱に収まるか**。今回は span が親の箱を超えており、span 自身は 345px を確保しているので `scrollWidth == clientWidth` になる |
| `crossingCardEdges`（カードの中身が箱の外に出ていない） | `main section.card` しか見ない。つなぐ画面のグループは `article.card` なので `cards === 0` となり、**この画面では何も主張していない** |

**さらに、どちらの検査も「グループが並んだ `/merge`」を一度も見ていない。**
合成カードでは検出が候補を作れず、`journey` が手で組んだ組はその場で「これは別々」
に戻すので、幅の検査が回る時点では 0 件のことが多い。**画面の状態を作ってから
測る網が要る。**

## 3. 語彙 —— 「承認」を捨てて「信頼」に寄せる

R7 は文言の揺れに見えるが、**同じ語が 2 つの操作を指している**のが本体。

- カードの `trust`：本文が「承認」、ボタンとダイアログが「信頼」
- 日時の `approve`（`/approve`）：画面の名前は「日時の確認」だが、コードも本文も
  「承認」

語彙表（`web/src/test/vocabulary.ts`）は既に「承認待ち → 確認」と定めている。
**カードの文脈から「承認」を落とし、「信頼」に統一する。** そのうえで
`FORBIDDEN` に「承認」を足し、**画面の言葉としては使わない**ことを試験で固定する。

## 4. 「設定」の中身を割る

R11（戻り先）と R12（ラベル）は同じ根から出ている。**「詳しい情報」が、性質の違う
3 種類を同じ形で並べているから、戻り先も決まらない。**

| 性質 | いま「詳しい情報」にあるもの |
| --- | --- |
| 作業 | つなぐ・日時の確認・接続中のカード |
| 記録 | 作業の履歴・つないだ後の後片付け・使っていないファイル |
| 設定 | 詳しい設定 |

**作業の 3 つは、ホームの「やること」からも入る。** だから戻り先を `/settings` に
固定すると、今度はホームから来た人が設定へ飛ばされる。**入口が 2 つあることが
先で、戻り先が決まらないのはその結果。**

### 決めたこと

**「詳しい情報」を、性質ごとに分けて名前を付ける。** 作業への常設の入口は
（0 件のときにも入れる必要があるので）残すが、記録・設定とは別の見出しに置く。
そのうえで、**作業の 3 画面の戻りは「どこから来たか」で決める** —— 遷移元を
`location.state` で渡し、無ければホームへ。ブラウザの履歴には頼らない（URL を
直接開いた場合と、画面内の遷移を区別できないため）。

**ナビの「設定」という名前は変えない。** 3 項目のナビは §13 の決めごとで、
ここを増やすと画面の骨格が変わる。**直すのは中の並びであって、タブの名前ではない。**

## 5. カードの中身に「何が入っているか」を出す

R8 と R9 は、**同じ 1 本の API で賄える。**

いま `/devices` が返すのは `size_bytes`（ボリュームの総容量）と `pending_count`
だけで、**取り込み待ちの合計サイズも、ファイルの一覧も無い。** `source_entry` を
返す経路は 1 つも無い（`api/` に参照が無い）。

### 決めたこと

**カード 1 枚の中身を返す経路を足し、カードの中身の画面がそれを描く。** 出すのは
ファイル名・サイズ・撮影時刻と、取り込み待ちの合計。**ボリュームの総容量には
ラベルを付け、写真側の合計と並べて出す**（どちらのサイズか、読めばわかる形にする）。

**サムネイルは出さない。** 未取り込みのファイルの絵は NAS に無く、カードから直接
読んで作ることになる。**まずファイル名で足りるかを実機で確かめてから決める** ——
「どのカードか分かる」が目的なので、名前と日時で足りる見込みが高い。

## 6. リセット —— まず 1 つ塞がっている

R13 には**症状と要望が両方入っている。**

**症状（スキャン後にカードから消えた写真の枚数が残る）は、いま作業ツリーにある
未コミットの変更で塞がっている。** 実サーバで確かめた。

```
カードに 2 件足す → スキャン        →「EOS_DIGITAL から 2 件を取り込む」
カードから 2 件消す → スキャン      → 札が消える
job_event: スキャン完了: 新規 0 件 / 取込済 4 件 / 消えた 2 件
source_entry: 6 行 → 4 行
```

**この Phase は、その変更を前提に置く。** リセット画面で消して回るのではなく、
**スキャンが自分で辻褄を合わせるのが正しい形**だから（「無い」には観測を要求する、
という Phase 9 の規則と同じ）。

### 残る要望 —— 段階的なリセット

**要るのは「消えた行の掃除」ではなく、「作り直したい」ときの入口。**

#### Phase 9 の削除の規則は、ここには掛けない

`DELETE /media/{id}` は「Immich に生きていない `derived`」しか消せない。**リセットは
この規則を迂回する。**

**理由は、規則が守っている対象が違うから。** 1 件の削除で守っているのは
**「Immich にしか無いものを、mediaferry から消させない」**という不変条件で、
利用者が 1 件ずつ判断している場面の話である。リセットは
**mediaferry が持っているデータを捨てる操作**で、Immich にある資産は対象ではない
——**消しに行かないし、消えない。** 「Immich にあるかどうか」は、この操作の可否に
関係しない（利用者の裁定、2026-08-25）。

#### ただし、取り消せない副作用が 1 つある

**送信の記録（`upload_record`）を捨てると、「自分が上げた」という証明が戻らない。**

次にもう一度送ると、初回の `checking` は当然 `reject`（重複）を返す。そこから
`origin` は **`pre_existing`** に決まり、`first_check_result` は**不変**なので
**以後どうやっても `created_by_us` には戻らない**（§9.10）。効くのは 3 つ。

| | リセット前 | リセット後に送り直すと |
| --- | --- | --- |
| ファイルの本体 | —— | **送らない**（`asset_known` へ進む。帯域も時間も食わない） |
| 撮影日時の補正 | 自動 | **`awaiting_datetime_approval` に積まれ、1 件ずつ承認が要る** |
| スタック | 束ねる | **`skipped`**（どちらかの `origin` が `created_by_us` でないと束ねない） |

**だから段階は 4 つに割る。** 送信の記録を「記録だけ」と同じ段に置かない ——
どちらも「記録」だが、**片方は作り直せて、片方は戻らない。**

| 段階 | 何が消えるか | 取り消せるか |
| --- | --- | --- |
| 作業の記録 | 作業の履歴・破棄した組み合わせの記録 | **作り直せる**（再スキャン・再検出） |
| 送信の記録 | `upload_record` | **戻らない。** Immich の資産は残るが、日時の補正とスタックが以後効かなくなる |
| 取り込んだファイル | `library/` と `derived/` の実体 | **カードに元があれば取り込み直せる** |
| すべて | DB ごと | 取り消せない |

**確認の本文には、Immich が無傷であることと、証明が戻らないことの両方を書く。**
「Immich からは何も消えません」だけだと、代償が無いように読める。

### N4 も一緒に見る

**枚数が変わった理由が、後から読めない。** 作業の履歴が出すのは「スキャン／完了／
終わった日時」だけで、`スキャン完了: 新規 0 件 / 取込済 4 件 / 消えた 2 件` は
**画面を開いていた間に届いたぶんしか描かれない**（一覧は SSE で受けた最新イベント
だけを添える）。リセットを足すなら、**何が起きたかを後から読める場所**が要る。

## 採らなかった案

**確認ダイアログに、送るファイルの一覧を出す。** 200 件のこともあるので、
ダイアログが一覧の画面になる。件数と内訳で足りる。

**`/merge` から `merged` を外さず、色と文言だけを分ける。** 「結合済みです」と
書き換えれば黄色は消せるが、**同じ画面に「これからやること」と「もう済んだこと」が
並ぶ構図は変わらない。** 済んだものへの操作（構成を変える・別々にする）は 1 本
ごとの判断なので、1 本を見ている画面に置く方が筋が通る。

**戻り先を `document.referrer` やブラウザの履歴で決める。** URL を直接開いた場合と
区別できず、外から来たときに戻り先が無い。

**「詳しい情報」を全部 `/settings` の下の URL へ移す。** `/merge` と `/approve` は
ホームの「やること」からも入るので、URL を設定の下へ動かすと**ホームからの導線が
設定の中を指す**ことになる。名前と並びの問題を、URL の階層で解こうとしない。

## 範囲の外

- **`uploads.py` の「持ち主のグループ」6 か所目**（`../development.md` の持ち越し）。
  つなぐ画面を触るが、`_choose_derived` は送信側なので別
- **CSS の色の規則を見る仕掛け**（同持ち越し）。N3 はトークン外の色を 1 か所直す
  だけで、**規則として見る網は別の判断**

## 試験の方針

**今回の 17 件のうち、既存の網が捕まえたものは 1 件も無い。** 全部緑のまま利用者が
