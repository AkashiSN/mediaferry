## 実機で分かった ffmpeg の挙動

- **concat demuxer は data ストリームを運べない。** `-map 0:4`（`tmcd`）を渡すと
  `Cannot map stream #0:4 - unsupported type` で即座に落ちる。**DJI は `tmcd` を
  持つので、concat 経路が成立する余地が無かった**（毎回 TS へ落ちていた）
- **TS 経路は `hvc1` を `hev1` に変える。** HEVC のパラメータセットの置き場所が
  変わるので、Apple 系で再生できないことがある。**通らずに済むこと自体に価値がある**
- **concat 経路の出力には `tmcd` が残る。** `-map` から外しても、mp4 muxer が
  コンテナのメタデータから作り直す。だから `streams` 検査は一致ではなく
  「足りない／増えた」で見る

## 環境と運用で分かったこと

- **`latest` は引き直されないことがある。** TrueNAS の Custom App は手元にある
  同名のイメージを使うので、検証中は `:sha-xxxxxxx` で固定する方が確実
  （どの版を試したかも残る）
- **`library` などを ZFS データセットに分けてはいけない。** 公開が `link(2)` なので
  同じファイルシステムに要る。`preflight` でデバイス番号を先に見ると早い
- **開発 LXC から実機の API に直接届く。** セッション cookie をもらえば、
  チェックリストを API で進められる（CSRF は二重送信 cookie）

**検査もサイズも同じ**なので取り違えても気づけない。しかも「消したはずのグループが
1 つ生き返る」という具体的な害が出る。

**リストアは手順どおり動いた。** バックアップ後に作った派生物は**孤立として報告され、
実体は消えなかった**。退避した元ファイルには `missing_at` が立ち、戻して起動し直すと
`{'restored': 1}` で解除された。

**手順書に足りなかったもの**（いずれも実際に踏みかけた）:

1. **`-wal` / `-shm` は「戻さない」ではなく「消す」。** 残すと「古い DB に新しい WAL」の
   組み合わせになる
2. **所有者と権限の復元。** root で `cp` すると `root:root` になり、非 root の
   アプリが書けなくなる
3. **バックアップを `DATA_ROOT` の中に置かない。** アプリが読み書きできる領域なので、
   侵害されたときにバックアップごと触れる（これは実測ではなく読んで気づいた）

**この検証で、入れたばかりの回収ログが実際に役に立った。** 何が起きたのかが
`docker logs` の 1 行で分かる（それまでは無言だった）。

## 11 番の実測 —— 前提が崩れた（2026-08-21）

**`timestamps.py` は「カードの時刻欄に UTC オフセットが無い（または 0）」を前提に、
mtime の UTC 表現を壁時計として使っている。DJI Osmo Pocket 4 ではこれが成り立たない。**

公開時にソースの mtime をそのまま保つので、**カードをマウントし直さずライブラリ側で
測れる**（`test_the_published_file_keeps_the_source_mtime`）。

```
DJI_20260808125404_0002_D.MP4   長さ 1518.0 秒
  ファイル名の開始（現地）: 12:54:04+09:00
  録画終端（現地）        : 13:19:22+09:00
  mtime を +09:00 で描画  : 13:19:24+09:00   終端との差 +2.00 秒
  mtime を UTC で描画     : 04:19:24+00:00   終端との差 -32,398 秒（9 時間）

DJI_20260815155045_0029_D.MP4   長さ 89.5 秒
  mtime を +09:00 で描画  : 15:52:16+09:00   終端との差 +1.83 秒
  mtime を UTC で描画     : 06:52:16+00:00   終端との差 -32,398 秒
```

**mtime は「録画終端の現地壁時計」を正しい瞬間として持っている**（+2 秒はファイルを
閉じるまで）。**DJI は exFAT の `OffsetFromUtc` を書いている。**

### 直すべき 3 か所（連動している）

1. **`timestamps.py::_wall_clock` の mtime fallback。** ファイル名に時刻を持たない
   ファイル（DJI なら `PANORAMA/PANO_0001.JPG`）の `captured_at` が**オフセットぶん
   ずれる**。今回のカードには写真が無かったので表に出ていないだけ
2. **`publisher._collision_stamp`。** 元ファイルの衝突接尾辞が同じだけずれる。
   タイムゾーンを渡す配管が要る
3. **`merger._recording_end_ns`。** `decisions.md` は「派生物の mtime は取り込みの
   mtime と同じ表現にする」としていたが、**測ったら取り込みの mtime は真の瞬間**
   だった。つまり**いまは派生物の方がオフセットぶんずれた epoch を持っている**
   （やり直した結合物の接尾辞 `_20260808145223` が現地の 14:52:23 と一致していたのが
   その証拠）

**片方だけ直すと `library/` と `derived/` で接尾辞の壁時計がずれる** ——
`decisions.md` がまさにその懸念を書いていた。3 つを同時に変える。

**リセット後の再取り込みが検証の機会になる。** 直さずに取り込むと、写真を足した
ときに誤った `captured_at` が入り、再計算をかけることになる。

### 直した（2026-08-21）

3 か所を同時に変えた。**失敗するテストを先に書いて、失敗を確認してから**直している。

| 直したもの | 変えた内容 |
| --- | --- |
| `timestamps._wall_clock` | mtime の fallback を、UTC 表現ではなく**解決した TZ を付けた aware な値**にする。TZ の解決を壁時計より先に動かした（`timezone_policy: none` は描画に使う TZ が無いので UTC のまま）。**naive の壁時計へ落とさない** —— 落として `_attach_offset` で付け直すと、DST の戻りでどちらの 1 時間かを失う（Europe/Berlin の `2026-10-25T01:30:00Z` が 1 時間ずれた。codex のレビューで見つかった） |
| `publisher._collision_stamp` | `captured_at` を解決したのと同じ TZ（`CapturedAt.tz`）で描画する。**配管は増えていない** —— 手順 5 で `captured` が既に手元にある |
| `merger._recording_end_ns` | `captured_at` の瞬間をそのまま epoch にする（`.replace(tzinfo=UTC)` をやめた）。オフセットの無い値だけ UTC と見なす（放っておくとシステムの TZ で読まれる） |

**再計算（`recompute_timestamps`）の入力は `media_file.mtime_ns`**（公開した実体に
固定された値）で、`source_entry` から引くのは**カード上の原名だけ**。後で再スキャン
しても値が動かないので、この形でよい。

**ただし既存 DB は自動では直らない。** プロファイルの定義（JSON）は変わっていないので
`ProfileRegistry._upsert_revision` は新しい版を作らず、既存行の
`captured_at_revision_id` は「現行版で算出済み」のまま残る。**手で
`POST /profiles/{slug}/recompute` を叩けば**同じ版でも全行を巡るので `original` の
`captured_at` は直る。**直らないもの**（再計算は日時の 5 列しか触らない）:

- 旧 `_recording_end_ns` で付けた**派生物の実ファイルの mtime と `media_file.mtime_ns`**
- 旧 `_collision_stamp` で**すでに確定した公開名**（ライブラリは不変。§7）

**検証環境はリセットして取り直す前提**なので、その環境ではここで閉じる。実データを
持ったまま上げる利用者が出たときは、影響するプロファイルの明示的な再計算と派生物の
作り直しを手順に書く。

### mtime の意味はプロファイルが宣言する（`mtime_semantics`）

**「mtime は真の瞬間」は、`OffsetFromUtc` を書く媒体でしか成り立たない。** valid bit が
立っていない媒体では、exfat ドライバはマウントの `time_offset`（既定 0）で epoch を
合成するので、その値は**現地の壁時計を UTC と見なした疑似 epoch**になる（FAT32 には
そもそもオフセットの欄が無い）。そういうカードを `force_offset` のプロファイルで
取り込むと、fallback だけがオフセットぶんずれる。

**1 機種の実測を全機種の契約にはできない。** API は `POST` / `PUT /profiles` を公開して
おり、任意のユーザ定義プロファイルが `force_offset` を選べる。しかも**確定済みの公開名と
派生物の mtime は再計算では直らない**ので、事故が出てから欄を足すと不可逆な部分が残る
（codex のレビューでの指摘。利用者の判断で、いま足した）。

| 値 | 意味 | 該当する媒体 |
| --- | --- | --- |
| `wall_clock`（既定） | 現地の壁時計を UTC と見なした疑似 epoch | FAT32、valid bit の立たない exFAT |
| `instant` | 真の瞬間 | `OffsetFromUtc` を書く exFAT（実測した DJI） |

**既定を `wall_clock` にした。** 宣言の無い定義（この欄より前に作られたユーザ定義
プロファイル）に「瞬間」を仮定すると黙ってずれる。ビルトインで明示するのは実測した
`dji-osmo` だけで、`canon-eos` と `generic-dcim` は `timezone_policy: none` なので
どちらでも同じ値になる。

**宣言は 3 か所に効く**（`_wall_clock` の fallback・`_collision_stamp`・
`_recording_end_ns`）。規則は `timestamps.mtime_wall_clock` と `timestamps.mtime_ns_of`
の 2 つに閉じてあり、3 か所はそれを呼ぶ。

**ビルトインの定義が変わったので、`sync_builtins` が `dji-osmo` の新しいリビジョンを
作る。** 既存行の `captured_at_revision_id` は前の版を指したままになるので、画面から
再計算をかける手がかりになる。

**変異試験は 8 件すべて検出**（`tz=zone` を `UTC` に戻す、接尾辞に TZ を渡さない、
`_recording_end_ns` を旧実装に戻す、naive の保険を外す、など）。素通りは無い。

**テストの前提もずらした。** `test_recompute.py` の `ns()` は「カード上の壁時計を
UTC 表現の epoch にする」ヘルパだったので、**真の瞬間**を書く `ns()` と、
**その TZ の壁時計**を書く `ns_local()` に分けた。分けないと、`force_offset` の
fixture と `timezone_policy: none` の fixture が同じヘルパを違う意味で使うことになる。

## 送信のリースが 61 秒で切れた —— 実機でしか出ない不具合（2026-08-23）

**残りをまとめて送ったら、ジョブが 61 秒で `failed` になった。**

```
ジョブ f11a20c9… のリースが無効（キャンセル・失効・別の所有者）
12:55:42 → 12:56:43（61 秒）。リースは 60 秒
```

### なぜ今日まで出なかったか

送信は `with_lease_pulse` でリースを延ばすが、**心拍を打つのは「1 回の送信が
`HEARTBEAT_INTERVAL`（20 秒）より長かったとき」だけ**。

```python
thread.join(timeout=HEARTBEAT_INTERVAL)
if not thread.is_alive(): break   # 20 秒以内に終わったら、打たずに抜ける
```

そして**送信のループに `ctx.heartbeat()` が無かった**。つまり **1 件ずつが速いと
リースが一度も延びない**。

| 送ったもの | 所要 | 通ったか |
| --- | --- | --- |
| 写真 10 枚 | 3 秒 | 通った（60 秒以内に終わる） |
| 440 MB 動画 | 3 秒 | 通った |
| **71.2 GB 結合物** | 364 秒 | 通った（**1 回が長いので 20 秒ごとに心拍**） |
| **小さい動画を連続** | **61 秒で死亡** | どの 1 件も 20 秒未満 → 心拍ゼロ |

**いちばん普通の使い方（写真を何十枚も送る）で必ず踏む。** 1 枚 1 秒なら
60 秒で落ちる。`recheck.py` と `recompute.py` はループの各回で `heartbeat` を
打っており、**送信だけが打っていなかった**。

### 直した

送信ループの先頭に `ctx.heartbeat()` を 1 行。回帰テストは
`test_uploader.py::test_many_quick_sends_do_not_lose_the_lease`（1 件 0.6 秒 ×
5 件、リース 1 秒。**実機と同じ `LeaseLost` で赤くなることを確かめてから**書いた）。

**変異試験で実装が 1 行減った。** 最初は `recheck.py` に合わせて
`assert_lease()` も置いたが、**消してもテストが 1 本も落ちない**。調べると、
キャンセルはループ先頭の `cancelled()` が見ており、失効と横取りは `heartbeat`
自身が `LeaseLost` で捕まえる（`extend_lease` は満期前の行しか更新しない）。
**保険に見えて誰も守っていない行**だったので落とした。

### 副産物 —— `origin = unknown` を実機で初めて踏んだ

落ちたジョブは、**送信を終えた直後に記録を書く前に死んだ**。Immich にはファイルが
あるのに、こちらの記録は未完了。再送すると Immich は `duplicate` と答え、
コードは `unknown`（自作と証明できない）と判定した。

```python
if upload_status == "created":      return "created_by_us"
if first_check_result == "reject":  return "pre_existing"
return "unknown"   # ← 初回が accept だったことは自作の証明にならない
```

**安全弁は正しく働いた** —— 証明できない資産の日時は書き換えず、承認を求めた。
画面から承認したら「日時の補正を承認して書き戻した」で通り、**承認の経路
（`awaiting_datetime_approval` → 書き戻し）も実機で初めて動いた**。

**ただし画面の文言が嘘だった。** 「先に誰かが Immich へ上げていた写真です」は
`pre_existing` の説明で、この record の `origin` は `unknown`。**実際はほぼ確実に
こちらが上げたもの**で、家族には「知らない人が上げた写真がある」と読める。
持ち越しに入れた。

## 10 番（取り外し）—— 合格（2026-08-23）

**画面の「取り外す」を押しても、何も起きなかった。** これは正しい:

```python
def close(self, volume_instance_id: str) -> None:
    if volume_instance_id in self._open:
        raise VolumeBusy("実行中のジョブがこのボリュームを使っている")
```

**掴んでいるジョブが無ければ本当に何もしない。** カードはジョブが要るときだけ
読み取り専用でマウントし、ジョブが終わればその場で外すので、**押した時点で
既に安全に抜ける状態**だった。200 は返っている。

### 物理的に抜いた後の `dmesg`

```
usb 2-4: USB disconnect, device number 8
rndis_host 2-4:1.0 ...: unregister 'rndis_host'
sd 33:0:0:0: [sdj] Test Unit Ready failed: hostbyte=DID_NO_CONNECT
sdj: detected capacity change from 226656280 to 0
sd 32:0:0:0: [sdk] Synchronize Cache(10) failed: hostbyte=DID_NO_CONNECT
```

**`I/O error` もファイルシステムのエラーも 1 行も無い。** `DID_NO_CONNECT` は
「もう居ない相手に話しかけた」で、消えた装置をカーネルが確認しにいっただけ。
`Synchronize Cache failed` は USB ストレージを予告なく抜けば必ず出る行で、
**読み取り専用マウントなので流し込むものが無い**ことが裏付けられた形。

**ついでに分かったこと。** `rndis_host` の登録解除も出ており、**このカメラは
USB でネットワーク機器としても見えている**（マスストレージだけではない）。
装置は 2 つ（`sdj` = 108 GiB の内蔵、`sdk` = SD カード）で、カーネル側でも
別々に見えている。

`/devices` は空になった。

### ただし、画面は何も言わない（持ち越し）

このボタンの値打ちは**返ってくる答えそのもの**にある —— 「いま抜いて大丈夫」か
「まだ抜かないで」か。ところが**成功したときに何も言わず、一覧を読み直すだけ**
（`CardDetail.tsx` / `Home.tsx` の `act`）。カードは挿さったままなので一覧にも
残り、**画面には変化が一切ない**。利用者には**どちらだったのか分からない**。
「取り外す」という名前も、何かが起きる（アンマウントされる）ように読める。

### 10 番 —— カードから消したファイルの行が残り続ける

**利用者がカードを抜き、PC で古い写真を消して挿し直したら、`pending_count` が
1488 のままだった。** 挿し直した後のスキャンは 68 件（`IMG_8364`〜`IMG_8397` の
34 組）しか見つけていない。

根本原因は `Scanner.scan` が**見つけたファイルの行しか触らない**こと。前回作られて
今回現れなかった行を、消しも印も付けもしない（本番コードに `DELETE FROM
source_entry` が 1 つも無かった）。`observed_at` は毎スキャン更新していて判定材料は
揃っているのに、誰も使っていなかった。**`design.md` §9.5 の照合表にも「カードから
消えたファイル」の行が無く、実装ではなく仕様の抜けだった。**

再挿入で引き継がれるのは `resolve_volume_instance` が `(fs_uuid, fs_type,
size_bytes)` で同じ `volume_instance` を引き当てるからで、**これ自体は意図どおり**。

害は 4 段階で効く。

| | 起きること |
| --- | --- |
| 1 | `pending_count` が実体より多い（1488 対 68）。画面は「1488 件」と言う |
| 2 | 取り込みの空き容量検査 `needed` に消えたぶんも入る。空きが足りなければ**1 件も始まらず** `NotEnoughSpace` |
| 3 | 始まっても `ORDER BY rel_path` で先頭は消えた `IMG_7649.CR2`。ENOENT は `_DEVICE_GONE` に無いので `continue` し、1420 件が `failed` に落ちて最後に `ImportFailed` |
| 4 | `state='failed'` も取り込み対象（`state IN ('seen','failed')`）なので**残り続け、以後の取り込みが毎回失敗する。画面から消す手段が無い** |

直し方は `decisions.md` の「取り込みと公開」にある。**消す前に 1 件ずつ開いて
「無い」を確かめる**のが要点で、列挙に現れないこと（`scan.extensions` を狭めた）と
カードから消えたことを区別する。

**変異試験は 7 件中 7 件を検出した。** 当初「`observed_at < スキャン開始` の絞りは
検出できない」と記録したが、**これは測った時点が古かった**（掃除中の心拍とその
テストを足す前に測り、足した後に測り直していなかった）。絞りを外すと候補が増え、
心拍の回数を厳密に見ている 2 本が落ちる。**codex のレビューが当て直して発覚した。**
報告を鵜呑みにさせない依頼が、そのまま効いた例。

**実機で直ったことを確かめた**（`sha-0b44fb7`）。入れ替え後の最初のスキャンが

```
スキャン完了: 新規 68 件 / 取込済 0 件 / 消えた 1420 件
```

を出し、`pending_count` は 1488 から 68 へ落ちた。**DB を手で触る必要は無かった。**

### 10 番のレビューで、直したはずの掃除から 2 件出た（2026-08-25）

**codex にレビューを頼んだら、`5db4dff` そのものに実害が 2 件見つかった。**
どちらも「テストは全部緑」の状態で残っていた。

**1. 一時的な I/O 障害でも消していた。** `exists_beneath` は全 `OSError` を
False にするので、`EACCES` / `EIO` / `EMFILE` / `ESTALE` でも「無い」に見える。
さらに `iter_media_files` の `_walk` は**開けないディレクトリを黙って
`return` する**ので、部分木ぶんが列挙から落ちて**そのまま掃除の候補になる**。
「存在を確かめてから消す」と書いておきながら、**確かめられていなかった**。

「無い」と言い切れる `errno`（`ENOENT` / `ENOTDIR`）だけを削除の根拠にする
`probe_beneath` を足し、確かめられなかった件数は警告としてジョブに残す。

**2. 一致するファイルが 0 件のカードでは、キャンセルを観測できなかった。**
`ctx.cancelled()` は列挙の中にしか無いので、列挙が 1 度も回らないと降りたことに
気づけず、そのまま掃除する。**掃除は破壊的なので `mark_scanned` より厳しく見る。**

### 直している最中に、自分で 1 件作った

`exists_beneath` を `probe_beneath` に載せ替えるとき、**真偽を反転させた**
（`is True` と書くべきところを `is False`）。部分的なテストでは気づかず、
変異試験で当てて初めて**どのテストも落ちない**ことが分かった。

`exists_beneath` の呼び出し元は `_known_files_survive` だけで、**その真偽を
固定するテストが 1 本も無かった**。既存の `test_a_reformatted_card_drops_back_to_low`
は `published` な行を 1 件も作らないので、`if not rows: return False` で先に
決着しており、存在判定に届いていない。

両方向（既知のファイルが残っていれば `high` / 消えていれば `low`）を固定する
テストを足した。**反転の変異は、この 2 本で落ちる。**

**教訓は「呼び出し元が 1 つしか無い述語は、真偽が誰にも見られていないことがある」。**

## Canon の 14〜17 番が決着した（2026-08-26）

**利用者がカードをカメラで初期化し、写真 5 組と動画 3 本を撮り直して挿した。**
これで 14〜17 番の題材がすべて揃い、**4 項目とも決着した**。あわせて、Canon の
時刻の扱いが DJI と正反対であること、Immich で動画だけが 9 時間ずれることが
実物で確かめられた。

### カードの姿が変わった —— ラベルが付いている

| | 2026-08-25（PC で焼いた状態） | 2026-08-26（カメラで初期化） |
| --- | --- | --- |
| `fs_label` | **空** | **`EOS_DIGITAL`** |
| 中身 | `IMG_8364`〜`IMG_8397` の 34 組 | `IMG_0001`〜`IMG_0005` の 5 組 + MOV 3 本 |

**`hints.volume_labels: ["EOS_DIGITAL"]` は、カメラで初期化したカードには当たる。**
前回「exFAT で焼いた SDXC にはラベルが付かない」と結論したが、**それは PC で
焼いたカードの話だった**。プロファイル側の値は正しい。

**`volume_instance` も別の行になった。** 初期化で `fs_uuid` が変わるためで、
スキャンが「消えた 0 件」を返したことが裏付けになる（同じ行なら、前回の 68 件が
消えたものとして数えられる）。

### 中身と mtime

| ファイル | 大きさ | mtime |
| --- | --- | --- |
| `IMG_0001` .CR2/.JPG | 24.6 MB / 6.1 MB | 12:33:06 |
| `IMG_0002`〜`IMG_0005` | 各 CR2+JPG | 12:33:47 / 12:34:00 / 12:34:10 / 12:34:24 |
| `MVI_0006.MOV` | 618,422,312 B | 12:36:18 |
| **`MVI_0007.MOV`** | **4,260,142,424 B（3.9675 GiB）** | **12:44:45** |
| **`MVI_0008.MOV`** | 218,782,864 B | **12:44:45** |

**Canon は exFAT の `OffsetFromUtc` を書かない。** 撮影は 12 時台の JST で、
mtime の生値は `12:33:06Z`。**現地の壁時計が UTC の桁としてそのまま刻まれている。**
DJI は書いていた（11 番の実測）ので、**同じ exFAT でも媒体によって逆**になる。
`canon-eos` は `mtime_semantics` を宣言していない＝既定の `wall_clock` なので、
**この形をそのまま正しく扱う**（`core/timestamps.py` の `mtime_wall_clock`）。

> **読み違えに注意。** mtime の生値を「真の瞬間」とみなして JST へ直すと 9 時間
> 進んだ値になる。`captured_at` の `+00:00` は「UTC の 12:33」ではなく
> 「**壁時計 12:33、ゾーンは主張しない**」（`timezone_policy: none`）という記録。

### 17 番 —— 合格。`exifread` は実機の CR2 を読める

取り込んだ 5 組は、CR2 も JPG も `captured_at_source = exif` で、値は
12:33:05 / 12:33:46 / 12:33:59 / 12:34:09 / 12:34:23。**実際の撮影時刻と一致する**
（mtime より 1 秒早いのは、撮影から書き込みまでの差で妥当）。組は 5 組すべて成立。

**前回取り込んだ 68 件が全部 `2026-08-08T13:00:00` で同一だったのは、カメラの
日時が未設定だったため。** 34 枚を同じ秒には撮れないので実装を疑ったが、今回の
5 組が正しく散ったことで切り分いた。**組の判定は Phase 10 以降、時刻を見ない**
ので、この状態でも 34 組すべてが成立していた —— **身元から時刻を外した判断が、
実データで報われた形**になる。

### 16 番 —— 合格。CR2 は Immich に入る

`GET /dashboard` の宛先要約が `complete: 104` / `failed: 0` / `stacked: 34`。
**CR2 が弾かれて `upload_record` に溜まることは起きていない。**

### 15 番 —— `creation_time` は「壁時計に `Z` を付けた」値で、録画の開始を指す

`ffprobe` を app のコンテナで打った（**ホストに ffprobe は無い。イメージには
入っている**）。

```
MVI_0006  creation_time = 2026-08-26T12:35:08.000000Z   duration  69.937
MVI_0007  creation_time = 2026-08-26T12:37:13.000000Z   duration 428.428
MVI_0008  creation_time = 2026-08-26T12:44:22.000000Z   duration  23.023
```

**2 つのことが同時に分かる。**

1. **数字は現地の壁時計なのに `Z` が付いている。** 撮影は 12 時台の JST。
   DJI は真の UTC を書いていた（そしてオフセットを書かない）ので、**ずれる向きは
   同じでも原因が違う**
2. **`creation_time` は録画の開始。** `12:35:08 + 69.937 = 12:36:17.9` が
   `MVI_0006` の mtime（12:36:18）と一致する。**mtime は録画の終了**

**分割された両片は mtime が同一になる。** `MVI_0008` の終端
（`12:44:22 + 23.023 = 12:44:45.02`）が両方の mtime に一致するので、**カメラは
録画を止めた時刻を、分割の全片に書き直している**。`MVI_0007` 自身のデータは
12:44:21.4 で終わっているのに mtime は 12:44:45。

### 14 番 —— 決着。現行の規則では検出できないが、`creation_time` なら分かれる

**現行の 2 条件は、どちらも成立しない。**

| 条件 | 実測 | 判定 |
| --- | --- | --- |
| 前の片が `min_part_size_gib` 以上 | 下限 4 GiB = 4,294,967,296 B に対し実測 4,260,142,424 B | **34,824,872 B（33.2 MiB）足りない** |
| 前の片の終端と次の開始の差が `tolerance_seconds` 以内 | MOV は EXIF が無く mtime へ落ち、**両片の mtime が同一**なので差は −428.428 秒 | 外 |

**`creation_time` を出所にすると、閾値を触らずに正しく分かれる。**

| 継ぎ目 | 前の終端 | 次の開始 | 差 | 判定（`tolerance_seconds: 5`） |
| --- | --- | --- | --- | --- |
| 0006 → 0007 | 12:36:17.937 | 12:37:13 | **+55.063 s** | 外 → **別録画**（正しい） |
| 0007 → 0008 | 12:44:21.428 | 12:44:22 | **+0.572 s** | 内 → **同一録画**（正しい） |

`_RESOLUTION_SECONDS` に `container: 1.0` が要る（`creation_time` は秒までしか
持たない）。丸めで符号がぶれる問題は DJI の 5 パートで踏んだのと同じ形。

**サイズの下限は 3 へ下げる。** 実測 3.9675 GiB は 4 を下回るが、別録画の 618 MB は
3 GiB にも届かないので、区別は保たれる。

### Immich で、動画だけが 9 時間ずれる（実物で確認）

送信後に利用者が Immich を見て確かめた。**写真は 12 時台の JST で正しく、動画は
12 時台の UTC（＝ 21 時台の JST）に並ぶ。**

- **写真が正しいのは**、EXIF にオフセットが無く、Immich が現地時刻として扱うから
- **動画がずれるのは**、Immich が `creation_time` の `Z` を素直に UTC と読むから

`canon-eos` は `fix_datetime_after_upload: false` なので、mediaferry は日時を
書き戻さない。**`true` にするだけでは効かない** —— `core/uploads/decisions.py` の
`datetime_plan` が `policy == "none"` を先に見て「タイムゾーンを解決していないので
補正案が無い」で降りる。**`timezone_policy: force_offset` とセットで要る。**

**`dji-osmo` が既に同じ形で解いている**（「Immich が撮影地の TZ を判定できない。
壁時計にオフセットを付けて書き戻す」）。`canon-eos.yaml` のコメントが
「EXIF にローカル時刻が入るので補正しない」「補正する対象が無い」と書いていたのは、
**写真しか無い前提**だった。MOV があると成り立たない。

### 一覧の並びが、同時刻のときに乱数になっている（利用者が発見）

利用者が写真タブで「`MVI_0007` が `MVI_0008` より左上に来る」ことに気づいた。
`captured_at` が同一（どちらも mtime 由来の 12:44:45）なので tie-break が効くが、
**それは `ORDER BY m.captured_at DESC, m.id DESC` の `id`** ——32 桁の乱数 hex。

```
MVI_0007.MOV  12:44:45  id=7f4bf615…
MVI_0008.MOV  12:44:45  id=7ce62d99…
```

**`7f4b… > 7ce6…` だったから 0007 が先に来ただけ**で、id の出方が逆なら 0008 が
先に来ていた。**同時刻の行の並びは、いま再現性のある意味を持っていない**
（時計が止まっていた 68 件も同じ理由でばらばらに並ぶ）。

`media_file.rel_path` は `TEXT NOT NULL UNIQUE` なので、**単独で tie-break として
成立する**（`id` を足す必要すらない）。副産物として RAW+JPEG の並びも決定的に
なる（`"JPG" > "CR2"` なので主が必ず先。いまは id の偶然でそう見えている）。

**ただし索引の張り替えが要る。** `sqlite_master` を見て数えると、`id DESC` で
終わる索引は **2 本**（`media_file_listing` と `media_file_derived_listing`）。
`0013` の `media_file_by_profile` は `(profile_id, role, rel_path)` なので対象外で、
`0022` の `media_file_by_role` は **`0023` が DROP している**。並びだけ変えると
ORDER BY を索引で満たせなくなって一時 B-tree のソートに落ちる。**Phase 9 の索引の顛末と同じ形なので、張り替えと
実測をセットにする。**

### 既に送った 81 件の直し方

プロファイルを変えると `sync_builtins` が新しいリビジョンを作り、
`POST /profiles/canon-eos/recompute` が `captured_at` を計算し直す。そのとき
`jobs/recompute.py` の `_requeue` が **`fix_datetime_after_upload` が真なら
送信済みを `needs_recheck` へ戻す**ので、**Immich 側の日時も追って直る**。
壁時計の数字は変わらない（`12:33:05+00:00` → `12:33:05+09:00`）ので、
**画面の見え方は変わらない**。

`identical` が真でも、次のすべてがそのまま出る。

  「承認する」があった場所なので目が滑る）。**「却下する」は `identical` の分岐の外に

`state = 'awaiting_datetime_approval'` だけで数え、`identical` を見ていない。

待たずに `complete` にする。書き換えないなら守るものが無い）。

**決着（Phase 16）。** 送信の時点で、観測した現在値が提案と同じ瞬間なら

立たないので、`awaiting_total` の数え方は変えていない（**数えるときに `identical` を

無い場面の語彙ではない）、変更のある行が 1 つも無いときは見出しで決断を迫らない
