## 実機で分かった ffmpeg の挙動

- **concat demuxer は data ストリームを運べない。** `-map 0:4`（`tmcd`）を渡すと
  `Cannot map stream #0:4 - unsupported type` で即座に落ちる。**DJI は `tmcd` を
  持つので、concat 経路が成立する余地が無かった**（毎回 TS へ落ちていた）
- **TS 経路は `hvc1` を `hev1` に変える。** HEVC のパラメータセットの置き場所が
  変わるので、Apple 系で再生できないことがある。**通らずに済むこと自体に価値がある**
- **concat 経路の出力には `tmcd` が残る。** `-map` から外しても、mp4 muxer が
  コンテナのメタデータから作り直す。だから `streams` 検査は一致ではなく
  「足りない／増えた」で見る

## 環境と運用で分かったこと

- **`latest` は引き直されないことがある。** TrueNAS の Custom App は手元にある
  同名のイメージを使うので、検証中は `:sha-xxxxxxx` で固定する方が確実
  （どの版を試したかも残る）
- **`library` などを ZFS データセットに分けてはいけない。** 公開が `link(2)` なので
  同じファイルシステムに要る。`preflight` でデバイス番号を先に見ると早い
- **開発 LXC から実機の API に直接届く。** セッション cookie をもらえば、
  チェックリストを API で進められる（CSRF は二重送信 cookie）

**リストアは手順どおり動いた。** バックアップ後に作った派生物は**孤立として報告され、

1. **`-wal` / `-shm` は「戻さない」ではなく「消す」。** 残すと「古い DB に新しい WAL」の

2. **所有者と権限の復元。** root で `cp` すると `root:root` になり、非 root の
   アプリが書けなくなる
3. **バックアップを `DATA_ROOT` の中に置かない。** アプリが読み書きできる領域なので、
   侵害されたときにバックアップごと触れる（これは実測ではなく読んで気づいた）

**この検証で、入れたばかりの回収ログが実際に役に立った。** 何が起きたのかが
`docker logs` の 1 行で分かる（それまでは無言だった）。

## 11 番の実測 —— 前提が崩れた（2026-08-21）

**`timestamps.py` は「カードの時刻欄に UTC オフセットが無い（または 0）」を前提に、
mtime の UTC 表現を壁時計として使っている。DJI Osmo Pocket 4 ではこれが成り立たない。**

公開時にソースの mtime をそのまま保つので、**カードをマウントし直さずライブラリ側で
測れる**（`test_the_published_file_keeps_the_source_mtime`）。

```
DJI_20260808125404_0002_D.MP4   長さ 1518.0 秒
  ファイル名の開始（現地）: 12:54:04+09:00
  録画終端（現地）        : 13:19:22+09:00
  mtime を +09:00 で描画  : 13:19:24+09:00   終端との差 +2.00 秒
  mtime を UTC で描画     : 04:19:24+00:00   終端との差 -32,398 秒（9 時間）

DJI_20260815155045_0029_D.MP4   長さ 89.5 秒
  mtime を +09:00 で描画  : 15:52:16+09:00   終端との差 +1.83 秒
  mtime を UTC で描画     : 06:52:16+00:00   終端との差 -32,398 秒
```

**mtime は「録画終端の現地壁時計」を正しい瞬間として持っている**（+2 秒はファイルを
閉じるまで）。**DJI は exFAT の `OffsetFromUtc` を書いている。**

### 直すべき 3 か所（連動している）

1. **`timestamps.py::_wall_clock` の mtime fallback。** ファイル名に時刻を持たない
   ファイル（DJI なら `PANORAMA/PANO_0001.JPG`）の `captured_at` が**オフセットぶん
   ずれる**。今回のカードには写真が無かったので表に出ていないだけ
2. **`publisher._collision_stamp`。** 元ファイルの衝突接尾辞が同じだけずれる。
   タイムゾーンを渡す配管が要る
3. **`merger._recording_end_ns`。** `decisions.md` は「派生物の mtime は取り込みの
   mtime と同じ表現にする」としていたが、**測ったら取り込みの mtime は真の瞬間**
   だった。つまり**いまは派生物の方がオフセットぶんずれた epoch を持っている**
   （やり直した結合物の接尾辞 `_20260808145223` が現地の 14:52:23 と一致していたのが
   その証拠）

**片方だけ直すと `library/` と `derived/` で接尾辞の壁時計がずれる** ——
`decisions.md` がまさにその懸念を書いていた。3 つを同時に変える。

**リセット後の再取り込みが検証の機会になる。** 直さずに取り込むと、写真を足した
ときに誤った `captured_at` が入り、再計算をかけることになる。

### 直した（2026-08-21）

3 か所を同時に変えた。**失敗するテストを先に書いて、失敗を確認してから**直している。

| 直したもの | 変えた内容 |
| --- | --- |
| `timestamps._wall_clock` | mtime の fallback を、UTC 表現ではなく**解決した TZ を付けた aware な値**にする。TZ の解決を壁時計より先に動かした（`timezone_policy: none` は描画に使う TZ が無いので UTC のまま）。**naive の壁時計へ落とさない** —— 落として `_attach_offset` で付け直すと、DST の戻りでどちらの 1 時間かを失う（Europe/Berlin の `2026-10-25T01:30:00Z` が 1 時間ずれた。codex のレビューで見つかった） |
| `publisher._collision_stamp` | `captured_at` を解決したのと同じ TZ（`CapturedAt.tz`）で描画する。**配管は増えていない** —— 手順 5 で `captured` が既に手元にある |
| `merger._recording_end_ns` | `captured_at` の瞬間をそのまま epoch にする（`.replace(tzinfo=UTC)` をやめた）。オフセットの無い値だけ UTC と見なす（放っておくとシステムの TZ で読まれる） |

**再計算（`recompute_timestamps`）の入力は `media_file.mtime_ns`**（公開した実体に
固定された値）で、`source_entry` から引くのは**カード上の原名だけ**。後で再スキャン
しても値が動かないので、この形でよい。

**ただし既存 DB は自動では直らない。** プロファイルの定義（JSON）は変わっていないので
`ProfileRegistry._upsert_revision` は新しい版を作らず、既存行の
`captured_at_revision_id` は「現行版で算出済み」のまま残る。**手で
`POST /profiles/{slug}/recompute` を叩けば**同じ版でも全行を巡るので `original` の
`captured_at` は直る。**直らないもの**（再計算は日時の 5 列しか触らない）:

- 旧 `_recording_end_ns` で付けた**派生物の実ファイルの mtime と `media_file.mtime_ns`**
- 旧 `_collision_stamp` で**すでに確定した公開名**（ライブラリは不変。§7）

**検証環境はリセットして取り直す前提**なので、その環境ではここで閉じる。実データを
持ったまま上げる利用者が出たときは、影響するプロファイルの明示的な再計算と派生物の
作り直しを手順に書く。

### mtime の意味はプロファイルが宣言する（`mtime_semantics`）

**「mtime は真の瞬間」は、`OffsetFromUtc` を書く媒体でしか成り立たない。** valid bit が
立っていない媒体では、exfat ドライバはマウントの `time_offset`（既定 0）で epoch を
合成するので、その値は**現地の壁時計を UTC と見なした疑似 epoch**になる（FAT32 には
そもそもオフセットの欄が無い）。そういうカードを `force_offset` のプロファイルで
取り込むと、fallback だけがオフセットぶんずれる。

**1 機種の実測を全機種の契約にはできない。** API は `POST` / `PUT /profiles` を公開して
おり、任意のユーザ定義プロファイルが `force_offset` を選べる。しかも**確定済みの公開名と
派生物の mtime は再計算では直らない**ので、事故が出てから欄を足すと不可逆な部分が残る
（codex のレビューでの指摘。利用者の判断で、いま足した）。

| 値 | 意味 | 該当する媒体 |
| --- | --- | --- |
| `wall_clock`（既定） | 現地の壁時計を UTC と見なした疑似 epoch | FAT32、valid bit の立たない exFAT |
| `instant` | 真の瞬間 | `OffsetFromUtc` を書く exFAT（実測した DJI） |

**既定を `wall_clock` にした。** 宣言の無い定義（この欄より前に作られたユーザ定義
プロファイル）に「瞬間」を仮定すると黙ってずれる。ビルトインで明示するのは実測した
`dji-osmo` だけで、`canon-eos` と `generic-dcim` は `timezone_policy: none` なので
どちらでも同じ値になる。

**宣言は 3 か所に効く**（`_wall_clock` の fallback・`_collision_stamp`・
`_recording_end_ns`）。規則は `timestamps.mtime_wall_clock` と `timestamps.mtime_ns_of`
の 2 つに閉じてあり、3 か所はそれを呼ぶ。

**ビルトインの定義が変わったので、`sync_builtins` が `dji-osmo` の新しいリビジョンを
作る。** 既存行の `captured_at_revision_id` は前の版を指したままになるので、画面から
再計算をかける手がかりになる。

**変異試験は 8 件すべて検出**（`tz=zone` を `UTC` に戻す、接尾辞に TZ を渡さない、
`_recording_end_ns` を旧実装に戻す、naive の保険を外す、など）。素通りは無い。

**テストの前提もずらした。** `test_recompute.py` の `ns()` は「カード上の壁時計を
UTC 表現の epoch にする」ヘルパだったので、**真の瞬間**を書く `ns()` と、
**その TZ の壁時計**を書く `ns_local()` に分けた。分けないと、`force_offset` の
fixture と `timezone_policy: none` の fixture が同じヘルパを違う意味で使うことになる。

## B-2（古くなった派生物の削除）を実機で踏んだ（2026-08-21）

**消せたが、画面からは到達できなかった。**

実機のライブラリには `derived` の `media_file` が 3 本あった。

```
8b7fe845  ..._0002-0006_MERGED.MP4                 66.31 GiB  ← 組み直しで置き換わった古い出力
0c922d08  ..._0002-0006_MERGED_20260808145223.MP4  66.31 GiB  ← 現行（衝突接尾辞が付いている）
d912d21f  ..._0027-0028_MERGED.MP4                  1.02 GiB  ← 現行
```

`DELETE /api/media/8b7fe845…` は **200 で通り**、後始末も設計どおりだった。

| 項目 | 前 | 後 |
| --- | --- | --- |
| `media_file` | 32 | 31 |
| うち `derived` | 3 | 2 |
| 孤立（`GET /orphans`） | 1 件 | **1 件のまま**（増えていない＝実体も消えた） |
| `missing`（行はあるが実体が無い） | 0 | 0 |

**問題は到達経路だった。** `MergeRepository.list_groups` は
`WHERE superseded_by_id IS NULL` を**両方の分岐に**持っており、置き換えられた
グループを `status` を指定しても返さない。削除ボタンはグループ行の「できたファイル」
表示の中にあったので、**まさに片付けたい 66 GiB にだけボタンが出なかった**。
`skipped` のグループは一覧に出るので、そちら経由では到達できていた。

**「実装した」と「つながっている」は別**（Phase 4 で学んだ形）の再発。今回は
**実装した本人が、実機の状態を見るまで気づかなかった**。`GET /media/stale-derived`
を足し、画面には「もう使われていない出力」の節を置いた。**判定は削除の前提と同じ

## 送信のリースが 61 秒で切れた —— 実機でしか出ない不具合（2026-08-23）

**残りをまとめて送ったら、ジョブが 61 秒で `failed` になった。**

```
ジョブ f11a20c9… のリースが無効（キャンセル・失効・別の所有者）
12:55:42 → 12:56:43（61 秒）。リースは 60 秒
```

### なぜ今日まで出なかったか

送信は `with_lease_pulse` でリースを延ばすが、**心拍を打つのは「1 回の送信が
`HEARTBEAT_INTERVAL`（20 秒）より長かったとき」だけ**。

```python
thread.join(timeout=HEARTBEAT_INTERVAL)
if not thread.is_alive(): break   # 20 秒以内に終わったら、打たずに抜ける
```

そして**送信のループに `ctx.heartbeat()` が無かった**。つまり **1 件ずつが速いと
リースが一度も延びない**。

| 送ったもの | 所要 | 通ったか |
| --- | --- | --- |
| 写真 10 枚 | 3 秒 | 通った（60 秒以内に終わる） |
| 440 MB 動画 | 3 秒 | 通った |
| **71.2 GB 結合物** | 364 秒 | 通った（**1 回が長いので 20 秒ごとに心拍**） |
| **小さい動画を連続** | **61 秒で死亡** | どの 1 件も 20 秒未満 → 心拍ゼロ |

**いちばん普通の使い方（写真を何十枚も送る）で必ず踏む。** 1 枚 1 秒なら
60 秒で落ちる。`recheck.py` と `recompute.py` はループの各回で `heartbeat` を
打っており、**送信だけが打っていなかった**。

### 直した

送信ループの先頭に `ctx.heartbeat()` を 1 行。回帰テストは
`test_uploader.py::test_many_quick_sends_do_not_lose_the_lease`（1 件 0.6 秒 ×
5 件、リース 1 秒。**実機と同じ `LeaseLost` で赤くなることを確かめてから**書いた）。

**変異試験で実装が 1 行減った。** 最初は `recheck.py` に合わせて
`assert_lease()` も置いたが、**消してもテストが 1 本も落ちない**。調べると、
キャンセルはループ先頭の `cancelled()` が見ており、失効と横取りは `heartbeat`
自身が `LeaseLost` で捕まえる（`extend_lease` は満期前の行しか更新しない）。
**保険に見えて誰も守っていない行**だったので落とした。

### 副産物 —— `origin = unknown` を実機で初めて踏んだ

落ちたジョブは、**送信を終えた直後に記録を書く前に死んだ**。Immich にはファイルが
あるのに、こちらの記録は未完了。再送すると Immich は `duplicate` と答え、
コードは `unknown`（自作と証明できない）と判定した。

```python
if upload_status == "created":      return "created_by_us"
if first_check_result == "reject":  return "pre_existing"
return "unknown"   # ← 初回が accept だったことは自作の証明にならない
```

**安全弁は正しく働いた** —— 証明できない資産の日時は書き換えず、承認を求めた。
画面から承認したら「日時の補正を承認して書き戻した」で通り、**承認の経路
（`awaiting_datetime_approval` → 書き戻し）も実機で初めて動いた**。

**ただし画面の文言が嘘だった。** 「先に誰かが Immich へ上げていた写真です」は
`pre_existing` の説明で、この record の `origin` は `unknown`。**実際はほぼ確実に
こちらが上げたもの**で、家族には「知らない人が上げた写真がある」と読める。
持ち越しに入れた。

## 10 番（取り外し）—— 合格（2026-08-23）

**画面の「取り外す」を押しても、何も起きなかった。** これは正しい:

```python
def close(self, volume_instance_id: str) -> None:
    if volume_instance_id in self._open:
        raise VolumeBusy("実行中のジョブがこのボリュームを使っている")
```

**掴んでいるジョブが無ければ本当に何もしない。** カードはジョブが要るときだけ
読み取り専用でマウントし、ジョブが終わればその場で外すので、**押した時点で
既に安全に抜ける状態**だった。200 は返っている。

### 物理的に抜いた後の `dmesg`

```
usb 2-4: USB disconnect, device number 8
rndis_host 2-4:1.0 ...: unregister 'rndis_host'
sd 33:0:0:0: [sdj] Test Unit Ready failed: hostbyte=DID_NO_CONNECT
sdj: detected capacity change from 226656280 to 0
sd 32:0:0:0: [sdk] Synchronize Cache(10) failed: hostbyte=DID_NO_CONNECT
```

**`I/O error` もファイルシステムのエラーも 1 行も無い。** `DID_NO_CONNECT` は
「もう居ない相手に話しかけた」で、消えた装置をカーネルが確認しにいっただけ。
`Synchronize Cache failed` は USB ストレージを予告なく抜けば必ず出る行で、
**読み取り専用マウントなので流し込むものが無い**ことが裏付けられた形。

**ついでに分かったこと。** `rndis_host` の登録解除も出ており、**このカメラは
USB でネットワーク機器としても見えている**（マスストレージだけではない）。
装置は 2 つ（`sdj` = 108 GiB の内蔵、`sdk` = SD カード）で、カーネル側でも
別々に見えている。

`/devices` は空になった。

### ただし、画面は何も言わない（持ち越し）

このボタンの値打ちは**返ってくる答えそのもの**にある —— 「いま抜いて大丈夫」か
「まだ抜かないで」か。ところが**成功したときに何も言わず、一覧を読み直すだけ**
（`CardDetail.tsx` / `Home.tsx` の `act`）。カードは挿さったままなので一覧にも
残り、**画面には変化が一切ない**。利用者には**どちらだったのか分からない**。
「取り外す」という名前も、何かが起きる（アンマウントされる）ように読める。
