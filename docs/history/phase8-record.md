## どう進めたか

**10 のタスクを 1 つずつ「実装 → レビュー → 修正 → 再レビュー」で回した。**
Phase 7 と同じ形だが、**規模が 1/3 なので巡数も浅い** —— 修正の輪は最大 1 巡で、
5 タスクは指摘なしで着地した。

- 実装者とレビュアーは別。**レビュアーは差分だけを渡され、自分で変異を当てて
  実測する**ことを求められた
- 指摘は**修正ラウンド**（同じ実装者を再開する）で閉じ、**範囲を限った再レビュー**で
  確かめてから台帳に `complete` を書いた
- 仕様とブリーフが衝突したとき、指摘を容れるか退けるかを迷ったときは、

### 一度は「検出できない」と書かれたが、そうではなかったもの

**`if state not in CLAIMABLE_STATES` を `if True` にする変異**（Task 6 の申告。
レビュアーも追認していた）。

> 再試行で降りる経路（`_retry_or_fail` の `pending`、`_release_unknown` の
> `needs_recheck`）は、いずれも**送信のストリームを最後まで読み切った後**に
> 来るため、`settle()` の `missing` が 0 になり、呼んでも呼ばなくても同じ。
> 差が出る場面を作るには preflight の失敗と成功を 1 回の `run` の中で
> 切り替える必要がある。

**preflight ではなく `bulk_upload_check` を 1 回だけ落とせばよかった。** これは
preflight より後・最初の 1 バイトより前にあるので、`ImmichUnavailable` を投げると
**1 バイトも送らずに `pending` へ降り、同じ `run` の中でもう一度 claim される**。
`settle()` の `missing` は大きさそのままなので、`if True` にすると 11 バイトの
ジョブが `bytes_done_all == 22` で終わる（実測）。

Phase 7 でも同じことが 3 回起きている（`StubEventSource`・`JobHistory` の
SSE の枝・`App.tsx` のルート表）。**「検出できない」は、その時点の道具と
筋書きの限界であって、性質ではない。**

- **サーバの応答の「欄」は、view とは別に数える。** `/devices` の

  **抜けていたのは真ん中の 1 行**である

  watcher が `scan` を積まない不具合は、**そもそも実機のログから見つかった**。

  テストは無かった**（戻り値の対称性だけが試験されていた）

## 申し送られた 2 件（Task 6 → Task 10）

Task 6 のレビューが見つけ、進行役が「この差分の責任ではない既存の穴なので
Task 10 へ」と裁定した 2 件。**代償は「偽物のテストは、直るまで『claim の延長が
守られている』と誤読させ続ける」**と書いてから渡された。

### A. 偽テスト —— 何も守っていなかった

`test_the_claim_is_extended_while_the_file_is_sent` は、`claim_next` の
`lease_seconds` を 1 秒にして 1.5 秒の送信を仕込み、「claim が切れれば commit
できない」を見ているように読める。**が、`_send` の直前に通る `_guard` が
`prepare_side_effect` を呼び、その既定が `lease_seconds=60` なので、送信が
始まる時点で claim の寿命は 60 秒に戻っている。**

**実測: `also=lambda: extend_claim(...)` を消しても 62 件が全通した。**

直し方は、`prepare_side_effect` が延ばす寿命も 1 秒にする（テスト側で包む）
＋ `extend_claim` が実際に呼ばれたことを数える。直したあと同じ変異を当てると、
`ClaimLost` が送出されて FAIL する。

**この形の偽テストは、名前と docstring がいちばん自信ありげに書かれている。**
「短いと延長の有無で差が出ない」と docstring が正しく述べているのに、**その
「短さ」を作る経路を 1 つ見落としている**（claim を延ばす場所が 2 つある）。

### B. 無防備な守り —— テストが 1 本も当たっていなかった

`_send` の `ownership_errors=(LeaseLost, ClaimLost)`。含め忘れると、claim の
延長（`also`）が投げた `ClaimLost` が `except ownership_errors` に掛からず、
**待つ側だけが即座に抜けて、走っているスレッドが後から数十 GiB を送り終える**
（呼び出し側は失敗したと見ているのに副作用が進む）。

**実測: この引数を消しても全通した。**

## この作り方から分かったこと

- **申し送りは、代償を書いてから渡すと本当に着地する。** Task 6 の
  Important-3 は「この差分の責任ではない既存の穴」として Task 10 へ回したが、
  **「偽物のテストは、直るまで『守られている』と誤読させ続ける」**という代償を
  台帳に書いたので、4 タスク後でも優先度が落ちなかった
- **「テストを直す」と「テストを緩める」は、直した本人には区別が付かない。**
  Task 8 の 2 件はどちらも正しい方向の修正で、**副作用として主張が消えた**。
  報告の「見たいものは変えていない」は嘘ではなく、**測っていなかった**
- **受け入れコマンドに入っていない検査は、無い。** E2E は 8 タスクぶん赤で、
  全員が緑だと思って進んだ。**「唯一の錠」と docs に書いた検査を、計画の
  チェックリストに書き写さなかった**のがこの穴の全部である
- **配線は両端が試験されていても抜ける。** `/devices` の 3 欄は、作る側
  （`VolumeService`）と使う側（`homeSections`）の両方に錠があったのに、
  **間の 1 行（ルートの写し）だけが無検証**だった。Phase 7 の
  「『叩いた』で止まる試験は、叩いた後を守らない」の裏返しで、
  **両端を守る試験は、真ん中を守らない**
- **死んだ定義は、変異試験に嘘をつく。** `db/uploads.py` の重複した
  `RELEASED_STATES` は、前の写しを壊すと「守るテストが無い」ように見える。
  **生き残りを見たら、まずそれが本当に実行されている行かを確かめる**
